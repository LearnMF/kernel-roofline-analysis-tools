# KDA on gfx936：第二阶段（构造式设计）方法论与结论（2026-10-14）

第一阶段的结论见 `docs/kda_phase1_summary.md`：局部候选只在现有设计附近搜索，方法上缺少“构造并评估新设计”这一层。第二阶段就是补这一层。

## 1. 做了什么

| 步骤 | 产物 | 结果 |
|---|---|---|
| ① 数据流 IR | `examples/kda/kda_ir.py`，`results/kda-ir-20261013/` | 生产拆分的读写字节与 optrace 逐个 launcher 一致（16 个形态 × 10 个 launcher，误差 0）；运算量与 kda_bound 一致 |
| ② 拆分层分析 | `kda_partition.py`（IR README 第 6–7 节） | 中间张量流量 19.2 KB/tok·head：跨阶段交接 44%、反向内部 kernel 之间的交接 45%、副本 5%。**按 chunk 并行的反向重新分组被锁死**：C=64 时卡在容量上（即使运算内部精简到最小）；C=32 时多出的交接字节（+1952 B）超过融合能省下的（−1536 B）。W-free 写法要多交接约 1.5 KB，也不划算 |
| ③ 构件成本库 | `examples/kda/blocks/`，`results/kda-blocks-20261014/blocks.json`，`blocks_model.py` | VMEM 读写各 540 个测点、LDS、barrier、MMAC、VALU、发射队列、访存延迟（空闲与负载下）、kernel 级开销；与机器峰值的比值：LDS 1.00、HBM 写 0.95、MMAC 0.95、HBM 读 0.92、L2 读 0.91 |
| ④ 递推单步模拟器 | `isa_sim.py`（循环体用 SQTT 抽出的生产代码） | 4 个递推实例误差 −18% / +2% / −17% / −17%；独立检验集（合成 kernel）32 个中 18 个在 ±20% 以内 |
| ⑤ 构造式模型 | `trace_sim.py` + `derive11.py` | **只用构件库、结构（SQTT 中的指令流）和访存特性，不用任何被预测 kernel 的实测时间**，推算 12 个生产 kernel：22 个 kernel × 形态点中 17 个在 ±20% 以内，各 kernel 时间之和误差 −7% / −13% |
| ⑥ 全局布局求解（第一轮） | `kda_layout.py`、`layout_eval.py` | 否决“g、kn/qn 改为 s4b 原生布局”（生产方和其他消费方多付的代价超过收益）；推荐“dA/dAqk 改为分块布局”，模型预测 1.8–2.1% |
| ⑦ 实测检验 | P-57（`results/kda-gfx936-20261014-p57-tile/`） | 逐位一致；第一版暴露 partition camping（R49）；修正后实测只有 0.2–1%，在噪声范围内 → **模型高估小幅收益 6–10 倍**，不合入 |

## 2. 关键发现（与第一阶段的直觉不同的地方）

1. **生产 ISA 必须从生产二进制里取**。用 `hipcc -S` 另外编译的 ISA 和生产 .so 不同，例如 MODE 4 的循环体分别是 395 条和 314 条。所以改用 SQTT 记录的实际执行序列。
2. **微基准本身会骗人**：
   - MMAC 依赖延迟 47.6 周期，是循环边界造成的假象，直线代码下 srcC 累加链只要 10.5 周期；
   - 访存“延迟”有 386 / 588 和 700 / 950 两组，前者是反复访问同一批行、命中了缓存；
   - barrier 的 57 周期里包含了约 47 周期的循环开销；
   - 好几个微基准的地址起点低位相同，导致 partition camping。

   每个构件都要用 ISA 核对，有条件的话用 SQTT 交叉验证。
3. **数据来自显存时，TA 会在整个取数过程中被占住**。所以单条 VMEM 指令的代价取决于访问模式在显存里的效率：s4b 的分片访问平均每条约 100 周期，而 L2 表里只有约 43。
4. **VMEM 没有硬性的在途指令上限**：每个 wave 约有 16 条的发射队列，满了之后按单元的接收速率放行。单个 wave 的 LDS 发射有自己的速率上限（ds_read2_b64 每条 16 周期）。
5. **驻留数要按资源计算**：每 SIMD 768 个 VGPR、最多 10 个 wave、每 CU 64 KB LDS。体检卡里截在 3 的字段对 gate、tail、l2n_apply 都是错的。
6. **改布局要检查同时在跑的 CTA 之间的地址间距（R49）**：分块顺序不对，会让 H 大的形态慢 10–40%。

## 3. 模型能信到什么程度

| 用途 | 可信度 | 依据 |
|---|---|---|
| 现有 kernel 的绝对时间 | ±20–30% | derive11：17/22 个点在 ±20% 以内 |
| **否决**大幅负收益的方案 | 可信 | g、kn/qn 改原生布局：生产方多付几百 µs，方向不会错 |
| **批准**小于约 5% 的收益 | **不可信** | P-57：预测 1.8–2.1%，实测 0.2–1% |
| 受延迟限制的 kernel 的变化量 | 偏乐观 | 访问模式代价的差异在真实 kernel 中大多被掩盖（与 R46 同一类） |

**使用规则**：模型用来筛掉方案、给方案排序；预测收益低于约 5% 的，一律以实测探针（按 R46）为准。

## 4. 仍未解决的问题
- gate 高估 37–44%：VALU 与超越函数的共享方式未确认，混合微基准需要重新设计。
- s4a/s4b 从 16K/12 到 16K/48 的超线性变慢（实测 4.6–5.0 倍，模拟 3.9 倍）：TLB 是待验证的假设。
- 合成检验集中有几项的实测结果不单调，无法解释。

## 5. 总的结论与下一步
- **拆分层**：在 gfx936 上被容量和交接字节锁死。
- **访问方式层**：单个布局候选的收益在 1% 量级，即使有多个候选，加起来也有限。
- **剩下的空间在实现层和递推单步**：TP8 下串行链是第一性原理下限（16K/12 约 0.83 ms），而现在三个递推合计约 1.8 ms，单步是微基准下限的 1.7–2.2 倍。递推单步模拟器在这里最可信（±20%），所以下一步转向**运算内部和递推单步的重新设计**，用模拟器给候选定价，再按 R46 做实测探针。

## 6. 阶段目标调整（2026-10-16，用户决定）
- **目标从“变成算力受限”改为“逼近算法访存下限”**。依据（`results/kda-gfx936-20261016-a2-hscale/README.md` 第 5 节）：KDA 训练（C=64，d=128）的算法算术强度约 122 FLOP/B，低于 BW1000 的屋脊点（约 380 FLOP/B）。即使字节降到必需量、80 个 CU 全部用上，MMAC 利用率也最多约 32%，所以物理上限是访存屋脊。
  - 16K/TP8：当前 6.35 ms，算法下限 0.65 ms，差距约 10 倍。其中约 6 倍来自拆分方式带来的多余字节，约 1.7 倍来自执行效率。
- **算子优化不考虑 Megatron 层面的配置**：全层重算、keep-state 的 auto 行为、activation offload 都属于框架配置。算子基准一律按普通前向+反向测（keep-state=0、不开 checkpoint）。keep-state 的数据（`results/kda-keepstate-20261016/`）只作为框架侧选项的参考。
- **TP8 下 CU 闲置**：Megatron-LM-das/Bridge 预训练时，KDA 每个 micro-batch 只有 1 段（cu_seqlens=None），所以这是真实负载下的情况。在逐位一致、不多占显存的约束下，这是结构性的：空闲 CU 最多只能换回约 29% 的递推吞吐量，因为全卡访存延迟会随活跃 CU 数增加而上升。

- **R58**（P-84，2026-10-16）：根据 SQTT 等待点设计探针前，必须先把等待点对到源代码位置（用 PC/ISA 映射，或 vm_wait_map），不能只凭“每个 wave 出现几次”去猜。P-84 就是把 phase 1 的 8 次等待误判成了 VNEW。
- **R59**（P-84b）：一个循环里如果既有 global 读、又有 global 写，而指针没有 `__restrict__`，编译器就不会把下一轮的读提到本轮的写之前，每一轮都会单独付一次访存延迟。解决办法是先单独写一个循环把读全部发出，再进入计算循环。
