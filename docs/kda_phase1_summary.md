# KDA on gfx936：第一阶段方法论与结论（定稿，2026-10-13）

## 1. 范围与目标

- **对象**：Kimi Delta Attention 的训练前向 + 反向，手写 HIP 实现（G2）。运行环境是 Hygon gfx936（BW1000），用于 Kimi K3 训练。
- **约束**：
  - 与生产版逐位一致、确定、可重入；
  - checkpoint 兼容；
  - 符合 cuDNN Frontend PR #556 的集成契约；
  - 同步到 Megatron-LM-das 和 flash-train（`feat/kda-g2`）。
- **目标**：把 KDA 从访存受限推向计算受限，并形成一套可复用、有证据支撑的优化方法论。

## 2. 方法论（第一阶段实际使用的流水线）

| 步骤 | 工具 / 产物 | 作用 |
|---|---|---|
| 1 机器标定 | `machines/gfx936-bw1000.json`、`examples/kda/hier_roofline.py` | 用实测的可达峰值，而不是标称峰值：HBM 读 1339 GB/s、写 1100 GB/s，L2 6.1 TB/s，LDS 15.2 TB/s，BF16 MMAC 476 TF，FP32 VALU 29.7 TF |
| 2 体检卡 | `results/kda-ceiling-cards-20261013/`（16 个形态 × 每个 kernel） | 每个 kernel 在 LDS/L2/HBM 三层上的位置，TA/VALU/MMAC/LDS/链五项利用率，以及三种下限：**现指令流下限**、**接口下限**、**第一性原理下限**；外加 TA 放大倍数、缺口类型、SQTT 停顿归因 |
| 3 先消融、再实现 | 每个候选先做“工作量不变、只去掉被怀疑的开销”的消融，测出上限（R42），并用 ISA 核对（R43） | 上限不够就不实现。本阶段至少有 10 个候选在这一步被排除 |
| 4 实现与门禁 | `gate_all.sh`：22 组逐位门禁，含 keep-state、极端门控、变长 | A 类改动必须逐位一致（R23） |
| 5 A/B 测量 | `ab_kernels.sh`：每边 5 个进程，显存位置抖动（R20），多形态，必要时换机复测 | 结论以改动所在 kernel 为准，算子总时间受位置效应影响 |
| 6 B 类精度门禁 | `bclass_gate.sh`：FP64 oracle（PR #556 的 reference_kda.py），17 组配对，R23b 四条 | 只有确实要改变数值的方案才进入，并且由用户决定 |
| 7 扰动式结构评估 | `examples/kda/decomp_eval.py`：t = max(R·λ, F·imb·e)，驻留数下降按实测曲线计算 | 对现有 kernel 做融合、重算、去副本、改几何等变换，先在 9 个历史实验上回测，再给候选打分 |
| 8 合入 | bw52 生产版 → bw7 → flash-train，设备代码指纹三方一致 | — |

## 3. 结果

### 3.1 合入的优化（本阶段）
| 编号 | 内容 | 收益 |
|---|---|---|
| P-52 | 递推中生产方算一次 exp2(G_last)，消费方直接读 | 算子约 0.5–2.5% |
| P-53 | 前向 GEMM1 的 h 片段在寄存器中复用给 o，每步少 8 条 ds_read2 | 前向递推 1–2%，算子 0–0.3% |
| P-54a | bwd_tail 每个 warp 只读一次 rstd 再广播，g_raw 改为 short2 读取 | tail 快 3.2–5.3%，算子 0.3–0.5% |

### 3.2 被证伪或关闭的方向（附证据）
| 方向 | 结论 | 证据 |
|---|---|---|
| dav / wu / 递推的 LDS 冲突 | 冲突计数高，但消融上限只有 0–2.5% | R42 |
| bN 宽读、dhu 16 B 写、prep 的 R scratch | 上限 ≤0.3% | r14 筛选 |
| 去掉 bf16 RNE（截断） | 递推快 6–10%，但无法逐位一致，B 类精度也不合格（误差为生产版的 3–4.4 倍） | r14、P-56 |
| P-51（dhu 64 列） | 慢 11–16% | 几何改动 |
| P-54b/c（tail 加宽 / 地址移到 SALU） | 慢 1–2.7% / 持平 | R45 |
| B4b（tail 融进 s4b）、F6（s4a+s4b 合并）、P-13（l2n 由消费方重算）、F9（递推与并行任务并发） | 历史实测均为负 | R37、R12/R30、R35 |
| F3a / P-55（s4b 自己算 dAqk） | 逐位一致、无溢出，但 s4b 慢 18–25% | R46 |
| L1 / L2（转置副本） | 修正访问模式后预测为负 | R47 |
| F2（去掉 Wb，由 dhu 转置）、G（wu 算 g）、D（dav 并进 dh 递推） | 模型预测为负 | 评估器 |
| C1（两个递推并发） | 6 个形态慢 1–26% | R48 |
| F8（换块内求逆算法） | 公开实现和最新研究中，没有比“列扫 + 分块合并”更好的方案 | 第二轮调研 |
| B 类（窄格式交接、rhu、rz） | 精度过关的收益不到 1%，收益约 2% 的截断精度不合格 | B 类评估 |
| s4a/s4b 每 CU 2→3 个 CTA | 换算到算子约 3.7–5.1%，s4b 的 LDS 压不到 21 KB | 标定 P1 |

### 3.3 本阶段新增的规则（完整版见 `docs/playbook.md`）
- **R42**：计数高不等于时间代价，先用消融测上限。
- **R43**：消融必须保持其余工作量不变，并用 ISA 核对。
- **R44**：gfx936 的 MMAC 结果依赖 K 的顺序。
- **R45**：VMEM 指令条数不等于 TA 开销，代价取决于访问模式。
- **R46**：往受延迟限制、寄存器满载、按 wave 分路径特化的 kernel 里加代码，代价会被模型低估。
- **R47**：访问模式要从代码推出来，不能凭名字猜。
- **R48**：两个递推 kernel 不能靠并发重叠。

## 4. 差距在哪

| 形态 | 实测 | Σ现指令流下限 | Σ接口下限 | 第一性原理下限 |
|---|---:|---:|---:|---:|
| 16K/12（TP8） | 6.53 ms | 5.17 | 3.70 | 0.83（受串行链限制） |
| 16K/48（TP2） | 25.63 ms | 20.73 | 14.38 | 2.62（受显存限制） |

| 层 | 倍数（16 个形态） | 本阶段兑现了多少 |
|---|---:|---|
| 实现层：实测 / Σ现指令流下限 | 1.21–1.30 | 一小部分（P-52/53/54a） |
| 访问方式层：Σ现指令流 / Σ接口下限 | 1.3–1.65 | 几乎没有 |
| 拆分层：Σ接口下限 / 第一性原理下限 | 4.5–5.7 | 没有 |

- **没有一个 kernel 真正到顶**：单个 kernel 的实测是自身现指令流下限的 1.06–1.9 倍。
- **算力不是瓶颈**：MMAC 利用率普遍在 0.1–0.5。
- **主要限制是指令发射和延迟**：按时间占比，16 个形态中有 60–85% 的时间属于发射受限，15–33% 属于显存受限，小 H 的递推受串行链限制。

## 5. 为什么第一阶段停在这里：方法上缺了一层

“局部候选都失败了”**不等于**“软件层面已到极限”。第一阶段的搜索有三个结构性的局限：

1. **体检卡是诊断工具，不是设计工具**。它的下限是按现有指令流和现有接口算的，只能评价现有 kernel，不能告诉我们一个不同的设计要花多少时间。
2. **评估器是扰动模型**。它从实测 kernel 出发做加减法，可以评估“合并 A 和 B”“去掉副本 X”这类改动，但无法估算一个还不存在的 kernel，比如换一种 tiling、布局或算法写法。
3. **候选只在现有设计的邻域里生成**，即沿数据流的边做两两融合、重算、增删副本。真正的设计空间没有系统搜过：
   - 算法写法：是否显式构造 W/U、dAqk 放在哪、keep-state 还是重算；
   - chunk 大小、V 切片宽度；
   - 反向按 LDS 容量如何分段；
   - **所有中间张量的布局作为一个整体来选**；
   - 按形态选择不同的拆分。

**访问方式层的浪费主要来自布局，而布局是全局耦合的**：生产方写成什么布局，所有消费方就按什么方式读。单独改一个 kernel，往往会让另一个变差（P-20、P-32、F2 都是例子）。这类问题只能整体求解，局部调优必然碰壁。

**硬约束会限制方案，但不能证明现方案最优**：
- 每 CU 只有 64 KB LDS，每 wave 最多 256 个 VGPR：NVIDIA Hopper 版反向每个 CTA 用 225 KB，做到 3 个 kernel，在这里放不下；
- 递推只有 4H 个 CTA，每步延迟 1–2.6 µs，与并行工作并发会产生争用；
- 按 chunk 并行与按 head 串行两种并行结构之间必须交接数据；
- MMAC 结果依赖 K 的顺序，与逐位一致的要求一起，限制了布局技巧。

## 6. 第二阶段：构造式设计（计划）

| 步骤 | 内容 | 负责 | 验收门槛 |
|---|---|---|---|
| ① 构件成本库 | gfx936 上每种基本操作的实测成本和组合规律：全局读写（按模式、数据来源）、LDS 与 barrier、MMAC 依赖链、VALU 与地址运算、**参数化的递推单步模型**、kernel 级开销 | 另一个 agent（`docs/tasks/kda_blocks_task.md`） | 只用构件库预测 4 个生产递推实例的单步时间、dav/tail/wu 的 TA 和 LDS 周期，误差 ±20% |
| ② 数据流 IR | KDA 前向 + 反向的运算、张量、尺寸、依赖、并行结构，包含算法写法的变体和每个张量的布局选项 | 主 agent | 能复现现有拆分的全部接口字节（对照 optrace） |
| ③ 构造式成本模型 | 给定设计（运算分组、tiling、布局、重算、chunk），用构件库组合出每个 kernel 的时间和 LDS/VGPR 占用 | 主 agent | **只用构件库“从零”推算现有 11 个 kernel 的时间，误差 ±20–30%**；过了这一关才用于新设计 |
| ④ 设计空间搜索 | 在约束下枚举拆分 × 写法 × 布局 × 按形态分派，16 个形态分别排序 | 主 agent | 输出前几名的预测收益、可行性、逐位一致与否、风险 |
| ⑤ 骨架验证 | 对前 1–2 名先写只含数据搬运和主循环结构的骨架 kernel，实测核对预测 | 主 agent | 预测误差在可接受范围内，再请用户决定是否正式实现 |

**理论空间**：现有拆分下 1.6–2.1 倍（实测 / Σ接口下限），再加上拆分层能被新设计消掉的一部分。能兑现多少，要等第 ③ 步验收、第 ④ 步搜索之后才能回答。这也是“软件层面是否只能如此”这个问题的回答方式。
