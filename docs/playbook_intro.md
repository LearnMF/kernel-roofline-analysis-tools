# 给团队的介绍：playbook 讲什么，以及为什么说 KDA 已经优化到上限

> 用途：向团队介绍 `docs/playbook.md`（v3），并以 KDA 为例，说明“已经到上限”这个结论是怎么得出的。
> 建议讲 30–40 分钟。第 1–2 节讲方法，第 3 节讲 KDA 案例，第 4–5 节讲经验和怎么上手，第 6 节是常见问题。
> 文中的数据都来自仓库里的实测记录，出处见第 7 节。

---

## 1. 我们要解决什么问题

做算子优化时，最常被问也最难回答的是三个问题：
1. **离上限还有多远？** 要能说清楚是哪一种上限。
2. **下一步该往哪里使劲？** 是局部调优、减少工作量，还是重构？
3. **什么时候可以停？** “试不动了”不能算理由，要有证据。

常见的三个坑：
- **只报加速比**：快了 5%，但不知道离上限还差多少。
- **局部打转**：反复调已经很快的部分，最大的那块差距却一直没动。
- **用错手段**：差距在 A 项开销上，却用了压 B 项开销的手段，结果收益为 0。

`playbook.md` 就是为回答这三个问题、避开这三个坑而写的。它的规则来自 KDA 上约 94 个编号实验（P-0 到 P-93），每一条都有实验来源。

## 2. playbook 的核心思想（五条）

### 2.1 第一步：先认清算子，选对视角
比较两个数：
- **算子的计算强度**：每读写 1 字节做多少次运算，单位 FLOP/B；
- **硬件的平衡点**：峰值算力 ÷ 峰值带宽。

| 情形 | 结论 | 该看什么 |
|---|---|---|
| 计算强度远低于平衡点 | 受访存限制 | 读写多少字节、带宽用得多充分 |
| 计算强度远高于平衡点 | 受算力限制 | 算力利用率 |
| 两者接近 | 两者都起作用 | 逐个 kernel 看每一种资源 |

视角选错了，后面的分析都会跑偏。

### 2.2 四个下限与三项开销
用“搬家”打个比方：

| 下限 | 比方 | 严格定义 |
|---|---|---|
| **理论下限** | 只搬非搬不可的东西 | 完全融合时的最少读写和计算，与怎么拆 kernel 无关：每个输入读一次、每个输出写一次，加上串行链 |
| **拆分下限** | 分成多个工种接力，每次交接都要先放进中转仓库（显存） | 按现有的 kernel 划分，每个 kernel 只读写自己的输入输出 |
| **满载下限** | 每个工种的车没装满、路绕远了 | 每个 kernel 按它实际执行的指令和字节，最忙的那个硬件单元一刻不停所需的时间 |
| **实测** | 再加上路上等红灯的时间 | 实际耗时 |

四个下限一定满足：理论下限 ≤ 拆分下限 ≤ 满载下限 ≤ 实测。**相邻两个之间的倍数，就是一项开销**：

| 开销 | 这一项回答的问题 | 怎么量 |
|---|---|---|
| **kernel 间交接开销** | 拆成多个 kernel 后，中间结果在显存里多搬了多少？ | 拆分下限 ÷ 理论下限 |
| **kernel 内冗余开销** | 每个 kernel 比它自己的输入输出多读写、多执行了多少？ | 满载下限 ÷ 拆分下限 |
| **硬件空等开销** | 最忙的那个硬件单元，有多少时间在等，没在干活？ | 实测 ÷ 满载下限 |

> 实测 = 理论下限 × kernel 间交接开销 × kernel 内冗余开销 × 硬件空等开销

### 2.3 每项开销都有自己的手段
| 开销 | 浪费的是什么 | 有效手段 | 无效手段（KDA 里的反例） |
|---|---|---|---|
| **硬件空等开销** | 硬件在等，没干活 | 预取、指令重排、发射节奏、占用率、grid 顺序 | 减少字节：硬件本来就不忙 |
| **kernel 内冗余开销** | kernel 内部多读写、访存方式差 | 改布局、合并访存、去掉重复读取 | 调度：重排读取后，等待只是挪了个地方（P-79） |
| **kernel 间交接开销** | kernel 之间经显存交接中间结果 | 融合、前向保存结果给反向用、换算法 | kernel 内部的任何调优 |

**用错手段，收益就是 0。**

### 2.4 每一轮怎么做
```
量四个下限、算出三项开销 → 选“最大、而且有手段可用”的那一项 → 定位到 kernel，再定位到源代码行
→ 先测上界（消融、容量预算、模型否决）→ 先登记预测，再实现
→ 逐位门禁 → 同一张卡上交替做 A/B → 合入，或否决并写成规则 → 重新量一遍
```

要点：
- **先测上界，再动手**：消融的做法是工作量不变，只去掉怀疑的那项开销，测出最多能省多少。
- **模型的用法**：用来否决方案很可靠；但模型预测收益不到约 5% 的，一律要实测。
- **每次失败都留一条规则**：现在共有 R1–R62，`playbook.md` 第 8.1 节可以按问题查。

### 2.5 判停准则（四条同时满足才停）
| # | 准则 | 需要的证据 |
|---|---|---|
| 1 | 硬件空等开销：每个 kernel 剩下的差距都已定位到源代码，并做过探针，单项能回收的不到约 1% | 每个 kernel 一行：剩余差距、查过的路、结论 |
| 2 | 边际收益：最近连续 4 个以上探针，最好的一个低于 0.5% | 探针列表 |
| 3 | kernel 内冗余开销和 kernel 间交接开销：每条路都已被实测的硬件限制或明确的约束挡住 | 每块剩余字节一行：大小、被什么挡住、实验编号 |
| 4 | 算法形式已经系统筛选过，剩下的单项收益有上界，而且与约束冲突 | 候选表 |

**“到顶”永远是相对一组约束而言的**。KDA 的约束是：结果逐位一致、不改算法、显存不超过 FLA 默认。

## 3. KDA 案例：从“远没到顶”到“到顶”

### 3.1 KDA 的特点
| 项 | 数值 |
|---|---:|
| 算法本身的计算强度 | 122 FLOP/B |
| 实际计算强度 | 我们 21，FLA 13 |
| 平衡点 | BW1000 355，A800 156，H20 36 |

由此得到三个判断：
- KDA **受访存限制**，优化目标是少读写字节、把带宽用足。
- BW1000 的算力优势用不上：我们是 H20 的 3.45 倍，但只用了 3.7%。
- H20 的带宽优势正好用上：它是我们的 2.85 倍。

### 3.2 起点和终点（16K/TP8）
| | 理论下限 | 拆分下限 | 满载下限 | 实测 | 硬件空等开销 | kernel 内冗余开销 | kernel 间交接开销 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 10-13 | 0.83 ms | 3.70 | 5.17 | 6.53 | 1.26 | 1.40 | 4.46 |
| **10-17（最终）** | 0.83 | **3.35** | **4.41** | **5.32**¹ | **1.21** | **1.32** | **4.04** |

¹ 满载下限和实测在同一张卡上测，bw52 快卡上实测为 5.61 ms。10-09 的起点是 8.53 ms。

### 3.3 过程：每一阶段压的是哪一项开销
| 阶段 | 理论当时指向哪一项 | 做了什么 | 16K/TP8 |
|---|---|---|---:|
| 10-09 ~ 10-11 | kernel 内冗余开销最大（47%） | 体检卡判断每个 kernel 卡在哪个单元，据此加宽访存、去掉副本 | 8.53 → 6.75 ms |
| 10-12 ~ 10-13 | kernel 间交接开销（从没动过） | 尝试融合：全部失败 | → 6.53 |
| 10-14 ~ 10-16 | 先证明 kernel 间交接开销被容量锁死，再转向递推单步（硬件空等开销） | 构造式模型、模拟器 | → 6.36 |
| 10-16 ~ 10-17 | kernel 间交接开销里不需要片上容量的那部分，加上硬件空等开销 | 逐个张量记账、把 SQTT 等待点对到源代码行、按 head 数折算耗时 | → **5.61** |

**累计快了 1.52 倍**，全部结果逐位一致。
- 对 A800 上的 FLA：从落后变为全面领先，几何平均 1.25 倍。
- 对 H20 上的 FLA：从 0.62 追到 0.88，64K/TP8 已经反超。

### 3.4 为什么说已经到上限
实测离理论下限还有约 6.4 倍，可以拆成三项开销相乘：**4.04（kernel 间交接）× 1.32（kernel 内冗余）× 1.21（硬件空等）**。每一项都有证据说明再挖不动了。

**kernel 间交接开销（4 倍，最大的一块）：被片上容量锁死**
- **工作集放不下**：反向时每个 chunk·head 要同时用到约 180–200 KB 数据，而 gfx936 每个 CU 只有 64 KB 共享内存。
- **融合必须降低占用率，而降低占用率的代价实测过**：
  - s4b 只放 1 个 CTA 每 CU，慢 355 µs；
  - prep 两个 kernel 合并，慢 565 µs；
  - 做成全异步流水后，每 CU 1 个 CTA 仍慢 19–30%。
- **13 次融合和并发实验，0 次成功。**
- **能走的已经走完**：不需要片上容量的“前向保存、反向不算”已经做了，显存也用到了批准的上限。
- **剩下的路都与约束冲突**：降低数值精度（中间结果改用 bf16）可以快约 3%，但误差会升到 FLA 的 1.05–1.06 倍，已按“精度不妥协”否决；改算法只剩 2–4% 的空间，而且做不到逐位一致。

**kernel 内冗余开销（1.3 倍）：已贴近访存的物理规律**
- 访问已经合并时，代价只取决于字节数：4 条 4 B 读和 1 条 16 B 读耗时相同（10.72 对 10.56 µs）。
- 剩下的布局副本不能去掉：改成跨布局读，每条要约 169 周期，原生布局只要约 22 周期。

**硬件空等开销（1.2 倍）：剩下的等待逐项查明是结构性的**
- 最大的一块在 s4b（7.5%），已经试过的路：
  - 调整读取顺序：等待只是挪了地方；
  - 去掉屏障：上限不到 8 µs；
  - 换布局：净收益 0.3–0.8%；
  - 重算 dAqk：慢 18–25%；
  - 读取直接进共享内存：+0.4%；
  - 每 CU 放 3 个 CTA：共享内存压不下来。
- 其余 kernel 都已贴着各自的满载下限。
- 满载下限假设所有等待都能完美掩盖，实际做不到，所以“实测/满载下限 = 1.2”不等于还能挖 20%。

**边际收益**：最近 4 个探针（P-89 到 P-92），最好的一个只有 +0.4%。

**剩下所有能看到的空间加起来**：上界 5–8%，现实约 2–4%。除 F8（改算法）外，每一项都不到约 1%。

### 3.5 为什么能赢 A800、赢不了 H20
把速度比拆成三项：速度比 = 字节优势 × 利用率之比 × 峰值带宽之比。

| 对手 | 字节优势 | 利用率之比 | 峰值带宽之比 | 速度比 |
|---|---:|---:|---:|---:|
| A800 FLA | 1.57 | 1.10 | 0.76 | **1.32（我们快）** |
| H20 FLA | 1.57 | 1.66 | **0.35** | **0.92（我们慢）** |

- **硬件和算法本身决定了理论差距**：三家离各自的理论下限都有 7–16 倍，没有哪个实现能接近，所以这 6–8 倍的理论差距不是我们实现得差。
- **我们能控制的两项，我们最好**：读写字节比 FLA 少 36%，带宽利用率 63%，三家最高。
- **输给 H20，只因为它的带宽是我们的 2.85 倍**。
- **同一条因果链（容量 → 拆分 → 降占用率 → 延迟暴露）在三张卡上松紧不同**：gfx936 上卡得最死；NV 有更大的共享内存和异步拷贝，卡得较松。详见 `kda_qa_intensity_platforms.md`。

### 3.6 什么情况下会重新打开
| 条件 | 能打开多少 |
|---|---|
| 放开精度约束 | 约 3–5% |
| 允许改算法形式 | 约 2–4% |
| 硬件：更大的片上内存、不受 vmcnt 牵连的异步拷贝、更高的带宽 | kernel 间交接开销可能大幅下降 |

## 4. 方法论的效率：我们学到了什么
| 手段 | 尝试 | 合入 | 命中率 |
|---|---:|---:|---:|
| kernel 内部调优（压硬件空等开销和 kernel 内冗余开销） | 约 75 | 约 40 | 约 50% |
| 融合与并发（压 kernel 间交接开销） | 13 | 0 | 0% |
| 前向保存、反向不算（压 kernel 间交接开销，不需要片上容量） | 4 | 4 | 100% |
| 改数值格式 | 3 | 0 | 精度政策不允许 |
| 事前否决（只靠模型、消融或容量测算，没有写实现） | 15 以上 | — | — |

四条经验：
1. **大收益来自新的观察角度**，不是在原有 kernel 上反复微调：
   - 判断每个 kernel 卡在哪个硬件单元：L16，访存加宽；
   - 逐个张量记账：P-82/87，前向保存结果，反向不再重算；
   - 按 head 数折算耗时：P-88，grid 顺序，TP1 上快 16.5–18.8%。
2. **最贵的教训是融合**：13 次，0 收益。如果事先做容量预算，并用消融测出降低占用率的代价，大部分可以提前否决。现在这已写进 playbook 的前置检查。
3. **小收益必须实测**：模型预测“快 9%”的一次，实测慢了 18–25%（P-55）。
4. **判停要有据**：“到顶”结论里的每一项开销都有可以复查的数据，而不是因为试不动了。

## 5. 拿到一个新算子，怎么用 playbook
| 步骤 | 做什么 | 工具或参考 |
|---|---|---|
| 1 | 列出算子由哪几类工作组成（流式、计算密集、串行链），算出每个任务单元的工作集，和片上容量比较 | playbook 1.1 |
| 2 | 算出两个计算强度（算法本身的、当前实现的），和硬件平衡点比较，选定视角 | playbook 1.2；`dataflow_graph.py` |
| 3 | 量四个下限：理论下限（第一性原理模型）、拆分下限（optrace 加字节账目）、满载下限（体检卡）、实测（hipprof），算出三项开销 | `kda_bound.py`、`byte_ledger.py`、`ceiling/cards.py` |
| 4 | 选最大、而且有手段可用的那一项开销，做对应的前置检查 | playbook 4.3 |
| 5 | 定位到 kernel，再到源代码行 | SQTT 加 `map_waits.py` |
| 6 | 先测上界，登记预测，然后实现，过门禁，做 A/B | playbook 3.2 |
| 7 | 合入或否决；每次否决都写成一条规则 | playbook 第 8 节 |
| 8 | 每轮重新量一遍，检查判停准则，记录效率指标 | playbook 第 5、6 节 |

## 6. 常见问题

**Q1：离理论下限还有 6–8 倍，凭什么说到顶了？**
理论下限假设完全融合，而完全融合在 gfx936 上做不到：工作集是片上容量的 3 倍，降低占用率的代价也已实测。FLA 在 NV 卡上同样离自己的理论下限 7–16 倍。在“必须拆分”这个前提下，剩下的两项开销（kernel 内冗余 1.3 倍、硬件空等 1.2 倍）都已逐项查明是结构性的。

**Q2：硬件空等开销是 1.2 倍（实测/满载下限），是不是还能再挖 20%？**
不是。满载下限假设每个 kernel 内部的等待全部被完美掩盖，有依赖、有屏障时做不到。判停看的是第 2.5 节的准则 1，即每个 kernel 的剩余差距是否都已查明，而不是这个比值。

**Q3：为什么不放开精度，换那 3%？**
项目规则是精度第一，结果要求逐位一致。实测表明，中间结果改用 bf16 后，dq/dk 的误差会从比 FLA 略好（0.995 倍）变成比 FLA 略差（1.05–1.06 倍）。用户已明确不接受。

**Q4：H20 以后会不会更快？**
有可能。NV 卡上，这条因果链还远没卡死，FLA 也没有把它用尽，写一个融合度更高的实现，H20 还能更快。但完全融合后，KDA 在 H20 上会变成受算力限制，理论下限约为 0.72 ms。

**Q5：为什么计算强度达不到 122？**
因为字节变多了，不是因为延迟。字节变多，是因为片上放不下，必须拆成多个 kernel 经显存交接。延迟是间接起作用的：它让融合这条路走不通。详见 `kda_qa_intensity_platforms.md` 的问题 1。

**Q6：这套方法换个算子还适用吗？**
四个下限与三项开销、判停准则和流程是通用的。具体的阈值和规则目前只用 KDA 标定过，建议下一个算子（例如 rmsnorm 或 GEMM）按 playbook 完整走一遍来检验。
