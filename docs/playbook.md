# HCU 算子优化方法论（v3，2026-10-18）

> **定位**：这是本仓库**唯一的通用理论指导**，适用于任何算子，回答三件事：离上限有多远、下一步往哪里走、什么时候可以停。
> - 每个数怎么测、口径是什么：`methodology.md`
> - 工具怎么搭：`design.md`
> - 完整案例：Kimi K3 的 KDA 算子，见附录 A 的文档索引
>
> **v2 → v3 的变化**：
> - 增加“先认清算子、选对视角”；
> - 四层改用最终定义（算法必需、接口、资源、实测），并列出每层有效和无效的手段；
> - 增加判停准则和方法论效率的度量；
> - 规则库补齐到 R62，并附“按问题查规则”的索引；
> - 规则和数据来自 KDA 上约 94 个编号实验（P-0~P-93），时间是 2026-10-09 ~ 10-17。

## 0. 一页流程

```
① 认清算子：工作类型、工作集与片上容量、计算强度与硬件平衡点 → 选视角（第 1 节）
② 量四层：算法必需 ≤ 接口 ≤ 资源 ≤ 实测（第 2 节）
③ 选层：最大、而且有手段可用的那一层；手段必须与层对应（第 4 节）
④ 定位：先找到 kernel，再找到源代码行（SQTT 等待点对到源代码，R58）
⑤ 先测上界：消融、容量预算、模型否决；预测收益不到约 5% 的一律实测（第 4.4 节）
⑥ 先登记预测，再实现 → 检查 ISA → 逐位门禁 → 同一张卡上交替做 A/B（第 3 节）
⑦ 合入，或否决并写成规则（第 8 节）
⑧ 重新量四层，检查判停准则（第 5 节）；同时记录效率指标（第 6 节）
```

## 1. 第一步：先认清算子，选对视角

### 1.1 算子由哪几类工作组成
把算子拆成几类工作，每一类各自受不同的资源限制：

| 类型 | 典型受限资源 | 主要手段 |
|---|---|---|
| 并行的流式计算（逐元素、归约、布局转换） | 显存带宽，或访存发射单元 TA | 少读写字节、提高带宽利用率 |
| 并行的计算密集部分（小矩阵乘、三角求解） | 矩阵乘单元 MMAC / 向量单元 VALU / 共享内存 LDS 的发射，以及延迟 | 减少指令、改善调度与占用率 |
| 串行链（递推、扫描） | 每一步的延迟，以及并行度 | 缩短每一步的关键路径、提高并行度 |

还要比较一个量：**每个任务单元（例如一个 chunk·head）的工作集 vs 片上容量**（每 CU 的 LDS、每个 wave 的寄存器上限）。工作集放不下时，算子只能拆成多个 kernel，拆分层的代价就是结构性的（第 4.3 节）。

### 1.2 访存视角还是算力视角
两个恒等式对任何算子都成立，因为利用率本身就是从实测时间倒推出来的：

| 视角 | 恒等式 |
|---|---|
| 访存 | 耗时 = 读写字节 ÷（带宽利用率 × 峰值带宽） |
| 算力 | 耗时 = 运算量 ÷（算力利用率 × 峰值算力） |

选哪个，取决于**计算强度**（每读写 1 字节做多少次运算，FLOP/B）和**硬件平衡点**（峰值算力 ÷ 峰值带宽）：
- 计算强度远低于平衡点：受访存限制，用访存视角，目标是少读写字节、提高带宽利用率；
- 计算强度远高于平衡点：受算力限制，用算力视角，目标是提高算力利用率；
- 两者接近：两种限制都起作用，单一视角下的利用率都会偏低，必须逐个 kernel 看资源层（第 2.2 节）。

计算强度要算两个（R29）：
- **算法本身的**：运算量 ÷ 算法必需字节，代表完全融合后能达到的强度；
- **当前实现的**：运算量 ÷ 实测字节。

两者相差很大，说明主要差距在拆分层。

### 1.3 跨实现、跨平台的粗分解
由访存恒等式可以直接得到（R16 的一般形式）：

> 速度比 = T_对方 ÷ T_我们 = **字节优势**（B_对方 ÷ B_我们） × **利用率之比**（u_我们 ÷ u_对方） × **峰值带宽之比**（P_我们 ÷ P_对方）

使用时注意三点：
1. 这是恒等式，三项相乘一定等于实测的时间比。它只说明差距落在哪一项，不能当作预测。
2. 只有字节优势完全由我们的实现决定。利用率之比同时取决于双方：对方在它自己的硬件上不平衡时，比如算力被削减，它的利用率也会被拉低。
3. 字节数要用同一种测量口径，例如 DRAM 计数器。用不同平台的 L2 大小时，要注明差异。

再配合 R15 按阶段做三方对比（我们、同一块硬件上的竞品、竞品在它自己的硬件上），就能区分“确定能追回的实现差距”和“硬件差距”。

### 1.4 KDA 示例（16K/TP8）
| 项 | 数值 |
|---|---:|
| 算法本身的计算强度 | 122 FLOP/B |
| 当前实现的计算强度 | 我们 21 FLOP/B，FLA 13 FLOP/B |
| 平衡点 | BW1000 355，A800 156，H20 36 |

结论：KDA 受访存限制，在 H20 上接近平衡。BW1000 多出来的算力用不上，H20 多出来的带宽正好用上。

| 对手 | 字节优势 × 利用率之比 × 峰值带宽之比 | 速度比 |
|---|---|---:|
| A800 FLA | 1.57 × 1.10 × 0.76 | 1.32 |
| H20 FLA | 1.57 × 1.66 × 0.35 | 0.92 |

详见 `kda_report.md` 第 0、5 节。

**延伸问答**（`kda_qa_intensity_platforms.md`）：
- 为什么实际计算强度只有 21 / 13，达不到理论的 122：字节变多 ← 必须拆分 ← 片上容量不够；延迟是间接起作用的。
- 同一条因果链（①容量 → ②拆分 → ③降占用率 → ④延迟暴露 → ⑤并行结构）在 gfx936、A800、H20 上各卡在哪一环，以及这如何导致各卡的性能差异。

## 2. 四层上限模型

### 2.1 定义
| 层 | 含义 | 怎么得到（工具） |
|---|---|---|
| **算法必需** | 与怎么拆 kernel 无关的下限：每个外部输入读一次、每个输出写一次，加上前向保存给反向的状态，以及串行链。显存、矩阵乘、VALU、串行链这几项取最大值 | 第一性原理模型（KDA 用 `examples/kda/kda_bound.py`），以及算子级数据流（`dataflow_graph.py`） |
| **接口** | 按现有的 kernel 划分，每个 kernel 只读写自己的输入输出、访问方式也理想时的时间，再求和 | 记录每个 kernel 的输入输出张量（optrace），按标定的带宽换算（`byte_ledger.py`） |
| **资源** | 每个 kernel 按当前的指令流和字节数，最忙的那一项资源（见 2.2）的忙碌时间，再求和 | 体检卡 `ceiling/cards.py`：PMC 计数 ÷ 标定后的峰值 |
| **实测** | 实际耗时 | hipprof 设备时间，以进程为样本 |

四层一定满足：算法必需 ≤ 接口 ≤ 资源 ≤ 实测。

与 v2 的命名对应：
- 物理下限 = 算法必需；
- 拆分代价 = 接口 − 算法必需；
- 多余工作 = 资源 − 接口；
- 执行效率损失 = 实测 − 资源。

### 2.2 资源层：逐项看每种资源
一个 kernel 是否到顶，要**逐项看下表中的每一种资源**，取占用最高的那一项作为主要受限因素。只看带宽和算力会漏掉真正的瓶颈：KDA 的递推 kernel 在 HBM 30%、计算 30% 的情况下，被访存发射单元（TA）卡在了 86–88%。

| 角度 | 指标（按正在工作的 CU 计算） | 标定后的饱和值 | 来源 |
|---|---|---|---|
| HBM 带宽 | 实测字节 / 可达带宽（按 grid 大小修正） | 1338 GB/s（理论值的 72.6%） | L0 `hbm_*`、`hbm_read_vs_ctas` |
| 计算流水线 | `SQ_ACTIVE_INST_VALU` / (周期 × CU 数) | 0.97–1.00 | L0 `pmccal` |
| MMAC（HFU） | (ACTIVE − INSTS) × 8192 / (时间 × 峰值)，即实际执行的 FLOPs | 理论 491.5 / 可达 476 TFLOPS（bf16） | L0 `mmac_*` |
| **MFU** | 算法的模型 FLOPs（op_spec 中的 `flops`；反向 = 2 × 前向）/ (时间 × 理论峰值) | — | PaLM 附录 B 的定义；KDA 为 2.6%，不是计算受限 |
| **向量访存发射（TA）** | `Σ TA_TA_BUSY` / (GRBM × CU 数) | **0.92** | L0 `vmem_issue` 加 PMC（模型 v2 新增） |
| 存储的发射成本 | 每条指令覆盖的字节范围，约每 512 B 27 周期 | — | L0 `vmem_store` |
| LDS | 冲突率，以及 `SQ_WAIT_INST_LDS` 所占比例（判断冲突是否在关键路径上） | — | P-1 |
| 依赖链 | 递推的 T_cp_impl / 实测时间 | — | op_spec 中的 `serial` 字段 |
| 并行度 | 正在工作的 CU / 总 CU 数 | — | grid 大小 |
| 系统层 | 空泡占比、launch 开销 | 每次 launch 约 2 µs | L1 timeline |

**判定规则**（`kra/model/bounds.py`）：
- **某项资源 ≥ 80%**：已饱和，只能减少落在它上面的工作量，例如字节数、指令数。改用更宽的访存，只在访问还没有合并时才有效（R54）。
- **某项资源在 60–80%**：受吞吐限制，可以减少工作量，或者提高这项资源的效率。
- **所有资源都低于 60%**：受延迟限制，用 SQTT 找出暴露的等待点，并对到源代码行（R58）。
- **实测已经接近资源下限**：这份指令流已经到头，只能减少工作量，或者重构。
- **注意**：TA 的忙碌时间里包含等待数据返回的时间（R54）。访问局部性改善（R60）会让资源下限本身下降，所以资源下限不是固定不变的。

### 2.3 每一层的差距：浪费类型与对应的手段
| 差距 | 浪费的是什么 | 有效手段 | 无效手段（反例） |
|---|---|---|---|
| 实测 − 资源 | 硬件在等，没有在干活 | 预取、调整指令顺序、发射节奏、占用率、grid 顺序 | 减少字节：资源本来就不忙 |
| 资源 − 接口 | kernel 内部多读写、访问方式差、指令冗余 | 改布局、合并访存、去掉重复读和副本 | 调度：P-79 重排读取，等待只是挪了地方 |
| 接口 − 算法必需 | kernel 之间经显存交接 | 融合、前向直接保存反向要用的结果、换算法形式、改数值格式 | kernel 内部的任何调优；把生产方并进消费方式的重算（R12、R30、R57） |

**层和手段一一对应，用错手段就不会有收益**，这条规则本身就来自实验。

## 3. 每一轮怎么做

### 3.1 每轮必须回答的三个问题
每一轮，不论有没有改代码，都要产出一份上限评估。KDA 的模板见 `results/kda-gfx936-20261010-ceiling/README.md` 和 `results/kda-ceiling-cards-20261017-p88/`。评估要回答：
1. **这是什么类型的算子或 kernel，受哪一种资源限制？**
2. **离上限还有多远？** 要分清是离哪一层。
3. **下一步做什么？** 方向必须由“最大、而且有手段可用”的那一层决定，而不是看哪个改起来方便。

只汇报加速比，不算完成这一轮。

### 3.2 一轮实验的流程
```
上限评估（四层，加上每个 kernel 的判定）
  → 选目标：按可回收的时间排序，选择与主要受限因素对得上的手段
  → 定位：SQTT 等待点 → 对到源代码行（map_waits.py）+ 静态检查 ISA
  → 先登记预测：机制、指标怎样变、时间范围、什么结果算证伪（提交之后才能改代码）
  → 测上界：消融（工作量不变，只去掉被怀疑的开销，用 ISA 核对，R42、R43）、容量预算、模型否决
  → 风险大的改动先做原型 bench（R10）
  → 实现 → 检查 ISA（指令数、VGPR、scratch == 0，R55）
  → 逐位门禁（含 keep-state、极端门控、varlen）；会改变数值的改动走 fp64 精度门禁（R23b）
  → A/B：同一张卡上交替，每侧 5 个以上进程，控制显存位置（R20、R41）
  → 对照预测：保留或回退；把结论写成规则
  → 合入：备份 → 安装同一份二进制 → 与备份逐位对比 → 所有部署点（包括下游库）同步
  → 重新做上限评估，检查判停准则
```

### 3.3 测量口径（要点；细节见 `methodology.md`）
- **样本**：独立样本是进程，不是窗口。收益小于进程间波动的，一律视为不显著。
- **对比方式**：跨版本的比值只在同一会话、同一张卡上交替测量。不同卡之间的绝对时间可能相差 ±5–10%，例如 bw52 的 HCU2、HCU4 比其它卡慢约 10%。
- **确认卡空闲**：测量前用 `hy-smi --showuse` 看利用率；`--showmemuse` 只能看显存占用，不能说明卡是否在忙。
- **跨平台的绝对值**：只采用离散度 ≤ 3% 的数据；竞品的数据跨会话复测一次，差异要在 ±0.5% 以内。
- **只看相关 kernel**：重新构建会改变显存分配位置（R41），判定时只看被改动的 kernel。

## 4. 怎么选方向

### 4.1 原则
1. 选**最大、而且有手段可用**的那一层。
2. 手段必须和层对应（2.3）。
3. 同一块硬件上竞品更快的阶段，属于确定能追回的差距，优先做（R15）。
4. 在我们已经领先的阶段，即使耗时最多也不优先：那就是局部打转。

### 4.2 怎样判断自己在局部打转
1. 每轮都做四层分解，看哪一层最大，以及它是怎么变化的。优化的那一层在缩小、另一层同时在变大，说明瓶颈在转移，这是正常的。
2. 某一层占比最大，最近几轮却没有针对它的手段，就是在局部打转。KDA 前 11 轮从没动过拆分层，正是这种情况。
3. 结构性方案（融合、换拆法、换算法）要先估算新方案的下限，并做容量预算，再决定投入；需要有人拍板。
4. 一定要和外部实现做对比（1.3、R15），防止只和自己比。

### 4.3 各层手段的前置检查
| 层 | 动手前必须做的检查 | 相关规则 |
|---|---|---|
| 执行层 | 等待点对到源代码行；查编译器是否因为别名把读串行化，或因为运行时分支而保守地多等；查发射节奏；用按 head 数（或按并发度）折算的耗时判断是不是局部性问题；提高占用率之前，先确认时间确实花在等待上 | R58、R59、R27、R8、R9、R21、R52、R60、R22、R17、R4 |
| 多余工作层 | 访问模式从代码推出来（每条指令覆盖几行、每行多少字节）；TA 代价看字节，不看指令条数；生产方和消费方两边都要算账；改布局要查同时驻留的 CTA 之间的地址间距 | R47、R54、R45、R7、R24、R49 |
| 拆分层，融合或重算 | 先做容量预算（VGPR 每 wave ≤ 256、LDS 每 CU 64 KB）；再用消融测“降占用率”的代价，确认宿主 kernel 还有余量；重算要按消费方的瓶颈资源定价；并发方案要测关键路径 kernel 在并发时的耗时 | R34、R37、R62、R61、R36、R12、R30、R57、R35、R48 |
| 拆分层，前向保存、反向不算 | 保存所需的显存是否在批准的预算内；能否做到逐位一致 | KDA：P-77b、P-82、P-87，4 次尝试 4 次成功 |
| 拆分层，换算法形式 | 先用 fp64 推导，证明数学等价；再在 PyTorch 里按 kernel 的精度做精度预判；最后才实现 | R23b |
| 数值格式 | 按精度政策决定：默认要求逐位一致；否则做 fp64 精度验收，并且每个张量都不能比生产版差 | R23、R23b、R25、R44、R53 |

### 4.4 模型的使用规则
| 用途 | 可信度 | 依据 |
|---|---|---|
| 现有 kernel 的绝对时间 | ±20–30% | 构造式模型：22 个点里有 17 个在 ±20% 以内 |
| 否决明显负收益的方案 | 可信 | 例如 g、kn/qn 改成原生布局：生产方要多付几百 µs |
| 批准小于约 5% 的收益 | **不可信** | P-57：预测 1.8–2.1%，实测 0.2–1%；P-55：预测快 9%，实测慢 18–25% |
| 往受延迟限制、寄存器已满的宿主 kernel 里加工作 | 偏乐观 | R46、R50 |

**规则**：模型用来否决方案、给方案排序；预测收益低于约 5% 的，一律以实测探针为准。

## 5. 判停：什么时候可以停

### 5.1 “到顶”的含义
“到顶”永远是**相对于一组约束**而言的，例如：结果逐位一致、不改算法、显存不超过某个预算。不能脱离约束说“已到物理极限”。

结论应该这样写：在约束 X 下，剩下所有能看到的空间上界是 a%，现实能拿到的是 b%，每一项为什么拿不到都有证据。

### 5.2 判停准则（四条同时满足）
| # | 准则 | 需要的证据 |
|---|---|---|
| 1 | **执行层**：每个 kernel 剩下的“实测 − 资源”，都已对到源代码并做过探针或消融，单项能回收的不到约 1% | 每个 kernel 一行：剩余差距 µs、受限资源、已经查过的路、结论（见 KDA 回顾第 5.1 节的表） |
| 2 | **边际收益**：最近连续 N 个（建议 N ≥ 4）结果逐位一致的探针，最好的低于 0.5% | 探针列表及各自收益 |
| 3 | **多余工作层和拆分层**：每一条能缩小它们的路，都被实测的硬件限制（容量、单个 wave 的延迟、争用）或明确的约束（精度、显存）挡住 | 每块剩余字节一行：大小、被什么挡住、实验编号 |
| 4 | **算法形式**：候选已经系统筛选过，剩下的单项收益有上界，并且与约束冲突 | 候选表：做法、估算或实测、结论 |

另外两点：
- **资源下限假设所有等待都被完美掩盖**。指令之间有依赖、有屏障时做不到，所以“实测 ÷ 资源 = 1.2”并不等于还能挖 20%。判停看的是准则 1，不是这个比值。
- **要列出剩下能看到的全部空间**，包括每项的收益上界和不做的理由，并汇总出上界和现实值。

### 5.3 什么情况下重新打开
- **放开约束**：数值格式、算法形式、显存预算。
- **硬件变化**：更大的片上内存、与 vmcnt 无关的异步拷贝、更高的带宽。
- **工作负载变化**：新的形态，例如 TP 或序列长度变化后，主要受限因素可能改变。

### 5.4 KDA 示例
16K/TP8 最终的四层：

| 层 | 值 |
|---|---:|
| 算法必需 | 0.83 ms |
| 接口 | 3.35 ms |
| 资源 | 4.41 ms |
| 实测 | 5.32 ms |

层与层之间的倍数：实测/资源 = 1.21，资源/接口 = 1.32，接口/算法必需 = 4.04。

- 拆分层：13 次融合或并发实验全部失败（第 6.2 节）；
- 最近 4 个探针，最好的只有 +0.4%；
- 剩下能看到的空间：上界 5–8%，现实 2–4%；
- 详见 `kda_retrospective.md` 第 5 节和 `kda_report.md` 第 4 节。

## 6. 方法论效率的度量

### 6.1 每个实验要记录什么
编号、日期、作用在哪一层、预测（机制、幅度、证伪条件）、结果（合入、否决、不显著）、收益、新增的规则。

### 6.2 指标
| 指标 | 含义 | KDA（2026-10-09 ~ 10-17） |
|---|---|---|
| 各层手段的命中率 | 合入数 ÷ 尝试数，按手段所在的层统计 | kernel 内部调优约 50%（约 40 / 75）；融合与并发 0%（0 / 13）；前向保存、反向不算 100%（4 / 4）；数值格式 0%（0 / 3，精度政策不允许） |
| 事前否决数 | 只靠模型、消融或容量测算否决、没有写实现的方向 | 15 个以上（F1、F7、F2、F8、chunk 16/128、C2、B4b 闸门、prep 合并、布局候选、F9 模拟等） |
| 预测记分 | 机制判断正确的比例、耗时落在预测区间的比例 | 截至 10-10：机制正确 13/14，耗时落在区间内 6/14（第 9 节） |
| 每阶段的收益 | 按阶段统计的加速比，以及这一阶段攻的是哪一层 | 10-09~10-11（多余工作层）1.26 倍；10-12~10-13（尝试融合）1.03 倍；10-14~10-16（递推单步）1.03 倍；10-16~10-17（逐个张量记账、grid 顺序）1.13 倍；累计 1.52 倍 |
| 判停所需的轮数 | 从最后一次显著收益（>1%）到判停，做了多少个探针 | 4 个（P-89 ~ P-92） |

### 6.3 从 KDA 得到的效率经验
1. **大收益来自新的观察角度**：最大的几项都来自“换一个角度看”：体检卡加入 TA 判定（L16）、逐个张量的字节账目（P-82/87）、按 head 数折算耗时（P-88）。在已有的 kernel 上反复微调，收益很小。
2. **最贵的教训是拆分层的融合**：13 次、0 收益。容量预算和“降占用率”消融如果在第一次融合之前就做，大多数可以事前否决。所以 4.3 把它们列为融合的前置检查。
3. **小收益必须实测**：模型批准小于 5% 的收益并不可靠（4.4）。
4. **每次失败都要留下一条规则**：R1–R62 全部来自实验。规则多了以后，事前否决的比例会上升，命中率也会提高。

## 7. 跨平台对照怎么做
1. 在三种情况下按阶段计时：我们、同一块硬件上的竞品、竞品在它自己的硬件上（R15）。
2. 用第一性原理模型给每个平台算出它自己的算法必需下限，比较“实测 ÷ 算法必需”。如果所有实现都离下限很远，说明差距主要来自硬件和算法本身，而不是实现水平。
3. 用 1.3 的恒等式，把速度比分解成字节优势、利用率之比、峰值带宽之比，指出差距落在哪一项。
4. 竞品在同一块硬件上更快的阶段，是确定能追回的差距；竞品在它自己的硬件上更快、在同一块硬件上不快的阶段，是硬件差距。

KDA 的例子见 `kda_report.md` 第 5 节和 `results/kda-xplat-3way-20261017/why_a800_not_h20.md`。逐环分析因果链在三种硬件上的松紧程度，以及它与各阶段耗时的对应关系，见 `kda_qa_intensity_platforms.md` 的问题 2。

| R23b 算法重组的精度门禁（B 类，用户 2026-10-12 确认） | 改变累加顺序或中间精度的改动（融合、重算、chunk 大小）按四条验收：① 确定性：同一输入重复运行逐位相同，固定顺序归约、不用原子操作；② 对 FP64 参考的精度不比现版本差：多 seed 配对，每个张量的几何均值比 ≤ 1+ε 且不显著变差，含极端门控；③ 不超过 FLA 的容差（相对 RMS：o 0.5%，dq/dk/dv 0.8%，dg/db 2%）；④ Megatron K3 的 loss 曲线与基线对齐。A 类（纯调度和数据搬运）仍要求与生产版逐位一致（R23） | 融合路线 |
| R24 字节还是模式 | 消融去掉一次写，同时去掉了字节和访问模式。重排布局之前，先确认节省来自访问模式还是字节；否则消费者可能为新布局付出更多（P-32：wu 快 1%，s4a 慢 2–4%） | P-32 |
| R25 小样本梯度的精度噪声 | 由大量元素归约成少数几个元素的梯度（dA_log、ddt_bias），单个用例的 rms_ratio 会随任何 fp32 级扰动摆动 ±10%。精度对比要用多 seed 配对统计，不能看单个用例 | P-26 的 seed 研究 |
| R26 SQTT 的 wave 等待占比是上限 | `hipprof --sqtt --sqtt-type 1` 给出每个 wave 的逐条指令发射时间，`sqtt_hotspots.py` 可以把等待归到具体的读。但等待占比是 wave 周期的占比，其它 wave 会填补空闲：dav 中两个串行循环占 45% 的 wave 周期，去掉第一个只让 kernel 快 5.6%，两个都去掉快 14–20%。一定要用 A/B 确认 | P-34/P-34b |
| R27 循环里的空写会挡住读的提前 | 循环体内按运行时条件判空后写全局（生产路径从不执行），编译器担心别名，不敢把后续的读提前到这次写之前，展开也没用。判空对整个 launch 一致，应提到循环外 | P-34b |
| R28 地址空间推断很脆弱，要查实际代码对象 | kernel 参数结构体被 lambda 取地址后，指针可能失去 global 来源，所有访存都变成 flat（同时计入 vmcnt 和 lgkmcnt，也不能用 SGPR 基址）。一个与之无关的改动（P-34 的展开）就让 wu 和 dav 的变长实例变成 flat。必须反汇编构建出的 .so 来查（用不同参数单独编译的结果不算数），修复办法是把参数指针显式标为 global | P-35 |
| R29 先算整个算子的计算强度 | 动手前，先用接口记录（optrace）得到算子级的数据流（`dataflow_graph.py`），算出最小字节（每个模型输入读一次、每个输出写一次）和完全融合后的计算强度，与硬件平衡点（可达峰值 ÷ 可达带宽）比较。平衡点远高于当前计算强度、MFU 又很低时，瓶颈在拆分方式本身，应先评估结构重组，再做局部调优。KDA 前 11 轮没有做这一步：BW 平衡点约 366 FLOP/B，当前约 24 FLOP/B，完全融合约 210 FLOP/B；接口流量是最小值的 8.7 倍 | 融合路线 |
| R30 消费者现场重算 ≠ 融合 | 让消费者现场重算中间张量，只有在消费者的输入流随之变小时才划算。如果消费者照样要读一份同样大的原始输入（例如读 raw q 而不是 qn），省下的只是生产者自己的读写；对于已达 99% 带宽的流式 kernel，这部分很小，而多出来的 VALU 和读会落在消费者的关键路径上。F1 中 l2n_apply 省下约 2%，wu 却慢了 22–27%。真正有价值的是生产者与消费者在同一个 kernel 里完成，中间结果不经过 HBM 的写和读 | F1（P-36） |
| R31 手写异步流水的等待必须让编译器看见 | gfx936 上用 inline asm 发出 `buffer_load … lds` 或 `buffer_store` 时：等待用 `__builtin_amdgcn_s_waitcnt`，不要写在 inline asm 里（waitcnt pass 看不到 asm 中的等待，会在循环内重新插入 `vmcnt(k)`，把异步流水排空）；循环外的不变量读要在进入循环前用空 asm 的 `"v"` 输入可见地消费掉，否则循环头合并时取悲观状态，每轮迭代都会重新等待；循环内不要留任何编译器生成的访存指令（写也用 asm 发出，越界偏移做屏蔽），这样手工计数才精确。验收标准：反汇编中循环体内没有编译器插入的 `vmcnt` | P-37 |
| R32 asm 写出的 buffer store 要自己处理 EXP_CNT 冒险 | gfx9 上超过 64 位数据的 VMEM store 是异步读取数据 VGPR 的（EXP_CNT），编译器只为自己生成的 store 插入保护。用 inline asm 发出 store 时，把同一组 store 放进一段 asm，结尾加 `s_waitcnt expcnt(0)`，否则编译器可能在 store 读完数据之前就复用这些寄存器（P-37b 中 dq 出错，而 dk、dg 正确） | P-37b |
| R33 序言里的发散分支会把读串行化 | 读之后紧跟一个带 `if/else` 的变换（例如 g2_c2a），每次「读加变换」都会被切成独立的基本块，读之间无法重叠（读 → vmcnt(0) → 变换 → 下一次读）。要先把所有读写在前面，变换改用 select 写法，保证位运算完全一样。2 CTA/CU 时被另一个 CTA 掩盖，1 CTA/CU 时完全暴露（s4b 中约占 10%）；生产版修正后也快了 0.7–3%（P-38） | P-37f, P-38 |
| R34 gfx936 每个 wave 最多 256 个 VGPR，没有 AGPR | 降低占用率不会给单个 wave 增加寄存器，只会给每个 CTA 增加 LDS。需要寄存器常驻的融合，在任何占用率下都受 256 的上限约束；融合要靠 LDS（每个 CTA 最多 64 KB）或者改变工作划分 | s4b 重写 |
| R35 并发探针不等于带依赖的流水 | 用互不相关的数据测“两个 kernel 并发能省多少”，会高估流水的收益。带依赖的流水里，关键路径上的 kernel（例如受延迟限制的递推）和吃满整卡的并行 kernel 共用 CU，在 gfx936 上会被拖慢约 2.2 倍，s_setprio 和高优先级队列几乎无效；分段本身还有 launch 和尾部开销（16K/TP8 前向分 4 段多 0.4 ms）。要先测关键路径 kernel 在并发时的耗时 | P-41 |
| R36 字节减少不等于更快：先看瓶颈资源 | 把收尾 kernel 融进 s4b（P-45）虽然省掉了 dg 的显存往返，却慢了 14%（2015 → 2289 µs）。s4b 卡在 VMEM 指令发射（TA，70–73%），不是带宽（55%）；融合后循环里每轮多 5 条 VMEM 指令，收尾段按“16 行 × 64 B”的方式读回（收尾 kernel 自己是一行 512 B 连续读），寄存器从 236 涨到 256 并溢出。估算融合收益前，先确认目标 kernel 的瓶颈资源；对受 TA 限制的 kernel，应按 VMEM 指令数和访问模式估算，而不是按字节 | P-45 |
| R37 融合要看宿主 kernel 有没有余量 | B4b-lite（P-47c）：dq/dk 与原路径逐位一致，访问模式也已改成高效的行连续，仍比 s4b + 收尾慢 9–12%。收尾的逐元素 VALU（每元素约 35 条，含 exp 和除法）是不可省的工作；放进已经受发射和延迟限制的 s4b（每 CU 8 个 wave、VGPR 249–256）里，只会把关键路径拉长约 40%，还丢掉了收尾 kernel 自己的高占用率（每 CU 3 个 CTA）。只有当宿主 kernel 有富余的发射或延迟余量，或者受带宽限制时，融合才划算 | P-47 |
| R38 gfx936 的 occupancy 要实测，不能用编译器的数 | DTK 的 `; Occupancy:` 按每个 lane 256 个 VGPR 计算，VGPR 超过 128 就报 1；但 occupancy_probe 实测，VGPR 为 200–256 时每个 SIMD 仍能同时驻留 3 个 wave。所以“VGPR ≤ 128 才能每 SIMD 驻留 2 个 wave”在 gfx936 上不成立。我们的 kernel 实际受 LDS（64 KB / CU）限制 | occupancy_probe.hip |
| R39 拿掉指令后查循环末尾有没有紧等待 | 编译器会把被拿掉运算的输入融进后面的指令（如每步末尾的 FMA），延长寄存器生命周期。一旦与下一步的预取重叠，编译器就会在循环末尾插寄存器拷贝，并等预取的数据到达（`s_waitcnt vmcnt(N)`），把显存延迟串进每一步。修法：用 asm volatile 的 v_mov 在原位置截断生命周期，访存位置保持原样 | P-52 v1→v3 |
| R40 深度饱和时 VALU 起着控制访存节奏的作用 | 每 CU 有多个 CTA 时，夹在两批访存之间的 VALU 能把访存隔开；拿掉后访存变密、争用加重（窄版 MODE 4 在 192/384 个 CTA 时为 0.93 / 0.83 倍）。所以要按并发度分开测量，必要时保留原实例 | P-52 v4 |
| R41 重新构建会改变显存分配位置 | code object 的大小变化会改变设备内存的分配位置，机器码相同、受带宽限制的 kernel 可能波动 2–8%。判定只看被改动的 kernel，并跑 5 轮以上 | P-52 wu |
| R42 计数高不等于时间代价，先做消融测上限 | dav 平均每条 LDS 指令冲突 4.0 个周期（全场最高），但把冲突最集中的转置写改成完全无冲突（指令条数不变），dav 也只快 0.9–2.4%：冲突被 VMEM 和 HBM 的限制掩盖了。所以任何优化动手前，先用“工作量不变、只去掉被怀疑的开销”的消融测出上限 | dav noConf2 |
| R43 消融必须保持其余工作量不变，用 ISA 核对 | 消融改动的地址或数值，可能让编译器把其他计算判为死代码删掉。例如把 kb0、kb1 写到同一地址，删掉了整条 GEMM2 链（每步 8 个 MMAC），测出“快 11–18%”的假象。每个消融都要用 isa_loop_mix.py 核对 MMAC、访存、舍入等指令数 | r14 fwdh_noconf |
| R44 gfx936 的 MMAC 结果依赖 K 的顺序 | 对两个操作数做同一个 K 置换，25.7% 的输出不逐位一致。所以任何依赖置换 K 的布局技巧（片段按寄存器布局直接生成、省掉转置）都是 B 类 | mmac_kperm_probe |
| R45 VMEM 指令数不等于 TA 开销，访问加宽要按访问模式算 | 体检卡里的“VMEM 指令数是理想值的几倍”（理想值按每条 1 KB 算）会误导：数据从 HBM 来时，TA 开销主要看一条指令覆盖几段行或缓存行，不看指令条数。bwd_tail 的 l2norm 段改成“每 lane 4 列、一条指令覆盖两行”，VMEM 读写从 224 条降到 176 条，shuffle 从 192 条降到 80 条，但 tail 反而慢了 1–2.7%（P-54b）。加宽前要先查 TA 代价表，确认每字节的 TA 周期确实下降 | P-54b |
| R46 往受延迟限制、寄存器满载、多路径特化的 kernel 里加代码，代价会被低估 | P-55（F3a）：s4b 自己算 dAqk，VGPR 不变（236）、逐位一致，但代码从 5177 行涨到 9409 行，主循环从 456 条变成 499 条，s4b 慢 18–25%。评估器按每条指令累加延迟，预测快 9%。往 s4a/s4b 这类宿主加工作的候选，一律先做实测探针，模型结论只作参考 | P-55 |
| R47 访问模式要从代码推出来 | 同样叫 gather，“4 行 × 64 B”约 43 个 TA 周期，“64 行 × 4 B”是 229 个。第 2 步把 s4b 的 aqB/akB 当成后者，高估了 L1/L2/F3a 的收益。打分前要写出每条指令覆盖的行数和每行字节数 | P-55 / 第 2 步 |
| R48 两个递推 kernel 不能靠并发重叠 | C1：fwd_h_bn 与 dhu 在两条 stream 上并发，6 个形态全部变慢 1–26%。TP8 时 48+48 个 CTA 被派到同一批 CU 上，每个都慢约 2 倍；CTA 总数超过 80 个 CU 时，任何派发方式都不可能比串行快。Hopper 版 KDA 反向的双向 scan 设计不能照搬 | C1 |
| R49 改布局要查同时驻留的 CTA 之间的地址间距 | 分块布局的块顺序如果让同时在跑的 CTA 落在同一组 HBM 通道上（partition camping），H 大的形态会慢 10–40%。P-57 v1 按 (i*H+hh) 排块，dav 慢到 0.58、s4a 慢到 0.78；改成 [hh][i] 后恢复。改布局时，除了访问模式，还要检查同时在跑的 CTA 之间的地址间距 | P-57 |
| R50 模拟器给出的收益要先确认在关键路径上 | 如果收益来自不在关键路径上的发射代价（LDS 写、地址运算这类能被其他 wave 掩盖的指令），先用 SQTT 确认这段指令确实落在串行链上，再写探针 | P-59 |
| R51 链式递推每一步的 VMEM 指令数是硬约束 | TP8 的链式递推每步只多 6 条 dword 读，前向递推就慢了 29%（P-61c）。布局重排要放在生产方（改存储地址），不要放在递推 kernel 里改加载 | P-61c |
| R52 写的位置与被等待的读 | 调整全局写的位置时，要同时检查它与后面 `s_waitcnt vmcnt` 所等的预取读谁先谁后。gfx9 的 vmcnt 也计写：写一旦排在被等的读前面，写的延迟就进入了链。这条只适用于受链上时延限制的情形；受 VMEM 发射限制时，效果正好相反 | P-63、P-64B |
| R53 改 lane 映射要钉住浮点运算顺序 | 改 lane 映射时，要把生产版 ISA 中的浮点运算顺序（mul/add/fma 的组合）逐条钉住；否则编译器的打包和融合方式一变，就会破坏逐位一致 | P-72 |
| R54 TA 代价跟着字节走，不跟指令条数走 | 访问已经合并时，把 dwordx2 换成 dwordx4（总字节不变）不会减少 VMEM 发射受阻：4 条 4 B 读和 1 条 16 B 读耗时相同（10.72 对 10.56 µs）。TA 在整个取数过程中都被占着，所以 TA 的忙碌时间里也包含等数据返回的时间。受 TA 限制的 kernel，能动的只有字节数（重复读取、scratch 往返）和 L2 命中率 | P-72、ta_width |
| R55 寄存器数组的下标里有运行时 wave 号，就会被放进 scratch | 寄存器数组的下标里只要混入运行时 wave 号，就会被放进 scratch；即使写成两个分支，也可能被编译器折叠回去。合入前必须检查 `.private_segment_fixed_size == 0` | P-74 |
| R56 用寄存器拷贝做跨步双缓冲，会被 phi 拷贝破坏 | 用寄存器拷贝实现“提前两步”的双缓冲时，phi 消除会把拷贝放到循环末尾，等于在本步结束时就要等刚发出的读。真要提前两步，必须静态地交替使用两组寄存器（循环展开两倍，或按奇偶分支） | P-76 |
| R57 生产方并进多个消费方，会把计算复制多份 | 把一个逐元素的生产方并进多个消费方，会把它的 VALU 复制到每个消费方里。只有每个消费方的 VALU 余量都大于复制进来的工作量时才划算；省下了字节，不等于省下了时间 | P-77 |
| R58 SQTT 的等待点要对到源代码行 | 根据 SQTT 等待点设计探针之前，必须先把等待点对到源代码位置（`map_waits.py`：用带 `-g` 的 ISA，按 `.loc` 匹配），不能只凭“每个 wave 出现几次”去猜。P-84 把 phase 1 的等待误判成了 VNEW，结果收益为 0 | P-84 |
| R59 同一个循环里既读又写，读会被串行化 | 循环里既有 global 读又有 global 写、指针又没有 `__restrict__` 时，编译器不会把下一轮的读提到本轮的写之前，每一轮都要单独付一次访存延迟。解决办法是先单独写一个循环把读全部发出，再进入计算循环 | P-84b |
| R60 grid 顺序是独立的调优维度 | grid 顺序决定哪些 CTA 同时驻留，进而决定 DRAM 和 TLB 的访问局部性。诊断时，比较同一个 kernel 按 head 数折算后的耗时是否随 H 上升。s4a/s4b 改成 head 维变化最快后快了 1.11–1.55 倍，结果逐位一致；同样的改动用在 wu、dav、prep 上却慢了 5–55%，所以必须按 kernel 逐个实测 | P-88、P-89 |
| R61 gfx936 的 LDS-DMA 和其它显存操作共用一个按顺序计数的 vmcnt | `buffer_load_dword{,x2,x4} … lds` 能把数据直接写进 LDS：M0 在指令发出时锁存，offset 同时作用于 LDS 地址和显存地址。但它和寄存器读、显存写共用同一个按顺序计数的 vmcnt，编译器为后面的寄存器读插入的等待，会把前面的 DMA 一起等完。只把部分读改走 DMA，最多只能省下寄存器和 ds_write | P-91 |
| R62 gfx936 上“大 kernel、低占用率”的融合不划算 | 所有读都改走 LDS-DMA、手工管理 vmcnt 的全异步流水，可以做到逐位一致，同样占用率下快 7.5–9%。但每 CU 只放 1 个 CTA 的代价，也只从 +29~39% 降到 +19~30%：每个 SIMD 只有一个 wave 时，LDS 往返、指令依赖和纯发射时间都暴露出来了。要融合，就必须保证每个 SIMD 上至少有 2 个 wave | P-92 |

## 10. 尚未覆盖的部分
- **推广到第二个算子**：阈值和规则目前只用 KDA 的数据标定过，建议下一个用 rmsnorm 或 GEMM 来检验 v3。
- **方案空间的自动估算**：融合或换拆法之后的下限还要手工推导，缺一个 what-if 生成器。
- **在真实模型中采集**：Megatron 中的时间线和 PMC 还没有采集。
- **NV 一侧的串行链延迟**：跨平台的算法必需下限里，NV 每一步的延迟是估计值（0.6 µs），没有实测。
- **发射节奏建模**：R9、R21、R52 目前只是定性规则。
