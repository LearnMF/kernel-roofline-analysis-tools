# HCU 算子优化方法论：操作流程（v2，2026-10-10）

本文写的是“怎么用”。`methodology.md` 写的是“每个数怎么量”，`design.md` 写的是工具结构。本文的规则来自 KDA 上 12 个预先登记的实验（P-0 到 P-12）以及 L16，每一条规则都注明了来源。

## 0. 每轮要回答的三个问题

每一轮（无论有没有改代码）都必须产出一份**上限评估**（模板见 `results/kda-gfx936-20261010-ceiling/README.md`），回答：

1. **这是什么类型的算子 / kernel？** 按 A/B/C/D 分类，并且要说清楚**受哪一种资源限制**。
2. **离上限还有多远？** 要分清是离哪一个上限：物理下限、现有拆法的下限，还是现有指令流的下限。
3. **下一步该做什么？** 是局部调优、减少工作量，还是重构？方向必须由最大的那一层决定，而不是看哪个改起来方便。

只汇报加速比，不算完成这一轮。

## 1. 上限要从哪些角度说明

**一个 kernel 是否到顶，要逐项看下表中每一种资源**，取占用最高的那一项作为主要受限因素。只看带宽和算力两项，会漏掉真正的瓶颈：KDA 的递推 kernel 在 HBM 30%、计算 30% 的情况下，被向量访存发射卡在了 86–88%。

| 角度 | 指标（按正在工作的 CU 计算） | 标定后的饱和值 | 来源 |
|---|---|---|---|
| HBM 带宽 | 实测字节 / 可达带宽（按 grid 大小修正） | 1338 GB/s（理论值的 72.6%） | L0 `hbm_*`、`hbm_read_vs_ctas` |
| 计算流水线 | `SQ_ACTIVE_INST_VALU` / (周期 × CU 数) | 0.97–1.00 | L0 `pmccal` |
| MMAC | (ACTIVE − INSTS) × 8192 / 峰值 | 476 TFLOPS（bf16） | L0 `mmac_*` |
| **向量访存发射（TA）** | `Σ TA_TA_BUSY` / (GRBM × CU 数) | **0.92** | L0 `vmem_issue` 加 PMC（模型 v2 新增） |
| 存储的发射成本 | 每条指令覆盖的字节范围，约每 512 B 27 周期 | — | L0 `vmem_store` |
| LDS | 冲突率，以及 `SQ_WAIT_INST_LDS` 所占比例（判断冲突是否在关键路径上） | — | P-1 |
| 依赖链 | 递推的 T_cp_impl / 实测时间 | — | op_spec 中的 `serial` 字段 |
| 并行度 | 正在工作的 CU / 总 CU 数 | — | grid 大小 |
| 系统层 | 空泡占比、launch 开销 | 每次 launch 约 2 µs | L1 timeline |

**判定规则**（`kra/model/bounds.py`）：
- 某项资源 ≥ 80%：该资源已饱和，只能**减少落在它上面的工作量**（字节数、指令数、改成更宽的访存），而不是去改延迟；
- 某项资源在 60–80%：受吞吐限制，可以减少工作量，或者提高这项资源的效率；
- 所有资源都低于 60%：受延迟限制，用 L3 的 `pcmap` 找暴露的等待点；
- 如果实测已经接近实现下限（同样的工作量按可达速率运行所需的时间），说明这份指令流已经到头了，只能减少工作量或者重构。

## 2. 局部还是全局：把算子时间分成四层

| 层 | 定义 | 怎样减少 |
|---|---|---|
| 物理下限 | 只算跨阶段的张量，加上只由依赖决定的关键链，与怎样拆 kernel 无关 | 无法减少，由硬件决定 |
| 拆分代价 | 现有拆法的下限，减去物理下限 | 重构：融合、减少中间结果在 HBM 上的往返、增加并行度 |
| 多余工作 | 实现下限，减去现有拆法的下限 | launcher 内部：改布局、去冗余、合并访存 |
| 执行效率损失 | 实测，减去实现下限 | 局部调优：等待、调度、占用率 |

**“是不是在局部最优上打转”的判断规则**：
1. 每轮都按四层分解，看哪一层最大，以及它是怎么变化的。如果优化的那一层在缩小，另一层同时在变大（例如 L16 之后多余工作 −620 µs，执行效率损失 +306 µs），说明瓶颈在转移，这是正常的。
2. 如果某一层占比最大，而最近几轮都没有针对它的手段，说明我们在局部打转。KDA 目前的拆分代价一直是 35%，从来没有动过，尤其是反向：现有拆法的下限是物理下限的 7.7 倍。
3. 结构性方案（融合、两级递推、换拆法）要**先用 op_spec 估算新方案的下限**，和当前的四层对比，再决定是否投入。这类方案需要人来拍板，要说清楚预期收益和代价。
4. 对照外部实现，例如 FLA、cuDNN PR #556 的参考实现，防止“自己和自己比”：目前 G2 比 FLA 快约 1.7 倍，其中约 0.8 ms 来自系统层的空泡（见 P0）。

## 3. 一轮实验的流程

```
上限评估（四层 + 每个 launcher 的判定）
  → 选目标：按可回收时间排序，选主要受限因素对得上的方法
  → L3 逐指令分析（pcmap：关键 wave、按源码行的停顿）+ 静态规则（ISA scan）
  → 先登记预测：机制、指标会怎样变化、时间范围、证伪条件（提交之后才能改代码）
  → 风险大的改动先做原型 bench（L16：用随机数据只测时间）
  → 实现 → ISA 检查（指令数、VGPR、scratch）
  → 逐位门禁（9 组 dense + 4 组 varlen）+ 树内测试
  → A/B：每侧 6 个进程，普通和 keep-state 两种形式，两种形态
  → 对照预测：保留或回退；把结论写成规则
  → 合入：备份 → 安装同一份二进制 → 与备份逐位对比 → flash-train 移植与验证 → 推送
  → 重新做上限评估
```

**测量口径**：
- 独立样本是**进程**，不是窗口。缓冲区的物理位置会让同一 kernel 的时间变化 1–2.5%（P-4）；
- 收益小于进程间波动的结果，一律视为不显著；
- 普通形态和 Megatron 的 keep-state 形态要分别测：两者经过的 kernel 和参数组合不同（P-8）。

## 4. 规则库（每条都来自实验）

| 规则 | 内容 | 来源 |
|---|---|---|
| R1 关键性 | D 层病因必须附带它在关键路径上的证据，例如 LDS 冲突要看 LDS 等待占比 | P-1 |
| R2 数学函数展开 | exp2 的非规格化保护是一条依赖链；吞吐受限时，去掉它的收益可能超过指令减少的比例 | P-2 |
| R3 到顶判断 | 对已到顶的 kernel 做常规优化，不应该有收益（这也是对照组） | P-0 |
| R4 hot loop 中的暴露等待 | 可操作的信号是循环内读完不久就等待的位置（`load_use_slack`）；序言里的暴露会被同一 CU 上的其他 CTA 掩盖 | P-3、P-5、P-6 |
| R5 发射与延迟 | 已经预取过的读，减少它们的发射数量没有用；要先确认受限的是发射吞吐（TA 利用率）还是延迟 | P-4、P-7 |
| R6 向量访存发射 | 每条读按宽度计成本，`dwordx2` 16 周期，`dwordx4` 18–23 周期；TA 利用率 ≥ 80% 时，改成 16 B 读是最直接的手段 | L16 |
| R7 存储定价 | 存储成本正比于每条指令覆盖的字节范围；改布局时读写两端都要算账 | P-8、P-12 |
| R8 保守的 waitcnt | hot loop 里位于运行时可选分支中的访存，会让编译器多等；改成编译期确定可以消除，但要逐个实例实测 | P-9、P-10 |
| R9 发射节奏 | 去掉一个等待之后，读可能扎堆，原本被掩盖的发射停顿又会出现；发射节奏本身也是一种资源。解决办法是在每组读之后加调度屏障（`sched_barrier`），保持源码中的间隔：模式 1 因此从慢 4% 变成快 6% | P-9 模式 1、P-10 v8b4、P-11 |
| R10 原型先行 | 跨多个 kernel 的改动，先用随机数据的原型 bench 验证收益，再投入完整实现 | L16 |
| R11 交换的代价 | 用 lane 交换换取更宽的访存时，要把交换指令（LDS/DPP 与额外的依赖）算进预测 | P-12 |

## 6. 尚未覆盖的部分

- **方案空间的自动估算**：现在要手工写一份新的 op_spec，才能估出融合或换拆法后的下限，还缺一个 what-if 生成器；
- **工具的推广**：第二个算子（建议 rmsnorm 或 GEMM）还没验证，阈值目前只用 KDA 的数据标定过；
- **在真实模型里的采集**：Megatron 中的时间线和 PMC 还没有采集；
- **发射节奏建模**：R9 只是定性规则，还没有量化模型。
