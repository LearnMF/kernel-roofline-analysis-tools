# KDA 问答：为什么达不到理论计算强度，同一条因果链在三张卡上有什么不同（2026-10-18）

> 本文是 `playbook.md`（v3）第 1.4 节和第 7 节的补充说明，以问答形式记录两个关键问题的分析。
> 数据口径：16K 序列、TP8（H=12）、一次前向+反向；我们的版本是 P-88 生产版，FLA 是 0.5.2 默认配置。数据来源列在文末。

---

## 问题 1

> `playbook.md` 第 1.4 节里，KDA 算法本身的计算强度是 122 FLOP/B，而实际上我们只有 21 FLOP/B、FLA 只有 13 FLOP/B。
> 122 FLOP/B 是 KDA 的理论计算强度吗？为什么我们和 FLA 都达不到？是什么限制造成的，是延迟还是别的原因？

## 回答 1

对，122 FLOP/B 是 KDA 的理论计算强度。我们和 FLA 都达不到，**直接原因不是延迟，而是读写的字节变多了**：
- 计算强度 = 运算量 ÷ 读写字节。运算量由算法决定，是固定的；字节一多，强度就下降。
- 字节之所以变多，是因为算子必须拆成多个 kernel，中间结果要经显存交接。**根本限制是片上容量。**
- 延迟是间接起作用的：它让“融合以减少字节”这条路走不通。

### 1.1 122 FLOP/B 是怎么来的
| 项 | 每个 token·head | 16K/TP8 合计（196,608 个 token·head） |
|---|---:|---:|
| 算法必需的矩阵乘运算量 | 504 kFLOP | 99.1 GFLOP |
| 算法必需的读写字节 | 4124 B | 0.811 GB |
| 理论计算强度 | | 99.1 ÷ 0.811 = **122 FLOP/B** |

- **“算法必需的字节”的含义**：假设整个前向+反向是一个完全融合的计算，每个输入只读一次，每个输出只写一次，再加上前向留给反向的状态，中间结果一律不落显存。所以 122 是只有完全融合时才能达到的计算强度。
- **口径**：这个数按“反向重新计算状态”的显存策略（kda_bound 的 P1）计算。如果改成前向直接保存 h（我们现在的做法），必需字节会略多、运算量会略少，计算强度略低，但仍是同一个量级。

### 1.2 为什么实际只有 21 和 13
运算量不变，读写字节变大了：

| | 实际读写 | 是必需量的几倍 | 计算强度 |
|---|---:|---:|---:|
| 算法必需 | 0.811 GB | 1 | 122 |
| 我们 | 4.722 GB | 5.82 | 122 ÷ 5.82 ≈ **21** |
| FLA | 7.423 GB | 9.15 | 122 ÷ 9.15 ≈ **13** |

多出来的字节几乎都花在 kernel 之间的交接上。我们的 5.82 倍里：
- 5.08 倍是接口字节，也就是每个 kernel 读写自己输入输出所必需的那部分；
- 剩下约 1.15 倍是 kernel 内部的多余读写。

交接的大头如下（16K/TP8；按 P-65 的逐张量账目，结合 P-88 的结构估算）：

| 交接 | 大小 | 为什么必须落显存 |
|---|---:|---|
| s4 交给 tail 的 dq/dk/dg（fp32） | 604 MB | tail 里的 l2norm 反向需要整行 128 维；dg 的反向累加要跨 chunk |
| 同一份 W/K 在不同 kernel 里要不同的布局 | 约 500 MB 以上 | 前向递推、反向递推、s4 对布局的要求各不相同 |
| 状态 h/dh 被多个 kernel 重复读写 | 约 500 MB | 每个 chunk 的状态是 32 KB，wu、s4a、s4b、dhu 各读或写一次 |
| s4a 交给 s4b、prep_a 交给 prep_b 的中间结果 | 约 300 MB + 265 MB | 合成一个 kernel 就放不下 |
| fp32 的门控 g | 302 MB | 有多个消费方，而且出于精度考虑必须用 fp32 |

FLA 只有 13 的原因：
- 拆得更碎，约 22 个 kernel；
- 默认在反向里重新计算前向的 w/u 和 h；
- 中间结果也更多。

### 1.3 真正的限制：一条因果链
| 环节 | 限制 | 证据 |
|---|---|---|
| ① 片上放不下 | 反向时每个 chunk·head 要同时用到约 180–200 KB 数据；gfx936 每个 CU 只有 64 KB 共享内存，每个 wave 最多 256 个寄存器 | 容量测算（P-78 的设计） |
| ② 只能拆 kernel | 放不下的中间结果只能写进显存再读回来，于是字节变多，计算强度下降 | 接口字节是必需量的 5.08 倍 |
| ③ 硬要融合，就得降低占用率 | 每个 CU 只放 1 个大 CTA，工作集才塞得进 64 KB | — |
| ④ 占用率一降，延迟就暴露（**延迟在这里起作用**） | 每个 SIMD 只剩一个 wave，访存、共享内存往返、指令依赖的延迟都没有别的 wave 来掩盖 | s4b 慢 39%；改成全异步流水后仍慢 19–30%（P-92） |
| ⑤ 并行结构不同 | 串行递推只有 H × V 分片个 CTA（TP8 下 48 个），按 chunk 并行的部分则有几千个 CTA，两者很难放进同一个 kernel | 递推和并行任务并发时，并行部分只剩 0.45–0.47 的速度（F9） |

所以：
- **延迟不直接降低计算强度**。它影响的是带宽利用率，也就是同样多的字节要花多久才能搬完。
- **延迟间接起作用**：在 gfx936 上，想通过融合减少字节，就必须降低占用率；占用率一低，延迟掩盖不住，融合反而更慢。这就是我们降不下字节、提不高计算强度的原因。

FLA 在 NV 上片上内存更大（164–228 KB），还有不占 vmcnt 的异步拷贝，按理更有条件融合，但同样没有做到。原因是训练反向的工作集太大，而且“串行递推 + 按 chunk 并行”的混合结构对哪个平台都不友好。公开实现中，唯一接近完全融合的训练反向是 NVlabs 在 B200 上的 megakernel，它依赖 228 KB 共享内存加 256 KB 张量内存。

### 1.4 就算做到 122，结论也不变
- **BW1000**：122 仍远低于平衡点 355。即使完全融合，KDA 依然受访存限制，矩阵乘利用率最多约 32%。所以在 BW1000 上，KDA 永远不会变成受算力限制的算子，优化目标始终是少读写字节、把带宽用足。
- **H20**：122 高于它的平衡点 36。如果真能完全融合，KDA 在 H20 上会变成受算力限制，这也是为什么 H20 的理论下限（0.72 ms）由算力决定，反而是三张卡里最慢的。但现实中所有实现都停在 13–21 FLOP/B，比的是字节和带宽，H20 的带宽优势就显现出来了。

## 问题 2

> 上面这条因果链在 gfx936、A800、H20 上分别有什么不同的特点？是不是这些不同导致了各卡上的性能差异？

## 回答 2

三张卡是同一条因果链，但每一环“卡得多紧”不一样：
- gfx936 在 **①容量** 和 **④低占用率下掩盖延迟** 这两环上卡得最死；A800 和 H20 在这两环上都比较松。
- 所以在 gfx936 上，字节降不下来，而每个字节的代价又最高（带宽最低）。
- 在两张 NV 卡上，FLA 的字节虽然多，但 H20 带宽高，搬得快。

### 2.1 逐环对比
| 环节 | gfx936（我们） | A800（FLA） | H20（FLA） |
|---|---|---|---|
| **① 片上容量**：每 CU/SM 的共享内存 / 寄存器 / L2 | 64 KB / 512 KB / 8 MB | 164 KB / 256 KB / 40 MB | 228 KB / 256 KB / 60 MB |
| 对比反向每个 chunk·head 约 180–200 KB 的工作集 | **差约 3 倍，放不下** | 差约 1.2 倍，大部分放得下 | 每 SM 放 1 个 CTA 时基本放得下 |
| **② 拆分程度**：kernel 数，读写字节 / 必需 | 12 个，**5.8 倍** | 约 22 个，9.2 倍 | 同 A800（同一软件），9.2 倍¹ |
| 每多交接 1 GB 的时间代价（1 ÷ 峰值带宽） | **0.75 ms** | 0.56 ms | **0.26 ms** |
| **③ 低占用率是不是常态** | 不是：我们的 kernel 每 CU 放 2–3 个 CTA，降到 1 个就变慢 | 是：FLA 的主力 kernel 占用率 6–12.5%，每个 CTA 用 40–124 KB 共享内存² | 同 A800 |
| **④ 低占用率下靠什么掩盖延迟** | **没有独立的异步拷贝**：LDS-DMA 和其他访存共用一个按顺序计数的 vmcnt（R61）。每 CU 1 个 CTA 时 s4b 慢 39%，改成全异步流水后仍慢 19–30%（R62） | cp.async 分组等待，加上 Triton 的多级软件流水 | TMA + mbarrier + cp.async，异步能力最强 |
| 访存延迟（实测，指针追逐） | 显存 325 ns，L2 140–160 ns | 显存 270 ns，L2 150 ns | 未测 |
| **⑤ 递推的并行度**（TP8 下 48 个 CTA） | 48 / 80 CU = 60% | 48 / 108 SM = 44% | 48 / 78 SM = 62% |
| 矩阵乘峰值（决定计算密集阶段） | **476 TFLOPS** | 276 TFLOPS | **138 TFLOPS** |
| 显存带宽峰值（决定流式阶段） | 1.34 TB/s | 1.77 TB/s | **3.82 TB/s** |

¹ H20 上 FLA 的字节数沿用 A800 上用 ncu 实测的值。H20 的 L2 有 60 MB，可能接住一部分交接，实际字节或许略少。
² 来自 A800 上的 ncu 统计：`wy_dqkg_fused` 每个 CTA 40 KB、每 SM 1 个 CTA；dhu 每个 CTA 124 KB，占用率 6.25%；前向 h 每个 CTA 120 KB。

### 2.2 最终体现在各阶段的耗时（16K/TP8，µs）
| 阶段 | 主要卡在哪一环 | 我们 | FLA@A800 | FLA@H20 | 谁占优，原因 |
|---|---|---:|---:|---:|---|
| 流式阶段（前向准备、反向重算、dAv、收尾） | ②：字节 × 带宽 | 2761 | 2536 | 1708 | **H20**：每字节的代价最低（3.82 TB/s），收尾达到 3.29 TB/s，即峰值的 86% |
| 计算密集阶段（wy+intra） | 矩阵乘与发射 | **1604** | 3350 | 2324 | **我们**：算力 476 TFLOPS，字节也只有 FLA 的一半。H20 算力只有 138 TFLOPS，从 A800 换到 H20 只快了 1.44 倍 |
| 串行递推（前向 h+o、dhu） | ⑤，加上延迟 | 1230 | 1277 | 1020 | 基本持平：都受延迟限制，带宽差距发挥不出来 |
| **合计**（含拷贝、填充等其他 kernel） | | **5614** | 7378 | 5160 | |

### 2.3 每张卡分别卡在哪一环
**gfx936（我们）：① 和 ④ 都卡死，② 的代价最高**
- 工作集放不下（①），只能拆分（②）。想融合就得降低占用率（③），而又没有独立的异步拷贝，占用率一降延迟就暴露（④）。所以融合这条路是负收益：试了 13 次，0 次成功。
- 在这些限制下，我们把字节压到了必需量的 5.8 倍，比 FLA 少 36%；带宽利用率 63%，三家中最高。
- 但每个字节的代价是 H20 的 2.85 倍。流式阶段我们只有 H20 速度的 0.31–0.87：收尾 0.40、dAv 0.31、前向准备 0.63、反向重算 0.87。
- 476 TFLOPS 的算力只在计算密集阶段派上了用场，这一段我们三家最快。

**A800（FLA）：硬件约束松，输在软件拆分和中等带宽**
- 共享内存够大、有异步拷贝，FLA 可以在低占用率下跑大 kernel，也确实把 wy 和 dqkg 融合成了一个 kernel。
- 但整体仍拆成约 22 个 kernel，还在反向里重算前向，字节是必需量的 9.2 倍。
- 带宽 1.77 TB/s 只比我们高 1.32 倍，抵不过我们 1.57 倍的字节优势；算力 276 TFLOPS 也不如我们。所以 A800 两头都不占优，我们快 1.31 倍。

**H20（FLA）：硬件约束最松、带宽最高，但算力被削**
- 同一套 FLA，字节仍是 9.2 倍，但 3.82 TB/s 的带宽让这些字节搬得最快，流式阶段远快于我们。
- 算力只有 138 TFLOPS：计算密集阶段比我们慢，带宽利用率也被拉低到 38%。
- 两相抵消后，带宽带来的收益大于算力带来的损失，所以 H20 比我们快：我们的速度是它的 0.92。

### 2.4 由此得到的判断
- **在 gfx936 上，这条链已经卡到硬限制**：①容量和④延迟掩盖都由硬件决定，我们的实现已经贴着这条链的边界在走。
- **在 NV 上，这条链远没有卡死，FLA 也没有用尽它的空间**：共享内存和异步拷贝都允许更深的融合。公开实现中，NVlabs 在 B200 上已经做出了接近完全融合的训练反向。
- **所以 H20 还有余量**：如果有人在 H20 上写出融合程度更高的实现，H20 还会更快，和我们的差距可能拉大。但它的余量也有上限：完全融合后计算强度约 122 FLOP/B，高于 H20 的平衡点 36，那时 H20 会转为受算力限制，理论下限约 0.72 ms。
