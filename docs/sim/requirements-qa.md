# 需求澄清：这个工具到底输入什么、能做到什么

## Q1 输入算子是 FLA 源码？配置文件？还是只要 shape？

会上三方的说法并不矛盾，拼起来就是**分级输入**，取决于你想要哪一层的答案。按 13 章第 6 章的四个下限正好对应四级输入：

| 层级 | 输出哪条线 | 需要的输入 | 谁来填 |
|---|---|---|---|
| L0 算法层 | `T_theory`（理论下限：算法必需的 FLOPs + 必需搬运的字节 + 不可消除的串行链） | 算子类型 + shape/dtype（`B,H,T,D,chunk`…）+ 该算子类型的**公式模板** | 使用者填 shape；公式模板由工具内置（算子库） |
| L1 切分层 | `T_split`（按当前/假设的 kernel 切分，加上 kernel 间经显存交接的流量） | 再加「切几个 kernel、每个 kernel 的接口张量」或由工具按 LDS/L2 容量**自动推导切分** | 工具推导为主，使用者可覆盖 |
| L2 实现层 | `T_full`（按真实指令流/各资源工作量，假设资源满载） | 需要真实实现：每 kernel 的 VALU/MFMA/TA/LDS 指令条数或可由 tile 配置推算的工作量 | 来自编译产物或 capture，**不是第一版必需** |
| L3 实测层 | `T_meas` + 三项开销（交接/冗余/空等） | 真机 profiling | 可选，用于校准模型 |

**结论：第一版（会上说的「仿真工具」）只做 L0 + L1，输入就是一个结构化算子描述（JSON/YAML/CLI 参数），不读 FLA 源码、不做指令级 replay。**文进辉已经明确否定了指令级 replay（「这事暂时干不了」），余果也明确「忽略细节估计上限」。

你会上那句「它总得有个公式吧」是对的，而且这是第一版最核心的工程量：**公式必须内置在工具里，按算子类型做一个算子库（operator zoo）**。使用者不提供公式，使用者只提供 shape/dtype 和算子名字；工具查表拿到该算子的：
- FLOPs 公式（前向 / 反向分别写）；
- 必需 HBM 字节公式（输入必须读 + 输出必须写，按 dtype）；
- 片上工作集公式（决定能否放进 LDS/L2，从而决定要不要拆 kernel）；
- 串行依赖结构（如 KDA/线性注意力的 chunk 递推步数 `NT = T/chunk`，这是传统 roofline 完全缺失的一维）。

所以工具的真实形态是：**「算子公式库 + 机器参数库 + 四层下限求解器」**，不是通用的「任意算子自动分析器」。新算子接入的成本 = 写一份该算子的公式插件（几十行），这点必须在专项会上讲清楚，否则对方会以为随便丢个 kernel 进去就能出数。

**前反向**：由算子插件分别声明 `fwd` / `bwd` 两组（或多组）group，各自有自己的 FLOPs、接口字节和递推结构。现有 `examples/kda/op_spec.json` 已经是这个结构（`groups[].phase = fwd/bwd`），可以直接沿用 `kra.opspec/1` schema，只是把「实测/capture 填的字段」改成「公式算出来的字段」。

## Q2 文档是实践总结出来的，现在工具要直接预估，这不矛盾吗？

不矛盾，但要讲清楚两者的区别，这是专项会要对齐的第一件事：

- 13 章方法论是**事后归因**：有了实测，用四个下限把 gap 拆成三项开销，告诉你该往哪个方向优化、还剩多少空间。
- 这个工具是**事前预测**：只给 shape + 硬件理论参数，输出 `T_theory`、`T_split` 和瓶颈类型，告诉你「这个算子在这台机器上值得追到什么量级」。
- 两者是同一个模型的两种用法：**预测模式**用公式填下限，**归因模式**用 capture/profiling 填下限。同一套 `bounds` 代码可以同时服务，这也是为什么应该直接在 `kernel-roofline-analysis-tools` 里加一个 `predict` 子命令，而不是另起一个工具。

必须明确写进文档的免责声明（你会上的担忧是对的，要落在纸面上）：
- 工具给的是**上限（lower bound of time）**，不是「优化后一定能达到的性能」；
- `T_meas / T_theory` 不能当成可优化空间，中间的 `O_handoff`（拆分交接）很大一部分是**约束决定的、不可回收**；
- 对单点改动收益 < 5% 的判断，模型不可信，必须实测（13 章第 6 章已有这条结论）。

## Q3 误差能给到多少？

会上钱永军拿硅前 EMU 的 5% 做对标，这个指标**不适用**于本工具，必须在专项会上重新定锚：
- EMU 是指令级 cycle 仿真，拿得到每条指令的周期数；我们拿不到（余果也承认）。
- 现有文档里的经验值：用构造式模型估算**现有 kernel 的绝对时间**误差约 ±20%~±30%；**排序/否决明显负收益方案**较可靠。
- 业界公开的解析模型（TileSight 报 pooled MAPE ≈12%，tile 级仿真 GPU-Tile-Sim 报 1.2%~8.7%）都需要 tile 级实现信息，属于上表的 L2 层，不是只给 shape 就能达到的精度。

建议对外承诺的口径（分指标分级）：
| 指标 | 期望精度 | 验证方式 |
|---|---|---|
| 瓶颈类型（访存/算力/其他资源受限） | 定性，期望准确 | KDA、PV、一个纯访存算子、一个纯 GEMM 四类回归 |
| `T_theory` / 理论 MFU 上限 | 量级正确，不承诺百分比 | 与已优化到位的算子实测对比 |
| 同一算子不同配置的**相对排序** | 期望可靠 | 扫 shape 对比实测曲线 |
| 绝对时间预测 | ±20%~30%，仅 L2 层有实现信息时 | KDA 已有四层数据回归 |

文进辉给的验证方法其实更可操作，应该写进计划：**按模型指导优化一两周，如果再也找不到方向，说明模型的上限是准的**；多跑几个算子就能把模型压实。

## Q4 和 hcu-train-simulator 是一回事吗？

不是。见 `03_industry_survey.md`，一句话：它的输入是**模型 config + 并行策略**，粒度是「把每个 GEMM 当成 `2MNK / (峰值 × 分档效率)`」，算子内部的切分、片上容量、串行依赖、TA/LDS 发射全部不建模；我们要做的恰好是它那个「分档效率系数」的下一层。两者是**上下游**：我们产出算子级 perf model，接到余辉的端到端模型里（余果会上明确要求了这件事）。
