# 专项会材料：算子 Roofline 预测工具（kra predict）

> 对齐对象：文进辉、余果、钱永军、余晖、邵博
> 一句话：**给定硬件参数 + 算子 shape，事前给出「这个算子在这台机器上值得追到什么量级、卡在哪种资源」，不需要上机。**

---

## 1. 工具定位（一页纸）

```
       算子名 + shape/dtype            机器参数文件(手册值/实测标定)
              │                                  │
              ▼                                  ▼
     ┌─────────────────┐              ┌────────────────────┐
     │ 算子语义库       │              │ 硬件资源求解器      │
     │ (每类算子一插件) │  ──────────▶ │ (算子无关, 通用)    │
     │ FLOPs/必需字节/  │              │ 各级屋顶/容量约束   │
     │ 工作集/串行结构  │              │ tiling/依赖链/固定  │
     └─────────────────┘              │ 开销/四层下限       │
                                      └────────────────────┘
                                                 │
                                                 ▼
           计算强度 · 瓶颈类型 · binding resource · T_theory / T_split
                      · 可达 MFU 上限 · 优化方向 · 置信度
```

**做**：事前预测上限、瓶颈定性、同算子跨 shape 排序、跨硬件对比（硬件设计 what-if）。
**不做**：不读 FLA/Triton/HIP 源码自动提取语义；不做指令级 cycle 仿真（文进辉已否）；不承诺 5% 误差；不把 `T_meas/T_theory` 当作可优化空间展示。

## 2. 与现有东西的分工（最容易误解的一点）

| | 输入 | 粒度 | 性质 |
|---|---|---|---|
| **13 章方法论** | 实测 profiling | 单算子 | **事后归因**：把 gap 拆成交接/冗余/空等三项开销 |
| **本工具 kra predict** | shape + 硬件参数 | 单算子 | **事前预测**：同一套 bounds 代码，用公式代替实测填下限 |
| **余晖 端到端仿真** (hcu-train-simulator) | 模型 config + 并行策略 | 整网/整训练 | 显存与吞吐估算，算子被压成一个数 |
| **SOC 硅前仿真** (C-model/EMU) | 算子参数表 | 单算子 | 高精度但重，需要源码/指令流，周期长 |

**与余晖的关系是上下游，不是竞争**：他的端到端模型里每个 GEMM/注意力目前是 `2MNK / (峰值 × 分档效率系数)` 这样一个数；我们产出的就是那个数的下一层依据。接口形态建议：我们按算子输出 `{T_theory, T_split, 瓶颈类型, MFU上限}` 的 JSON，他按需调用或离线查表。**这件事余果会上明确要求过。**

## 3. 「那个系数」到底是什么（会上反复提到）

指 hcu-train-simulator 里的**分档效率系数**，是一张按规模查的经验折扣表（源：`docs/tiered_efficiency.md`，开关 `use_tiered_gemm_efficiency` / `use_tiered_communication_efficiency`，默认开）：

GEMM —— 按 `m,n,k` 的**最小维度**分档，有效效率 = `gemm_efficiency × shape 系数`：

| 最小维度 | shape 系数 |
| ---: | ---: |
| ≤ 512 | 0.15 |
| 513–1024 | 0.40 |
| 1025–2048 | 0.75 |
| > 2048 | 1.00 |

通信 —— 按每条 flow 的字节数分档，有效带宽 = `配置带宽 × 通信效率 × 消息大小系数`：

| 每条 flow 大小 | 系数 |
| ---: | ---: |
| ≤ 64 KiB | 0.02 |
| 64 KiB–1 MiB | 0.15 |
| 1–16 MiB | 0.55 |
| 16–64 MiB | 0.85 |
| > 64 MiB | 1.00 |

所以**它确实就是「算子性能折扣比」**：承认小 shape 跑不到峰值，于是直接乘一个 0.15/0.40/0.75 下去。该文档自述系数是按 BW1000/BW1100 的 BF16 GEMM profile「分档中位性能相对大维度平台期**近似取整**」得到的，且「不接受自定义分层系数」、有实测 profile 时直接用实测。

**问题在哪**：
1. 系数是**从 BW1000/BW1100 实测反推**出来的，换新硬件（S4000/S2000/S2200）就失效，而硬件设计探索恰恰要换硬件；
2. 只按**最小维度**一维分档，同一档里访存型和算力型混在一起，不区分瓶颈；
3. **只给折扣，不给原因**，无法回答「为什么只有 0.4、怎么提」；
4. 跨档跳变（0.40 → 0.75）不连续，边界 shape 不可信。

**我们的替代方案**：不乘经验系数，而是按「必需字节 / 必需 FLOPs / 片上容量 / 串行链 / 固定开销」解出该 shape 的上限，**系数变成推导结果而不是输入**。这正是钱永军吐槽「直接乘系数不准」的那个点，也是本工具最直接的价值交付：拿 S2200 做 demo —— 现在的做法是 `S2200 = 83% × S2000` 一刀切线性折算，而算力与带宽未必同比例下降，我们能分资源折算。

## 4. 这是一个「需要先验算子知识」的工具

必须讲明，否则会被期待成「丢任何 kernel 进去都出数」：

- 工具必须内置每类算子的 **① 必需 FLOPs ② 必需 HBM 字节 ③ 片上工作集 + 串行结构**，这三项无法从 shape 猜出；③ 正是传统 roofline 对 KDA 这类 chunk 递推算子失效的原因。
- 工程量：**通用求解层 ~80%（与算子无关，一次写好）+ 算子语义层 ~20%（一类算子一份，不可省）**。
- 先验的三种获取方式：**手写插件**（递推类算子只能这样，几十行）→ **家族模板**（GEMM/FlashAttention/elementwise/reduce/MoE 各一个模板，覆盖率主力）→ **PyTorch meta/FakeTensor 自动抽取**（M2 之后；可接受一段 torch 前向代码，只做 meta 推导拿 op 序列与 shape，不解析指令流；能自动得 FLOPs/字节，但拿不到串行与拆分结构）。
- 边界：**没有插件的算子直接报「不支持」，不做猜测性外推。**

## 5. 误差口径（不接受 5% 的对标）

EMU 的 5% 前提是拿得到每条指令的周期数，我们拿不到。公开可引用的锚点（`Vr978/LLM-Inference-Performance`，T4，78 个 held-out kernel shape）：

```
纯手册 roofline 43.8% → 加结构项 24.0% → 一次校准 12.9% → 二次校准 9.2%
```

即：**不做指令仿真、只用手册值做 roofline，kernel 级误差就是 40% 量级；加结构项并用微基准校准才能进 10%。** 建议分级承诺：

| 指标 | 期望 | 验证方式 |
|---|---|---|
| 瓶颈类型（访存/算力/其他资源） | 定性准确 | KDA、PV、纯访存算子、大 GEMM 四类回归 |
| `T_theory` / 理论 MFU 上限 | 量级正确，不报百分比 | 与已优化到位的算子实测对比 |
| 同算子不同 shape 的相对排序 | 可靠 | 扫 shape 比实测曲线 |
| 绝对时间 | ±20%~30%，且仅在有实现信息（L2）时 | KDA 已有四层数据回归 |

文进辉给的验证法更可操作，建议写进计划：**按模型指导优化一两周，如果再也找不到方向，说明上限是准的。**

## 6. 验证集

1. **KDA 16K/TP8**（已有四层实测）：`T_theory 0.83ms / T_split 3.35ms / T_full 4.41ms / T_meas 5.32ms`，作为固定回归用例；
2. **SOC PV 仿真表**（S4000/S2000 的 GEMM/DSA/MoE latency，曹媛媛 10-23）：16 行 GEMM 横跨 `OI = 1 → 2891`，天然覆盖「一个偏访存、一个偏计算」。注意**是仿真值不是 BW1000 实测**，只能换上对应机器参数后验证「上限能否框住 + 分区与趋势是否对」；
3. 一个纯访存算子（RMSNorm/elementwise）+ 一个大 GEMM。

从 PV 表反推出的可用数据：S4000 fp8 GEMM **2130–2316 TFLOPS** / S2000 **978–1017 TFLOPS**（算力比 2.28×）；带宽侧 S4000 **3.88–4.00 TB/s** / S2000 **2.34–2.41 TB/s**（1.66×）；两款芯片小 shape 都压在 **约 18–20us 固定地板**（印证模型必须带 `T_launch` 固定开销项）。推论：S4000 ridge point 右移约 1.4×，不少在 S2000 上算力受限的算子到 S4000 会变访存受限 —— 这就是余果要的「指导硬件设计」的典型输出。
