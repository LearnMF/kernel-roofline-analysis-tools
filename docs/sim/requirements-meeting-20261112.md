**余果（定调模型粒度）**
- 「给你个硬件参数：**算力、访存，还有 L2，类似这些一大堆硬件参数**，然后再给你个算子，你来评估一下这个算子在这硬件上的上限。」

- 「你可能还可以加一些 **LDS 大小、L2 cache** 这些影响……这要比传统 roofline 更细，因为我看你的优化方法论里提到过这些，但不一定在你这个仿真模型里能体现。」
- 「硬件那边比咱们强的是：**一条指令需要几个时钟周期他们很清楚**，能做指令级、流水线级仿真。咱拿不到这个信息，所以**不会特别准，但该有的东西得有**。」
- 「这个工具一方面评估算子上限，一方面**可以指导硬件设计**：加上哪个硬件特性后这个算子的性能会更好、对端到端有啥影响——这个你**和余辉对一下，把你算子的 perf model 接到他的模型上**，这样会更准一些。」

**文进辉（控制范围与节奏）**
- 「这就是我们之前优化的时候，**不知道走没走到上限，不知道要花多大精力**，所以现在让他做的就是这个。」
- 「他现在唯一跟我们说的区别就是：**他的硬件上限是实测出来的，我们说的硬件上限是手册给的**。」
- 误差怎么验证：「他按这套模型优化到某个程度（比如 50% 多），模型已经指导不了他了，后面靠自己摸索；**如果探索一两周、两三周还是没有优化方向，那证明这个 roofline 模型就是挺准的**。来几套算子过来，就能把模型压实到比较可靠的程度。」
- 「你这相当于是**指令级别的 replay** 了……甚至把每个指令的时钟周期都算进去，那这事暂时就干不了。」

- 「**不要把愿景定得太大**，第一个版本愿景太大这个事可能就会黄，小步快走。」「TMA 这种硬件现在都没有……按**版本化管理**。」

**谭波（当场提出的疑问，仍待对齐）**
- 「目前是实测，直接测硬件（跑小程序量带宽和硬件特点）。」→ 被要求改成「给理论值也能出」。
- 「这个能弄，肯定能弄。只是目前文档写的是按实测硬件来的，仿真这块肯定也可以。因为**算法本身最低需要搬运的数据量和计算是确定的**。」
- 「基本的 roofline 模型用来判断带宽/算力受限，对**实际算子能优化到的上限，它的指导肯定是不准的，只能给大致方向**。并且我们第 6 章明确有**四个下限**：理论下限、拆分下限（工作集放不进 LDS 要拆 kernel，kernel 之间多出显存交换）、满载下限（当前真实字节流不停跑能达到的上限）、实测上限。KDA 的优化就是按这四层来的，对应三个方向：kernel 间交接、kernel 内冗余、硬件空等。」
- 「理论下限可以判断出来，但**实际能达到的上限还是要在做的过程中逼近**，比如拆成 3 个还是 4 个 kernel，是需要自己判断或者测试的。」
- **最核心的未解问题**：「他输入 KDA 这个算子，要评估它在给定硬件上的上限，**对于 KDA 这个算子要输入什么信息呢？我的 shape 吗？head 吗？还是 KDA 算子具体的实现是怎么实现的？它总得有个公式吧？**」→ 钱永军答「不要借助 AI，要做成工具，别人输入算子的 size、shape」；余果答「输出算子基本信息 shape、dtype，然后算计算强度」；最后结论是「**先调研，再拉专项会对齐**」。

## 三、从原话归纳出的真实需求（供专项会确认）

1. 使用者不是谭波自己，而是**组内其他优化人员（刘恒业等）+ 余辉的端到端 perf model + 硬件设计评估**三类。
2. 硬件侧输入必须支持**纯手册理论值**（算力、带宽、L2/L1/LDS 容量、未来的 TMA/co-issue/scaling 等特性），实测标定退化为可选的「校准模式」。
3. 算子侧输入要**尽量轻**（shape、dtype 一级的信息），不要求用户提供实现代码或指令流。
4. 输出：**理论性能上限 + 瓶颈区域判定**（访存受限 / 计算受限 / 其他资源受限），精度期望「比乘固定系数准」，**不要求指令级精确**；但要能给出**误差水位**。
5. 排期：**文档先行（已完成初稿）→ 调研 → 专项会 → 工具化**；工具按版本管理，不追求一次做全。
