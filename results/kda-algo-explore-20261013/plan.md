# KDA 算法形式探索 v0.1（2026-10-13）

**目标**：改变“需要经过显存的东西”本身，而不只是改写 kernel 的写法。

**前提**：
- 现有拆分方式下，各 kernel 之间的接口字节约为必需量的 5.45 倍；实际执行的字节约为 6.5 倍（16K/TP2）。
- 融合在 gfx936 上受三方面限制：寄存器（每 wave 256）、LDS（每 CU 64 KB），以及宿主 kernel 已经受发射或延迟限制（R37）。
- 所以必须从算法形式入手，让每个阶段需要交接的中间张量变少或变小。

## 1. 结构事实：哪些耦合是本质的

| 量 | 依赖维度 | 结论 |
|---|---|---|
| 前向状态 h、反向 dh | 沿 chunk 串行；V 的各列互相独立；K 维通过 W·h（对 K 求和）和逐通道门控耦合 | 递推只能按 V 切分，不能按 K 切分 |
| dq、dk、dg、dA、dAqk | 都要对 V 求和（do·hᵀ、v_new·dhᵀ、dv2·hᵀ、do·v_newᵀ） | 若按 V 切分融合，每个切片都会产生 fp32 部分和，交接量翻倍，所以不可行 |
| dv、dv2 | 按 V 列独立 | 可以和 dh 递推一起按 V 切分 |
| 每个 chunk 的梯度计算 | 需要 h_c、dh_{c+1}、v_new、dv2 | 只要梯度计算按 chunk 并行，这四者就必须写入显存，约 1.5 KB/token·head，是“状态接口”的下限 |
| 其余 W/U/K̃ 变体、g、qn/kn、dA、dAqk、dwT、fp32 dq/dk/dg | — | 都是拆分带来的接口，约 16 KB/token·head，是算法形式可以动的部分 |

“整个反向做成一个串行融合 kernel”已用模型排除：每个 head 只有 1 个 CTA，16K/TP8 每个 chunk·head 约需 75 µs 的 CU 时间，256 个 chunk 串行约 19 ms。

## 2. 候选形式与第一轮量级估算

| # | 形式 | 去掉 / 增加什么 | 估算（16K，模型） | 结论 |
|---|---|---|---|---|
| F1 | **分段并行递推**（FLA 的 CP 预处理思路：每段先求局部状态和段转移矩阵，再串行合并、修正） | 串行链缩短到原来的 1/P，代价是递推工作量翻倍 | TP8：递推按全卡吞吐算（TP2 实测折算），12 个 head 约 1.48 ms，翻倍后 2.96 ms，**高于现在受延迟限制的 1.93 ms** | **排除** |
| F7 | **矩阵值扫描**（把 chunk 转移矩阵复合起来，用矩阵乘换掉串行链） | 每个 chunk 要读写 128×128 的矩阵，约 512 B/token·head/层；矩阵乘大量增加 | TP2 下访存增加；TP8 下与 F1 同理 | **排除** |
| F2 | **统一布局**：每个张量只写一种布局，消费方经 LDS 转置读取（ds_read_m32x16 / transposed fragment） | 去掉 Wb（Wn 的副本）、dOT（do 的副本）、Vn 的 C 布局和 aN 副本、kgB 等，约 1.0–1.5 KB/token·head | TP2 约 −3~5%；消费方受 TA 或延迟限制，LDS 转置的代价要实测 | **主线之一**，先做微基准 |
| F3a | **在 s4b 内重算 dAqk**（MMAC：do·v_newᵀ，每个 chunk 0.5M 次乘加） | 去掉 dav 写出的 fp32 dAqk（读写共 512 B/token·head），以及 s4b 开头的转置 gather | TP2 约 −1~2% | 次要 |
| F4 | **前向保存 bf16 状态 h**（显存仍在 FLA 默认预算内），反向在消费方用 v_new = U − W·h 重算 | 去掉 fwd_h_bn 这一遍串行，以及 P1 那几份布局（约 1.5 KB），前向多写 512 B | 之前实测 keep-state 只快 1–4.5%；模型显示 TP8 的延迟链少一遍 | 次要，可与 F2 一起做 |
| F8 | **换掉块内算法**：不显式构造 T = (I+Akk)⁻¹ 及其反向。例如以 16 行子块为单位做块内递推或分块前代，把 64×64 的求逆和 dAkk = −Tᵀ(·)Tᵀ 换成 4 个 16×16 的小求解，再加一条很短的块内状态链 | s4a 的 dA 阶段、s4b 中依赖 dA 的表格（dak/akB），以及 prep 的 T 求逆都要重写。中间张量 dA（fp32）、dwT 有可能消失；VALU 和 LDS 需求降低（小矩阵） | 若 s4a 与 s4b 里和 T 相关的部分减半，TP2 约 −8~10%；数值属于 B 类 | **主线之二，最深**，需要推导和数值研究 |
| F5 | **按吞吐选择递推的切片宽度**（P-49 推广到 dhu），每个 CTA 处理多个 head 或多列，摊薄共享读取 | 去掉 V-slab 之间重复读的共享分块 | 32K/48 +0.85%，64K/48 +3.4%（P-49 实测，前向与重算） | 进行中（第 A 项） |

## 3. 评估方法（下一步要补的工具）

1. **design_eval 增加“假想 kernel”的输入**：每个阶段的读写字节（按访问模式）、VALU、MMAC，直接用 TA 代价表和递推单步微基准算出 TA、VALU、显存、延迟链四项时间。
2. **容量预算检查器**：按每个 wave 常驻的操作数和循环临时变量估算 VGPR，按共享表格和分阶段缓冲估算 LDS，先排除放不下的形式（B4b 的教训）。
3. **关键原语的微基准**：LDS 转置读取的代价（F2）；16×16 子块求解链的单步延迟（F8）。

## 4. 执行顺序

1. **F2 的微基准**：在 gfx936 上测 ds_read 转置分片读取（每条指令的周期数、bank 冲突），据此判断“消费方转置”是否划算，再选第一个张量（Wb 或 dOT）做原型。
2. **F8 的推导**：写出“子块递推”形式下前向、反向的完整计算图和中间张量清单，用模型估算，再决定是否做数值原型（先用 PyTorch 参考实现对 FP64 验证）。
3. F3a、F4 作为小项穿插进行。

## 5. 公开资料调研（2026-10-13）

| 项目 | 平台 | 覆盖 | 关键设计 | 能否迁移到 gfx936 |
|---|---|---|---|---|
| [MoonshotAI/FlashKDA](https://github.com/moonshotai/FlashKDA)（含 v1 设计说明） | SM90+，CUTLASS | **只有前向**（推理），FLA 在 inference_mode 下自动调用 | **chunk 取 16**：lower_bound=−5 时，16 步内 exp(cumsum g) 在 bf16 范围内，不需要块内重缩放；16×16 求逆直接前代。**拆成两个 kernel**：K1 按 token 并行做门控、l2n、衰减、L/Mqk 和求逆；K2 按 head 并行做递推和输出。早期试过单一融合 kernel，因为递推并行度低，反而慢 15% 以上。状态在片上存 bf16，更新用 fp32 FMA。sigmoid 用 tanh.approx，exp 用 ex2.approx。用 MOVM_T 在寄存器堆内转置 | 拆两个 kernel 的结论和我们一致（R：前向融合不划算）。chunk 16 只适合前向：训练要按 chunk 落盘 h/dh，chunk 16 时每 token 的状态字节变成 4 倍，所以不适合我们的训练反向。近似 exp/sigmoid 属于 B 类数值改动。gfx936 没有 MOVM_T |
| [NVlabs/kda](https://github.com/NVlabs/kda)（Kernel Design Agents） | B200/B300 | 前向三套（CuTe、TIRx、PTX，比 FlashKDA 快 2.5–3.6 倍）；**反向一套（TIRx 持久化 megakernel，B200）** | 前向：host 调度器把（序列，head）的递推链打包到各 SM 上，长序列在 kernel 内以 FP32 交接状态，切给多个 CTA。反向：输入是 FLA chunk_kda_bwd 的预备张量，一次 launch 完成全部反向，按“152 个 CTA / 768 条链”的静态计划调度。累积衰减表始终保持 FP32，精度明显好于 FlashKDA | 依赖 Blackwell 的大容量片上存储（228 KB SMEM + 256 KB TMEM / SM）和 TMA，无法直接移植。可借鉴的是**持久化静态调度**：递推链和按 chunk 并行的工作放在同一个 kernel 里按 CU 分配角色，避开 P-41 的 CU 共享争用和各 kernel 尾部的 wave 量化，见 F9 |
| [sgl-project/cuLA](https://github.com/sgl-project/cuLA) | SM90 / SM10X，手写 CUDA | KDA 前向：Hopper 融合版平均比 FLA v0.4.2 快 1.52 倍，Blackwell 模块化版平均快 1.45 倍；**反向优化仍在路线图上** | 路线图包括：用多项式近似 exp（同 FA4）缓解 exp 瓶颈、加大 chunk、SM10X 上用 2-CTA | 多项式 exp：gfx936 上 v_exp_f32 是四分之一速率，按 packed fma 估算，每个元素约 3 个发射槽、原来是 4 个，收益小且属于 B 类 |
| [Int21-AI/KDA-H100 / B200](https://github.com/Int21-AI/KDA-H100) | H100 / B200，CUDA + PTX | **只有前向** | TMA、mbarrier、ldmatrix、cp.async，近似 exp/rcp/rsqrt | 硬件特性不同，无法迁移 |
| FLA 自身（0.5.x） | Triton 为主 | 训练前向 + 反向 | 已有 `chunk_kda_bwd_kernel_wy_dqkg_fused`（相当于我们的 s4 两个 kernel 合一）、`inter_solve_fused`（块间 Akk + solve_tril 合并）、按 token 并行的块内 kernel。0.5.0 起支持多后端：KDA 有 **tilelang** 后端，推理时走 flash_kda | 我们在 H20 上测的基线是 FLA 0.5.2 的 Triton 路径，当时没有装 tilelang。**目标可能变动**：H20 装上 tilelang 后，FLA 默认路径可能更快，需要复测 |

**结论**：
- 公开的大幅加速几乎都是 Hopper/Blackwell 上的**前向或推理**，依靠大容量共享内存、TMA 和 warp specialization 获得。
- 训练反向仍以 FLA 的多 kernel 结构为主；唯一的融合反向是 B200 上的 TIRx megakernel。
- 没有现成的“算法级技巧”能直接改变 gfx936 上的结论。

**新增候选 F9：持久化反向 megakernel（静态调度）**

| 项 | 内容 |
|---|---|
| 做法 | 一次 launch 完成反向。每个 CU 一个常驻 CTA，按静态计划执行任务：递推链（fwd_h_bn、dhu）固定放在一部分 CU 上，按 chunk 并行的任务（wu、dav、s4a、s4b、收尾）由所有 CU 领取，依靠显存里的标志位处理依赖 |
| 去掉什么 | 各 kernel 尾部的 wave 量化（P-49 已证明这在 TP2 下显著，例如 64K/48 的 L2 颠簸）、kernel 启动间隙，以及“递推期间其他 CU 空闲”的时间 |
| 代价 | 工程量大，依赖标志位同步；必须避免 P-41 那种递推与并行任务共用 CU 的争用 |
| 估算 | 收益上界约等于“递推链 + 尾部浪费”：TP8 约 10–20%，TP2 约 3–6%，需要先做调度模拟 |

**F8 的容量复核**：
- 块内改成 16×16 分块求解后，与 T 相关的矩阵变小。
- 但 s4a 与 s4b 融合时，LDS 的大头是 dwT（128×64 bf16，16 KB）、块内表格（13 KB）和 h/dh 暂存，这三项都不随 T 的形式缩小。
- 所以 **F8 解决不了 F6 的 LDS 容量问题**，收益只剩 T 反向部分的 VALU 和延迟，约 2–4%。**降级**。

## 6. F9 与 F2 的实测 / 复核结论（2026-10-13）

### F9：持久化或并发调度——证伪

**模拟**（f9_sched_sim.py，16K/TP8，借用前向 P-41 的争用系数：递推 0.48、并行 0.71，且假设争用只发生在递推所在的 CU 上）：

| 策略 | 反向耗时 | 相对串行 5094 µs |
|---|---:|---:|
| 递推与并行任务共用 CU | 4364 µs | 省 10.8% |
| 只在递推等待时接活 | 4575 µs | 省 7.7% |
| 递推独占 CU | 9717 µs | 大幅变慢 |

前向：1685 → 1493 µs（省 2.8%）。

**实测争用**（f9_contention_probe.py：录下真实反向各 launcher 的参数，两组数据互不依赖，在两条 stream 上并发重放）：

| 组合 | 单独运行 | 并发运行 | 并发总耗时 vs 串行 | 递推速度 s | 并行速度 p |
|---|---|---|---|---:|---:|
| fwd_h_bn ∥ wu+dav | 0.558 + 0.939 ms | 0.804 / 1.384 ms | 1.384 vs 1.497（−7.5%） | 0.69 | 0.45 |
| dhu ∥ s4a+s4b | 0.684 + 1.912 ms | 1.156 / 2.525 ms | 2.525 vs 2.596（−2.7%） | 0.59 | 0.47 |

**分析**：
- 并行 kernel 整体只剩 0.45–0.47 的速度。递推只占 48 个 CU，也就是说争用并不局限于这些 CU：递推 CTA 占住了 VGPR 和 LDS，使同一 CU 上能驻留的并行 CTA 变少，同时还在争抢共享的 L2、TA 和显存。
- 两组合计最多省 0.18 ms（约占算子 2.7%）。这还是数据无依赖时的上界；加上依赖后会更少。
- 模拟中 10.8% 的前提（争用只发生在递推所在的 CU）不成立。
- **F9 降级为不做。** 这与 P-41 和 R35 的结论一致：在 gfx936 上，递推与并行工作同时驻留时，争用会吃掉大部分重叠收益。

### F2：统一布局——已被前几轮挖完

| 位置 | 情况 |
|---|---|
| 已做过的 | P-17 去掉了 vB（s4a 读行主序的 v，在片上构造操作数）；P-20 去掉了 aN_do；P-22 去掉了 aN 副本。这些都是“由读整行的消费方经 LDS 转置”的情形 |
| 剩下的副本 | Wn/Wb（W 的 A、B 两种形式）、KgA/Kn（kg 的两种形式）、dOT（do 的转置） |

剩下的副本，消费方都是按 V 切片的递推 kernel（fwd_h_bn、dhu），两种替代办法都不划算：
- **直接读另一种布局**：一个 32 列 slab 每行只有 64 B 连续，属于 16 行 × 64 B 的分片访问，按 TA 代价表每条约 169 周期，是现在原生布局（22 周期）的约 8 倍，而 TP2 下这两个 kernel 本来就受 TA 限制；
- **在片上转置**：用 LDS 或 bpermute 转置，会在 TP8 的关键路径（每一步）上增加指令。

预期收益为零甚至变慢，**不做原型**。

### 小结：结构性方向已全部评估完

| 方向 | 结论 | 依据 |
|---|---|---|
| Phase A（前向分段流水） | 证伪 | P-41 |
| keep-state | 1–4.5% | 实测 |
| F6（s4a+s4b 融合） | 变慢 | 实测 |
| C2（收尾融进 s4b） | 不成立 | 容量核算 |
| B4b（融合梯度 kernel） | 0.88–0.91 倍，止损 | P-47，R37 |
| chunk 128 | 不划算 | 递推单步微基准 |
| chunk 16 | 只适合前向 | FlashKDA 的设计；训练反向状态流量为 4 倍 |
| F1（分段并行递推）、F7（矩阵值扫描） | 不成立 | 模型估算 |
| F8（换块内算法） | 2–4% | 容量复核 |
| F9（持久化 / 并发调度） | 不超过 2.7% | 实测争用 |
| F2（统一布局） | 已被前几轮挖完 | 本节 |

剩下唯一字节降幅较大、又不受片上容量限制的方向，是**数值格式**：fp32 中间结果改用 bf16 交接，涉及 dq/dk/dg、dA、dAqk、g，约 1.5–3 KB/token·head，TP2 估计 5–10%。它属于 B 类，必须先做精度研究（规则 2：FP64 精度不差于现状）。
