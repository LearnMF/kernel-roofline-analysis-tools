# P-76：TP8 重算递推的 U 预取（2026-10-16，bw46 HCU7，A2 探针 (b)，**不合入**）

**依据**：用 `blocks/vm_wait_map.py` 回放每个 wave 的 VMEM 队列：gfx9 的 vmcnt 同时计数读和写，并按发射顺序退役。重算递推（MODE 4）链上最大的一项（306 周期/步）是下一步 W 读之后的 `s_waitcnt vmcnt(14)`（步内位置 67）。它在等上一步位置 112 发出的 `loadU(nxt)`，而那条读紧跟在本步的两条 Vn 写之后。

**改法**（`examples/kda/p76_rec_u_prefetch.py`，模板参数 UV，探针期间用 `KDA_G2_REC_UV` 选择，只作用于生产版 TP8 重算实例 `<VL,4,GE,SG,!PF,KP,!VP,BP>`）：
- UV=1：U 提前两步预取。un0/un1 存第 i+1 个 chunk 的 U；v_new 算完后执行 uf ← un，再把 U(i+2) 读进 un。
- UV=2：把 loadU(nxt) 挪到两条 Vn 写之前。

两个实例都没有 scratch，VGPR 分别为 141 和 139。两者的逐位门禁都是 GATE_ALL PASS（10/10，对照生产版 g2_r5）。

**重放计时**（`examples/kda/op_env_time.py`：记下生产版的 fwd_h_bn 调用参数后，在同一进程内轮流切换 UV 重放，20 轮取中位数）：

| UV | 16K/12 | 64K/12 |
|---|---:|---:|
| 0（生产版） | 455.5 µs | 1514.8 µs |
| 1 | 0.917 | 0.983 |
| 2 | 0.966 | 0.982 |

**UV=1 为什么变慢**（SQTT `cp_p76uv1_d3.txt`）：每步 2441 周期，生产版是 2238。链上出现一个新的 1371 周期等待：位置 330 的 `s_waitcnt vmcnt(6)` 在等**同一步**位置 121 刚发出的 U(i+2) 读。原因推测：编译器把循环内的 `uf ← un` 当成循环头处的 phi，phi 消除会在循环末尾插入拷贝。拷贝要读 un，而 un 的数据要在本步结束前到位，结果把原本有两步余量的预取，变成了“当步发出、当步就等”。
- **新规则 R56**：用寄存器拷贝实现跨步双缓冲时，phi 消除会把拷贝放到循环末尾，等于在本步末就要等新发出的读。想要真正做到提前两步，必须静态地交替使用两组寄存器（循环展开两倍或按奇偶分支），代码量会翻倍。

**UV=2 也变慢**：把 U 读挪到 Vn 写之前，并没有消除等待（0.966 / 0.982）。说明那 306 周期主要不是 R52 所说的写排在读前面造成的，而是 U 读本身的延迟。U 是每个 V-slab 各自独有的数据，4 个 CTA 之间不共享，大概率每次都要去 HBM 取。这与规模扫描的结论一致：访存延迟随全卡流量上升。

**结论**：P-76 不合入，代码保留为默认关闭的探针。剩下的唯一形式是循环展开两倍的静态双缓冲，上限约为每步 306 周期（重算递推约 −13%，约 60 µs，占算子约 1%），而且会让代码量翻倍，影响指令缓存。按新的阶段目标（逼近算法访存下限），这类递推单步的小项排在“拆分方式带来的约 6 倍多余字节”之后。
