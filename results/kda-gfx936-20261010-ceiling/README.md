# KDA 上限评估：R5 对比当前生产（模型 v2，2026-10-10）

本文是每轮优化结束后都应产出的“上限评估”。两边用同一把尺子量：
- **R5**：用 v2 模型重新分析 10/09 的原始数据。PMC 原始计数已经提交，所以 TA 计数可以从中恢复；
- **当前生产**：R5 + P-1..P-4 + L16 + P-9 + P-10，于 10/10 采集。

逐 kernel 的明细表见同目录的 `*.waterlevel.md`。

## 模型 v2 相对 v1 的变化

1. **新增一种资源：向量访存发射（TA）利用率**。
   - 计算方法：`Σ TA_TA_BUSY / (GRBM × CU 数)`；
   - 标定：L0 的 `vmem_issue` 达到饱和时，这个值是 0.91–0.93，与 hipprof 给出的“L1 cache unit is active”一致；
   - 这个资源计入实现下限，按饱和值 0.92 换算。
2. **吞吐判断改为按“正在工作的 CU”计算**：只用 48 个 CU 的 grid，在这 48 个 CU 上一样可能被吞吐卡住；空闲的 CU 另行标为并行度不足。
3. **新增两张表**：
   - 每个 launcher 的多维度判定：HBM、计算流水线、向量访存发射、LDS 等待、依赖链、CU 占用；
   - 算子级的四层时间分解，用来判断该做局部调优还是全局重构。

**回看验证**：用 v1 模型分析 R5，v8o、dhu、dav、s4 都会被判成 `C/latency`（延迟受限）。用 v2 重新分析同一份 R5 数据，它们都是**向量访存发射受限（63–87%）**，下一步的建议直接是“减少向量访存指令 / 用更宽的访存”，也就是 L16 的做法。L16 实测收益最大的正是发射利用率最高的 dhu（86% → 快 1.23 倍）。如果当时就有 v2，P-4、P-5、P-6 这几个失败实验本可以省掉。

## 计算角度：MFU / HFU（8K/H12，当前生产）

- **模型 FLOPs**：54.0 GFLOP（算法本身，前向 × 3；计算方法见 `op_spec.json` 的 `flops`）。按可达的 476 TFLOPS 算，计算下限是 113 µs；
- **MFU 2.6%**（按理论 491.5 TFLOPS），按可达峰值算是 2.7%；
- **HFU 12.8%**：MMAC 单元实际执行了 261 GFLOP，包括分块重算和 padding；
- **结论**：KDA 不是计算受限的算子，计算下限只占实测时间的 3%。MFU 只用于汇报，不作为优化目标。各 launcher 的 MMAC 利用率（HFU）最高的是 fwd_prep，26.8%。

## 算子级：时间分成四层（8K/H12，PMC 计时）

| 层 | R5 | 当前 | 怎样才能减少这一层 |
|---|---:|---:|---|
| 物理下限（只算跨阶段的张量和依赖链，与怎样拆 kernel 无关） | 303 µs（7%） | 303 µs（7%） | 无法减少，由硬件决定 |
| 拆分代价（现在 10 个 launcher 的拆法，相对物理下限多出来的部分） | 1455（33%） | 1455（35%） | 融合，减少中间结果在 HBM 上的往返 |
| 多余工作（实际读写的字节和发出的指令，超过接口最小量的部分） | 2081（47%） | **1461（35%）** | 改布局、去掉 launcher 内部的冗余 |
| 执行效率损失（在已有工作量下的停顿） | 635（14%） | **941（23%）** | 局部调优：等待、调度、占用率 |
| **合计** | 4474 | **4160** | |

8K/H48 的形状完全一样：物理下限 8%、拆分代价 37%、多余工作 35%（R5 是 41%）、执行效率损失 20%（R5 是 16%）。

**解读**：
- 这轮优化压缩的是“多余工作”层（2081 → 1461 µs），对应 L16 和 P-2。工作量减少以后，有一部分以停顿的形式重新出现，所以“执行效率损失”层从 635 涨到 941；
- “拆分代价”层一直没动，因为至今所有改动都没有改变 launcher 的拆分方式。

## 按阶段看拆分代价（当前生产，8K/H12）

| 阶段 | 实测 | 现有拆法的下限 | 物理（融合）下限 | 实测 / 现有下限 | 现有下限 / 物理下限 |
|---|---:|---:|---:|---:|---:|
| 前向（fwd_prep、fwd_h_o） | 952 µs | 292 µs | 114 µs | 3.3 倍 | 2.6 倍 |
| 反向（8 个 launcher） | 3187 µs | 1462 µs | 190 µs | 2.2 倍 | **7.7 倍** |

反向的 8 个 launcher 之间要经过 HBM 交换约 1.3 GB 中间数据，其中仅 wy_s4_split 的接口就有 567 MB。**这是目前最大的一块结构性空间，而且没有任何局部调优能触及它。**

## 全局方向的候选：融合哪两个 launcher 收益最大（`python -m kra.model.fusion`）

做法：从 launcher 接口记录中建立“谁写、谁读”的中间张量图。如果把一对 launcher 融合，消费者的读就不必经过 HBM；若消费者是唯一的读者，生产者的写也一并省掉。这些字节按可达带宽折算成时间。

这里只算省下的流量，因此是**上限**。能否真正实现，取决于片上容量、重算成本和占用率。

8K/H12 下，中间张量经过 HBM 共 **1905 MB，折合 1422 µs（占算子的 34%）**。张量的生产者和读者按“版本”配对：caching allocator 会复用地址，所以一次读属于这个地址在它之前的最后一次写。排名前列的候选：

| 生产者 → 消费者 | 省下的流量 | 折合时间（8K/H12） | 8K/H48 |
|---|---:|---:|---:|
| wy_s4_split → bwd_tail（dq/dk/dg 的 fp32 部分和） | 303 MB | **226 µs** | 904 µs |
| fwd_prep → fwd_h_o（前向的 5 个中间张量加 Gn） | 228 MB | 170 µs | 681 µs |
| wu → fwd_h_bn / wu → dhu_bn | 各 151 MB | 各 113 µs | 各 451 µs |
| fwd_h_bn → wy / dhu_bn → wy | 各 151 MB | 各 113 µs | 各 451 µs |
| dav → wy / dav → dhu | 各 101 MB | 各 75 µs | 各 301 µs |

各方案的可行性见 **[bwd_fusion_eval.md](bwd_fusion_eval.md)**，包括依赖图是否凸、片上容量和数值三方面。

## 对“局部最优还是全局最优”的回答

1. **在现有拆法之内**：实测 4160 µs，现有拆法的下限是 1758 µs。也就是说，即使完全不改拆法，理论上还有最多 2.4 倍的空间，主要在多余工作和停顿这两层。dhu、dav、l2n_apply 已经到了当前指令流或这种拆法的下限，再调它们的延迟没有意义。
2. **跨越拆法**：现有拆法的下限是 1758 µs，物理下限是 303 µs，差 1455 µs，其中 87%（1272 µs）在反向。这部分只能靠重新设计反向的数据流来拿：融合 launcher，或者调整中间结果的生命周期。
3. **方向判断规则**：每轮之后看四层里哪一层最大，也看它的变化趋势。当前多余工作和拆分代价并列最大（各 35%）。所以下一阶段的局部工作应该集中在“已到实现下限、但还能减少工作量”的 dhu 和 dav，以及计算流水线已满的 fwd_prep；同时需要开始评估反向的融合方案。它属于“需要人决定”的结构性变化，可以先用 op_spec 估算融合后的下限，再决定是否投入。
