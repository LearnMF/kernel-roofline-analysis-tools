# KDA 算子逐 kernel 水位表（L2 + L4，gfx936 / BW1000，2026-10-09）

## 环境与口径

- 节点 bw7，容器 `tanbo_mega_k3`。PMC 在 GPU0 上采集（`--pmc-read` / `--pmc-write`），launcher 接口捕获在 GPU1 上运行（不需要 profiler）。
- 算子：Kimi K3 KDA，一次前向 + 反向，hip_kda G2（R5 树）。
- 各 shape 的完整表格见同目录 `*.waterlevel.md`；原始 PMC csv、`pmc.json`、`optrace` 在 `raw/`。在仓库根目录用 README 中的 `kra analyze` 命令可以**逐字节复现**这些表格。
- 口径见 [docs/methodology.md](../../../docs/methodology.md) §3–4。简要说明：
  - **先验下限**：接口字节按该 grid 可达带宽折算的时间、只算依赖的关键路径、launch 开销，三者取最大；
  - **实现下限**：不改实测工作量，假设把硬件用满时的时间；
  - **融合下限**：假设每个阶段只用一个理想 kernel，只有阶段边界上的张量进出 HBM。

## 结论

1. **KDA 还没有到上限。** 在当前 10 个 launcher 的拆分下，先验达成率为 39–43%，理论上最多还能快 2.3–2.5 倍。只有 l2n_apply 已经到顶（95–98%）。
2. **“延迟型算子”需要按 kernel 区分。** 时间占大头的 v8o、dhu、dav、s4a、s4b 属于 C 类（延迟受限）；prep_a、gate 受 VALU 吞吐限制；wu、bwd_tail、prep_b、l2n 受 HBM 吞吐限制。
3. **递推 kernel 不受依赖链限制。** 只算依赖的关键路径，每个递推在 8K 时只需 13 µs（当前数据流的链也只有 65 µs），而实测是 417–541 µs。它们离下限远，原因是延迟没有被隐藏（SQTT 测得 91.5% 的周期在空等），以及 H=12 时 48 个 CTA 带来的并行度不足，而不是递推本身的串行性。这是在“算法串行”之外仍然存在的实现空间。
4. **更正此前分析中的一个数字。** 旧脚本 `pmc_lds.py` 的 “valu_busy” 多除了一个 4。prep_a 的 VALU 利用率实际是 76%，不是 18%；gate 是 89%，不是 19%。因此 prep_a 和 gate 应该归为吞吐受限，而不是延迟受限。
5. **拆成多个 kernel 本身是有代价的。** 融合下限（0.30 ms）与先验下限（1.76 ms）之间相差 1.46 ms，这是当前 launcher 边界必须承担的 HBM 往返流量。要低于 1.76 ms，只能合并 launcher 或重新设计数据流。

## 局限

- **接口字节可能被高估。** 计算时假设每个输入至少完整读一次。如果某个 launcher 实际只需要输入的一部分，真实的最小流量会更低，那么该行的先验下限会偏高（偏乐观地报告达成率）。
- **没有逐 kernel 的计算先验。** 计算量只用实测 MMAC 工作量计入实现下限。按 KDA 分块算法估算，前向+反向的矩阵乘法量在 8K/H12 时只有几十 GFLOP，按 476 TFLOPS 计算只需约 0.1 ms，不会成为约束。
- **部分 kernel 的延迟子类型未确定。** dav、s4a、s4b 标记为 `C.unresolved`，需要 P2 的 SQTT 确认。此前的 SQTT 结果显示 s4a/s4b 的 waitcnt 占比为 35–46%，指向访存延迟暴露。
- **峰值来自微基准。** 如果出现比微基准更快的 kernel，审计会自动标记（目前没有）。
