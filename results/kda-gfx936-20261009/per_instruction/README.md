# v8o / dhu 逐指令分析（gfx936，8K/H12，2026-10-09）

## 方法（工具：`kra/sqtt/pcmap.py`）

1. **采集**：用 SQTT 采集生产 kernel（`examples/kda/sqtt_capture.sh`，标准 bench 是 `bn_sqtt.hip`）。
2. **导出发射流**：XCompute CLI 的 `--sqtt-sections pipeline --sqtt-location xcd=,se=,cu=,simd=,wave= --sqtt-time-range a:b` 能导出单个 wave 的完整发射流，包括每条指令的发射时间戳和指令之间的气泡。这是 CLI 里唯一能拿到逐指令时间的途径，`hot_inst` 和 `bubble_summary` 只按 opcode 汇总。
3. **源码映射**：ISA 用 `-gline-tables-only` 编译。已核对 v8o4 的 946 条指令与生产 codegen 完全相同，`.loc` 给出每条指令对应的源码行。
4. **对齐**：hot loop（含 MMAC 的最内层循环）每次迭代的控制流相同，所以把每一步的动态 opcode 序列与静态循环体做序列对齐（difflib），就能把每个气泡归到具体指令上。
5. **气泡的记账**：
   - 紧跟在 `s_barrier`、`s_waitcnt` 之后的气泡，记为在这两条指令上的等待（等 barrier 或等计数器）；
   - 其余气泡记为下一条指令的发射停顿（依赖或结构冲突）。
6. **多 wave**：CTA 的步长由最后到达 barrier 的 wave 决定，所以要对同一个 CTA 的每个 wave 分别做（dhu 就是这种情况）。

## v8o4（4 个 wave，每个 SIMD 1 个；每步 5716 周期；对齐 9 步，84% 的停顿被归到指令上）

| 类别 | 周期/步 | 占比 | 指令数/步 |
|---|---:|---:|---:|
| global_load 发射停顿 | 1690 | **29.6%** | 32 |
| 整数地址 VALU | 730 | 12.8% | 195 |
| barrier 等待 | 466 | 8.1% | 2 |
| waitcnt | 436 | 7.6% | 34 |
| LDS | 412 | 7.2% | 42 |
| MMAC | 135 | 2.4% | 48 |

停顿最多的一条指令是 GEMM1 之后的第一个 `loadW(nxt)`（`g2_fwd_v8.cuh:276`），每步 410 周期。

## dhu v8b（8 个 wave，每个 SIMD 2 个；每步约 6770 周期）

| wave | barrier 等待 | global_load 停顿 | global_store 停顿 |
|---|---:|---:|---:|
| 每个 SIMD 上的第 1 个 wave（slot 0） | 38–42% | 19–20% | 5–6% |
| 每个 SIMD 上的第 2 个 wave（slot 1，关键 wave） | **0.4–8%** | **38–43%** | **17–23%** |

两个 wave 共享向量访存发射，后来的 wave 被饿着。整个 CTA 的步长由 slot 1 决定，slot 0 都在 barrier 上等它。

## 关键的硬件事实（新增 L0 原语 `vmem_issue`，见 `machines/gfx936-bw1000.json`）

每个 CU 对 cache 命中的读，按发射一条 wave 级指令计：

| 宽度 | 命中 L1 | 命中 L2 |
|---|---:|---:|
| `dword` | 8.3 周期 | 10.0 周期 |
| `dwordx2` | 16.1 周期（32 B/clk） | 16.2 周期 |
| `dwordx4` | 18.4 周期（56 B/clk） | 22.8 周期（45 B/clk） |

由此可以推出：
- v8o4 每步 32 条 `dwordx2` × 4 个 wave × 16 周期 = 2048 周期，**占 CU 向量访存发射能力的 36%**；
- dhu 每步 19 条 × 8 个 wave × 16 周期 = 2432 周期，同样约占 36%；
- 同样的字节数，用 `dwordx4` 发射，访存发射时间可以减少约 29%（按 L2 命中算）。

## P-7 的结论（预测见 `validation/predictions.md`）

把 `loadW(nxt)` 挪到 bar2 之前之后：
- fwd_h_o 没有变化（439.5 → 438.4 µs）；
- fwd_h_bn 慢了 4.4%（407 → 425 µs）。

**H1（写后读冲突）被证伪，H2（向量访存发射的结构性吞吐限制）得到支持**：停顿随读指令一起移动了。fwd_h_bn 没有 oh 段，挪过去的读紧贴在 bar2 前面，直接推迟了到达 barrier 的时间。已回退。

## 对“是否改用两级递推”的判断

- GLM 的 Z1、Z5 当时的前提是“每步受 barrier 链和 GEMM2 的串行依赖限制”（8 wave 时代的数据：bar2 等待 2.8 µs）。现在的逐指令数据显示，v8o4 的 barrier 等待只占每步 8%，依赖链上的 MMAC 停顿约 2%。**每一步的时间主要花在 CU 上的指令吞吐**：向量访存发射约占 36%，地址运算约占 13%，**而不是串行依赖链**。
- 两级递推（Z5）要把计算量变成 3 倍，以此换取更短的串行链。在吞吐受限的情况下，它主要靠用满 80 个 CU 来获益（H=12 时只用了 48 个），但在 H=48（每个 CU 约 2.4 个 CTA）时，3 倍计算量很可能让它变慢，而且会改变数值。
- **建议**：暂不做两级递推。先做两项逐位安全的修改，降低每一步的吞吐成本：
  1. **16 B 操作数布局**：把 W/QgA/Kn 等 A-form 原生布局改成按 kt 两两交织，每个 lane 一次读 16 B。这是跨 kernel 的布局修改，生产者（prep、wu）和消费者（v8o、dhu）都要改。按 L0 数据，访存发射时间预计减少约 29%，对应递推每步约快 10%；
  2. **减少整数地址运算**：每步 195 条，约占 13%。

  这两项做完之后，再用同一套方法重新评估两级递推的空间。
