# P-52：递推每步的指令瘦身（Gn 改为存衰减因子 exp2f(G)），已合入

**改动**（examples/kda/p52_gn_exp2.py；flash-train 部分在 p52_ft.py）：
- **问题**：Gn 只有一个用途，就是计算衰减因子 d = exp2f(gl)，共 7 处（前向递推、反向重算、dhu，含旧版 kernel）。前向递推每步每个 lane 要算 8 次带范围检查的 exp2f，约 50 条指令（v_cmp、v_cndmask、v_exp、v_mul、v_add），全部在串行链上。
- **做法**：改由生产方对每个元素算一次同一个设备端 exp2f：
  - 前向的 prep_a 直接写出 exp2f(refv)；
  - 反向的 `to_gn` 之后跑一个原地的 `g2_exp2_` kernel。
- **为什么逐位一致**：同一个函数作用于同一个 fp32 输入。也不增加显存，因为是替换 Gn 的内容，不是新增张量。

**每步循环的指令数**：

| kernel | 原来 | P-52 |
|---|---:|---:|
| 前向（MODE 1） | 433 | 359 |
| 反向重算（MODE 4） | 395 | 313 |
| dhu 8-wave | 270 | 229 |
| dhu 4-wave | 625 | 548 |

**门禁**：22/22 逐位一致（8192:12/48/96、16384:24、32768:12/48，每个形态测普通、keep-state、极端门控三种，加 4 组变长）。

**合入**：bw52 生产版 9cc164f，bw7 设备代码一致（35b7bd3a8862）。

## 迭代过程（三个坑）

| 版本 | 现象 | 原因 | 处理 |
|---|---|---|---|
| v1：直接 d = gl | MODE 4 在 16K/48 只有 0.84 倍，8K/96 只有 0.74 倍 | 编译器把衰减融进每步末尾的 FMA（ht = ht·d + upd），gl 要活到每步结束；而下一步的 Gn 预取在步中间就发出了，生命周期重叠。编译器只能在循环末尾插一次寄存器拷贝，这次拷贝要等预取的数据到达（`s_waitcnt vmcnt(5)/(4)`），显存延迟就串进了每一步 | — |
| v2：loadG 挪到状态更新之后 | 末尾的紧等待消失，但改变了访存的发射节奏 | — | 放弃，改用 v3 |
| v3：保留生产版的 loadG 位置，衰减通过 `g2_vcopy`（asm volatile 的 v_mov）取出 | 寄存器生命周期在原 exp2f 的位置结束，访存节奏与生产版相同；MODE 4 在 TP8 是 1.08–1.15 倍，但窄版在 192/384 个 CTA 时仍只有 0.93 / 0.83 倍 | 深度饱和时，少了 exp2f 这段 VALU 夹在两批访存之间，访存发射变密，争用加重（R21 的同类现象） | 进入 v4 |
| v4：窄版 MODE 4 在 ≥192 个 CTA 时走原代码 | 退化消除 | 反向额外保留一份原始 Gn（每 chunk·head 512 B），这种情况下 launcher 改用 GE=false 的实例，即生产版原代码 | 合入 |

## 5 轮 A/B（ab_kernels，每边 5 个进程，带显存位置抖动；比值 = 生产版 / P-52）

| 形态 | 前向 #1 | 重算 #2 | dhu | wu（未改动） | 总计 |
|---|---:|---:|---:|---:|---:|
| 16K/TP8 | 1.014 | 1.077 | 1.028 | 0.999 | **1.010** |
| 16K/TP4 | 1.074 | 1.025 | 1.050 | 1.000 | **1.011** |
| 16K/TP2 | 0.983 | 0.994（原代码） | 1.067 | 1.000 | **1.005** |
| 32K/TP8 | 1.024 | 1.124 | 1.008 | 1.001 | **1.012** |
| 32K/TP2（宽版） | 1.036 | 1.049 | 1.064 | 0.979 | **1.025** |
| 64K/TP8 | 1.140 | 1.150 | 1.002 | 1.000 | **1.024** |
| 8K/TP1 | 1.018 | 1.007（原代码） | 0.990 | 1.000 | **1.000** |

**测量上的一个陷阱**：v1–v3 期间，wu 的机器码逐字节相同，却稳定慢了 2–8%；到 v4 又恢复到 1.000。
- 各 kernel 的地址都按 256 B 对齐，对齐方式没有变；
- 同一版本里加一个从不调用的 pad kernel，在 16K/12 上 wu 是 1.000，在 TP2 上有 ±3% 的差异；
- 这说明 code object 的大小变化会改变设备内存的分配位置，从而影响受带宽限制的 kernel。

所以判定只看被改动的 kernel（沿用第 4 轮的规则），而且要跑 5 轮。

## 规则
- **R39**：编译器会把被拿掉的运算的输入融进后面的指令，延长它的寄存器生命周期。一旦与下一步的预取重叠，就会出现“循环末尾插拷贝并等待预取”的问题。检查方法：看循环末尾有没有紧的 `s_waitcnt vmcnt(N)`。修法：用 asm volatile 的 v_mov 在原位置截断生命周期，保留原来的访存位置。
- **R40**：深度饱和（每 CU 多个 CTA）时，夹在两批访存之间的 VALU 起着控制发射节奏的作用，拿掉它会让访存变密、争用加重。所以要按并发度分开测量，必要时保留原实例。
- **R41**：重新构建会改变 code object 的大小，进而改变设备内存的分配位置。机器码没变、但受带宽限制的 kernel 可能因此波动 2–8%。判定只看被改动的 kernel，并跑 5 轮以上。
