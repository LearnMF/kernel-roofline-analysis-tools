# 成段融合的整体设计与容量测算（2026-10-16，生产版 P-77b，bw46）

目标：把账目（`../kda-bytes-ledger-20261016`）里“同一段按 chunk 并行的计算被拆成多个 kernel 后产生的交接”（约 1.9 GB，约占实测字节的 37%）留在片上。递推是硬边界（R48），融合只能在两个递推之间的同一段内进行。

## 1. 分段与段内交接（16K/12，MB 为写 + 所有读）

| 段 | kernel | 段内交接（可融合） | 跨段 / 跨递推（不可融合） |
|---|---|---|---|
| F（前向） | prep_a → prep_b → [递推 fwd_h_o] | R（fp32）+ Kb 往返约 222 MB，实测约 265 MB | Wn/Kn/Un/QgA/AqkA/Gn → 递推 457 |
| B0 | head_gate → wu (+gn_kp) → [递推 R1：fwd_h_bn] | 无（g 的消费方 wu 和 s4 不在同一段） | g（fp32）→ wu、s4：302；wu → R1/R2/s4：705（其中 Wb 是 Wn 的副本，101） |
| B1 | dav → [递推 R2：dhu] | 无 | dVn、dOT → dhu：202；dAqk → s4：101 |
| B2 | s4a → s4b → tail (+reduce) | s4a → s4b 的 dA/dwT/db_part，加上 h 被读两遍，约 300；**s4b → tail 的 fp32 dq/dk/dg：604** | 递推的输出 → s4：654 |

## 2. 容量现状（生产版 ISA 元数据，gfx936：每 CU 64 KB LDS，每个 SIMD 每个 lane 512 个 VGPR）

| kernel | VGPR | LDS | 每 CU 的 CTA 数（256 线程） | 卡在哪一项 |
|---|---:|---:|---:|---|
| s4b | **236** | 26.9 KB | 2 | VGPR（≤256）和 LDS（≤32 KB）都接近上限 |
| s4a | 144–152 | 30.5–32 KB | 2 | LDS |
| bwd_tail | 111 | 20 KB | 3 | |
| prep_a | 154 | 21.5 KB | 3 | LDS（3 × 21.5 ≤ 64 KB） |
| prep_b | 71 | — | | |
| wu | 213 | 17 KB | 2 | VGPR |

每个 chunk·head 在 B2 段的工作集：h 和 dh 各 32 KB（bf16），dq/dk/dg 合计 96 KB（fp32），再加 A 表格 16–48 KB，总量远远超过单个 CU 的 64 KB LDS。

## 5. 结论
- **多出来的字节是系统性的，根源是容量不匹配**：chunkwise 算法每个 chunk·head 的工作集（B2 段约 180–200 KB）远大于 gfx936 每个 CU 的片上容量。拆成多个 kernel，正是为了在每 CU 2–3 个 CTA 的占用下掩盖访存延迟；任何一对融合都要降到每 CU 1 个 CTA，而降占用的代价（s4b +27%、prep +53%）与省下的字节相当，甚至更大。
- **要真正打开这块空间，前提有两个**：
  1. **对占用不敏感的 kernel 设计**：让每个 CU 只放 1 个 CTA 时也能掩盖延迟，比如单个 wave 同时推进两轮 kt、预取更深一层、由 MMAC 主导的长链。s4b+tail 的盈亏平衡点，是 s4b 在每 CU 1 个 CTA 时的代价从 +355 µs 降到约 +150 µs 以下。
  2. **改算法以减小工作集**：例如 F8 块内算法，替换显式的 T⁻¹ 及其反向，可以去掉 dA/dwT 表格；或者改变 chunk 大小。属于 B 类或研究性工作。
- 跨递推的交接（约 1.9 GB）由算法写法决定，需要改算法才能动（见 `../kda-ir-20261013` §3.2）。

## 6. 方案 a，第一步：让 s4b 在每 CU 1 个 CTA 时也能掩盖延迟（P-79，2026-10-16，bw46 HCU1）

**s4b 在每 CU 1 个和 2 个 CTA 时的 SQTT 对比**（`s4b_occ1.txt` / `s4b_occ2.txt`）：

| | 每 CU 2 个 CTA | 每 CU 1 个 CTA |
|---|---:|---:|
| 每个 wave 的周期 | 100.9K | 61.8K |
| 每个 CTA 实际摊到的周期（2 个 CTA 并行，所以按一半算） | 50.4K | 61.8K（+22.6%） |
| 其中发射 / 访存等待 / 发射受阻 / 屏障（每个 wave） | 25.1K / 35.8K / 29.2K / 10.8K | 25.1K / 19.0K / 13.3K / 4.4K |

要达到盈亏平衡（1 CTA/CU 的代价不超过 +150 µs），每个 CTA 需要降到约 56.2K 周期，也就是少掉约 15% 的停顿周期。每个 CTA 光发射就要 25.1K 周期，这部分省不掉。

**P-79**（`examples/kda/p79_s4b_ot.py`，模板参数 OT，`KDA_G2_S4B_OT`）：
- OT=1：每轮 kt 先发 gv、gn、kk、qq，再发 dwv，最后发 kt+2 的 h/dh 预取；
- OT=2：在 OT=1 的基础上，kt+1 的 gv/gn/kk/qq/dwv 改在第 kt 轮、它们最后一次被用之后就发出（复用同一组寄存器，避免 R56 的循环拷贝），VGPR 由 236 增到 251，没有用 scratch。
- 结果全部逐位一致，但耗时没有变化：

| wy_s4_split | OT=0 | OT=1 | OT=2 |
|---|---:|---:|---:|
| 16K/12，每 CU 2 个 CTA | 1915.0 µs | 0.996 | 0.995 |
| 16K/12，每 CU 1 个 CTA | 2297.3 µs | 0.999 | 1.003 |
| 16K/48，每 CU 2 个 CTA | 8984.3 µs | 0.996 | 0.998 |
| 16K/48，每 CU 1 个 CTA | 10018.1 µs | 1.002 | 1.002 |

**结论**：只改读的顺序、提前一轮预取，都解决不了每 CU 1 个 CTA 时的问题。每轮 kt 那次显存等待，不是因为读发得晚，而是那一轮的读写字节和依赖链本身就要这么长。要想恢复，只能让两轮 kt 真正重叠执行（软件流水，表格双缓冲以去掉屏障）。
