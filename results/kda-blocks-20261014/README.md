任务说明：`docs/tasks/kda_blocks_task.md`，由主 agent 执行。代码在 `examples/kda/blocks/`，测量机器是 bw52（BW1000），原始输出在 `raw/`。

**时钟**：负载下实测 shader 时钟为 **1.50 GHz**（`clk_probe.hip`：s_memtime 计数与 hipEvent 墙钟时间对比）。s_memrealtime 的频率是 25 MHz，不是 100 MHz。

## 1. 全局访存（`vmem_bench.hip`，540 个点）
- **参数网格**：每 lane 2/4/8/16 B × 每条 wave 指令覆盖 1/2/4/8/16/32/64 行 × 行距 3/6/12/24/48 KB × 数据来源（L2：4 MB 工作集；显存：1 GB） × 读 / 写 × 访问方式（scatter：相邻指令相距很远；stream：相邻指令访问下一组行）。另有 rowvec16（16 行，每行 4 个 lane 读同一个 4 B）和 uniform（整个 wave 读同一地址）两种特殊模式。
- **ISA 已核对**：循环体内恰好是 8 条目标宽度的 global_load/store（dword/x2/x4/ushort）。

### 主要结论
1. **数据在 L2 里时，TA 代价主要由一条指令覆盖的行数（缓存行数）决定，与每 lane 的宽度基本无关**：

   | 每条指令覆盖的行数 | 读（周期/条/CU） | 写 |
   |---|---:|---:|
   | 1 行（256 B–1 KB，连续） | 12–22 | 15–59 |
   | 4 行 | 10–28 | 13–61 |
   | 16 行 | 41–44 | 51–58 |
   | 32 行 | 77–89 | 104–120 |
   | 64 行 | 165–178 | 227–241 |

   连续读取时：16 B/lane 是 22，8 B/lane 是 21，4 B/lane 是 12，2 B/lane 是 13。
2. **数据来自显存时，代价主要由显存带宽决定，按实际取回的缓存行字节数计**：
   - 1 KB 连续读：99.5 周期，约 1.23 TB/s，接近 1.34 TB/s 的峰值；
   - 16 行 × 64 B：171–208 周期，每行只用到半个 128 B 缓存行，相当于取回 2 KB；
   - 写：1 KB 连续写 111 周期（约 1.1 TB/s，即写峰值）；部分缓存行的写非常贵，64 行 × 4 B 在小行距下要 1500 周期以上（与 R10 一致）。

   所以模型应拆成两项资源：**TA 发射**（用 L2 表）+ **显存流量**（按缓存行粒度计算真正需要取回的字节，再除以带宽）。显存一列的实测值用来核对这个组合。
3. **与旧 TA 表的冲突已经查清**：
   - 16 行 × 64 B：显存 171–208，与旧表的 169 一致（另一个 agent 测的 97 偏低，像是命中了 L2）；
   - 16 行 × 32 B：显存 103–175，旧表是 85。旧表的微基准里，相邻 wave 的地址区间相互重叠，部分数据命中 L2，所以偏低。
4. **tail 的 TA 差额可以解释了**：tail 每条指令只读写一行，数据全部来自显存。按显存一列的代价（512 B 读 49、256 B 读 29、256 B 写约 35、rstd 的 rowvec16 约 100、beta 64 行约 600）逐项相加，每 wave 约 6100 周期，**与实测的 5907–6155 吻合**。说明 PMC 的 TA busy 里包含了因显存带宽而被反压的时间。指令条数 148 与 195 的差距仍未解决。

## 2. LDS 与 barrier（`lds_bench.hip`）
- **单条指令，无冲突时（周期/条/CU）**：
  - ds_read_b32：3.1；b64：5.1；b128：8.1（126 B/周期，接近 128 B/周期的峰值）；read2_b32：8.1；u16：4.7；
  - ds_write_b32：4.7；b64：8.0；b128：10.3；
  - ds_bpermute：6.4。
- **冲突**：每多一路冲突，代价线性增加（b32：2 路 4、4 路 8、8 路 16、16 路 32、32 路 64）。
- **延迟**：相互依赖的 ds_read_b32 约 89 周期。
- **一次 LDS 交换**（写 → barrier → 读 → barrier，W=4，每 CU 1 个 CTA）：每 wave 1 KB 时 281 周期，16 KB 时 1958 周期，约为 160 周期 + 每 KB 约 113 周期。每 CU 放 2–3 个 CTA 时更慢（见原始数据）。
- **s_barrier 本身**：4 个 wave 57 周期，8 个 65 周期，16 个 94 周期。到达时间不齐时，代价约等于最晚到达的 wave 的延迟。

## 4. 递推单步：ISA 级顺序发射模拟器（`isa_sim.py`）

**输入**：
- 循环体：生产二进制在稳态下实际执行的一步指令序列，用 `sq_loop.py` 从 SQTT 记录中抽出，见 `raw/sqtt_bodies/`。用 `hipcc -S` 另外编译的 ISA 与生产 .so 不同，不能用。
- 每个实例的访存特性 `hbm_frac` = 体检卡的 HBM 读字节 / 循环读取的总字节。这是描述访存行为的输入，不是拟合常数。

**代价参数全部来自本库的微基准**：

| 机制 | 参数 | 来源 |
|---|---|---|
| MMAC 累加链（srcC 转发） | 10.5 周期 | `mmac_dep_bench`（直线代码） |
| MMAC 结果交给 VALU 读取 | 约 30 周期（读后再送回 MMAC 一轮 38.5） | 同上 |
| 每条指令的发射占用 | 4 周期 | SQTT 中 clks=4 |
| VMEM / LDS 发射队列 | 每 wave 16 条，满了之后按单元的接收速率发射 | `issue_burst_bench`（SQTT） |
| dwordx4 读的 TA 接收 | 30 周期（每 CU 2 个 wave，低并发）；32 个 wave 饱和时为 22 | 同上 / `vmem_bench` |
| 单个 wave 的 LDS 速率 | ds_read2_b64 16 周期，ds_write_b16 8 周期 | 同上 |
| 读完成延迟 | L2 386、HBM 588 周期（预热后）；写 430 周期 | `vmem_compl_bench` |
| LDS | 各指令的占用见 `lds_bench`；完成延迟 80 周期 | `lds_bench` |

**重要发现**：
1. 之前测的“MMAC 依赖延迟 47.6 周期”是微基准循环边界造成的假象。生产代码里累加到同一寄存器的相邻 MMAC 只间隔 8–16 周期发射。
2. VMEM 的在途指令数**没有硬上限**：单个 wave 连发 32 条读都不会被卡住。实际机制是每个 wave 约 16 条的发射队列，满了之后按 TA 的接收速率放行。
3. `vmem_compl_bench` 的第一次运行受冷启动影响，读延迟测成 930–1030 周期；预热后是 386（L2）/ 588（HBM）。
4. 4 个 wave 以上同时开 SQTT 时，发射时间会被量化成整齐的 32 或 64 周期，所以突发测试以 1–2 个 wave 的数据为准。

**验收**（`validate.md` 第 1 节，**4 个实例都在 ±20% 以内**）：

| 实例 | 模拟 | 实测 | 误差 |
|---|---:|---:|---:|
| 前向 MODE 1 | 2.087 µs/步 | 2.571 | −19% |
| 重算 MODE 4 | 2.009 | 1.966 | +2% |
| dhu 8-wave | 2.132 | 2.564 | −17% |
| dhu 4-wave（P-24 限流，每 CU 1 个 CTA，3 轮） | 2.517 | 3.031 | −17% |

**仍有系统性偏低**：4 个里有 3 个低 17–19%。说明还有没建模的开销，可能的方向：标量指令和分支的真实代价、VALU 双发射的限制、TA 在混合访问模式下的接收速率。用这个模拟器给新设计定价时，**比较相对差值比看绝对值可靠**，绝对值大约要乘 1.2。

第二版合成 kernel（`rec_step_gen`）作为独立检验集，尚未用模拟器复核。

## 7. 交叉验证（`validate.md`）

1. **递推单步**：4 个实例 −19% / +2% / −17% / −17%，**达标**。
2. **bwd_tail 的 TA**：按访问盘点 × 库代价（数据全部来自 HBM）计算，16K/12 预测 6209、实测 5907（+5%），16K/48 预测 5768、实测 6155（−6%），**达标**。指令条数仍是 148 对 195（PMC），差距没有查清。s4b、dav、wu 的访问盘点还没做完，留待布局盘点任务。

1. **峰值点**（`stream_peak.hip`，最优流式访问，原始数据 `raw/stream_peak_and_tail_count.txt`）：

   机器文件里的 1339 GB/s 和 6.1 TB/s 是 kra calibrate 用专门优化过的 kernel 测出来的。本库的访问模式能达到 0.91–0.92，**HBM 读和 L2 读这两项按 ±10% 算通过，按 ±5% 不通过**，如实记录。
2. **bwd_tail 的指令条数**：SQTT 记录的动态指令数是每 wave **148.8 条**（读 100.0、写 48.8），与源码盘点的 148.2 一致。**是 PMC 的 vmem 字段多计了约 46 条**；数量与 48.8 条 dword 写接近，推测是这类写被重复计数（未证实）。
3. **模拟器的两处参数修正**（都来自本库的实测）：
   - **s_barrier 本身只要 10 / 16 / 45 周期**（4 / 8 / 16 个 wave）。原来的 57 / 65 / 94 里包含了约 47–51 周期的循环开销；rec_step_gen 中空的一步 51 周期，加两个 barrier 后是 64 周期，可以印证。
   - **ds_write_b16 每条发射占 8 周期**：突发测试显示，单个 wave 从第一条开始就是 8 周期一条，没有排队的好处。

   修正后 4 个递推实例的误差为 **−18% / +2% / −17% / −17%**（`validate.md`），仍在 ±20% 以内。

   **系统性偏低的原因**有一部分在“实测”这一侧：
   - 体检卡的每步时间 = 整个 kernel 时间 / 步数，由最慢的 CTA 决定，还包含开头几步缓存冷的阶段；
   - 模拟器模拟的是一个典型 CTA 的稳态；
   - SQTT 实测的稳态步长（MODE 1：2.27–2.54 µs）比体检卡的 2.57 低 1–13%。

   相对 SQTT 稳态，模拟器误差为 −8% 到 −17%。
4. **独立检验集**（第二版合成 kernel 32 个配置，用同一个二进制的 ISA 模拟，`synth_check.md`）：
   - **18 个在 ±20% 以内，误差中位数 15%**（barrier 修正后的数字）。
   - 只有 MMAC、VALU 或 LDS 一种操作的配置，以及按生产指令构成配置的 fwd1 系列，误差都在 ±12% 以内。

## 9. 构造式模型：“从零”推算生产 kernel（`derive11.py` → `derive11.md`）

**输入只有三类，没有任何被预测 kernel 的实测时间**：
- **结构**：生产二进制的指令流。按 chunk 并行的 kernel 用一个 CTA 各 wave 的完整动态轨迹（`cta_trace.py`，从 SQTT 抽取，见 `raw/cta_traces/`）；递推用一步的稳态循环体。
- **启动几何与驻留数**：CTA 数，以及每 CU 同时驻留的 CTA 数。
- **访存特性**：hbm_frac = HBM 读字节 / 读取的总字节。

**模型**：`trace_sim.py` 在一个 CU 上模拟 res 个同时驻留的 CTA；一个 CTA 结束后立即补上下一个，直到跑完这个 CU 分到的 ceil(CTA 数 / 80) 个 CTA。代价规则和参数与 `isa_sim.py` 完全相同，都来自本库。递推用 `isa_sim.py`，再乘以步数和轮数。

**结果**：

| kernel | 16K/12 误差 | 16K/48 误差 |
|---|---:|---:|
| fwd_prep_a | +7% | +11% |
| fwd_prep_b | −17% | −21% |
| l2n_apply | +16% | +15% |
| gate | **+40%** | **+43%** |
| wu | +3% | +1% |
| dav | −9% | −4% |
| wy_s4a | −16% | **−34%** |
| wy_s4b | −21% | **−34%** |
| bwd_tail | −3% | −4% |
| 前向 MODE 1 | −18% | — |
| 重算 MODE 4 | +2% | — |
| dhu（16K/12 为 8-wave，16K/48 为 4-wave） | −17% | −17% |
| **各 kernel 之和** | **−8%**（5973 对 6504 µs） | **−14%**（19086 对 22203 µs） |

22 个 kernel × 形态点中，**16 个在 ±20% 以内，18 个在 ±30% 以内**。任务要求“现有 kernel 从零推算误差 ±20–30%”，**基本达到**。

**已知的薄弱点**：
1. **TA 代价目前只按指令宽度取值，没有区分访问模式和行距**：s4a、s4b 到了 16K/48 偏低 34%。它们有大量 16 行 × 32–64 B 的分片访问，行距随 H 增大 4 倍，vmem_bench 显示这类模式在显存中的代价随行距从 171 涨到 208；prep_b 偏低也属于这一类。改进方法：把 `kda_layout.py` 按源码推出的每条访问的模式，接到模拟器的 TA 代价上（来源 R47）。
2. **gate 偏高 40%**：这是一个 VALU 和超越函数密集的 kernel，可能高估了超越函数的发射代价，或者 VALU 在 wave 之间能并行的程度。需要用 SQTT 按类别对照。

**结论**：构造式模型已经足以支撑下一步（全局布局求解，以及运算内部重设计的定价），前提是**比较相对差值**，并且对依赖分片访问模式的 kernel（s4a、s4b、prep_b）**先补上按访问模式计价的 TA 代价**。


## 10. 模型细化（进行中）

1. **驻留数输入改为按资源计算**。体检卡的 `resident` 字段对 LDS 用量小的 kernel 一律截在 3，与实际不符。按 VGPR 预算（每 SIMD 768，依据 R38）、每 SIMD 最多 10 个 wave、每 CU 64 KB LDS 重新计算后：gate 是 8，bwd_tail 是 6，l2n_apply 是 10。

   **SQTT 印证了这一点**：用实测 kernel 时间除以单个 CTA 的时长，倒推出的轮数对应 gate 约 7.3、tail 约 6.2 个同时驻留的 CTA。

   修正后：l2n_apply 由 +16% / +15% 变为 +9% / +8%，tail 由 −3% / −4% 变为 −7% / −15%（`derive11.md`）。
2. **gate 仍偏高 37–40%**。SQTT 显示它主要卡在 VALU 发射上：每 wave 约 33K 周期的发射等待，相当于每个 SIMD 上 8 个 wave 争用 VALU。如果超越函数单元不占用 SIMD 的 VALU 发射口，gate 的误差会降到 +22%，但 prep_a、tail 会变为 −9%、−12%。为此写了一个混合微基准（`trans_mix.hip`），结果自相矛盾：一半 wave 闲着时时间不变，说明 wave 到 SIMD 的映射和驻留数都不受控，**这组数据作废**，需要重新设计后再定。
3. **s4a、s4b 在 16K/48 偏低 34%**：
   - 实测从 16K/12 到 16K/48，耗时增加 4.6–5.0 倍（工作量只多 4 倍）；模拟器只给出 3.9 倍。
   - 两个形态的 hbm_frac 都是 0.82。行距效应也解释不了：16 行模式在 6 KB 和 24 KB 行距下的显存代价基本相同（206 对 207）。
   - 更可能的原因是**高并发下零碎访问让显存的有效带宽下降**，模拟器按峰值带宽平均分给各 CU，没有这个效应。

   下一步：用 vmem_bench 测“全部 80 个 CU 同时做 16 行 × 32–64 B 访问”时显存的实际带宽，把它作为一个独立构件，对应的就是按访问模式计价的显存代价。


## 11. 全局布局求解：第一轮（`layout_eval.py`）——模型尚不足以给候选排序

**第 2 步：访问盘点**。只盘点影响 s4b 侧候选的 4 个张量 g、kn/qn、dA、dAqk，生产方和其他消费方的访问模式都从源码推出：
- gate 写 g：每条 1 行 × 256 B（每 lane 4 B）；wu 读 g：2 行 × 512 B；
- l2n_apply 写 kn/qn：1 行 × 512 B；wu 读 kn/qn：2 行 × 256 B；tail 读 kn/qn：1 行 × 256 B，带固定顺序的行归约；
- dav 写 dAqk：4 行 × 256 B；s4a 写 dA：16 行 × 64 B。

s4b 每个 wave 的 VMEM 指令序列已经与源码一一对应：序言为 aa、dak/aqA、转置读取、ado、avn、h/dh 暂存；每个 kt 步依次是 dwT、gv、gn、h、dh、kk、qq，再加 3 条写。

**第 3 步：定价**。`trace_sim` 增加了逐条指令的 TA 代价覆盖：每条指令按自己的访问模式取 vmem_bench L2 表中的值，再对 4 个候选（把对应张量改成 s4b 的原生片段布局）计算 6 个 kernel 的时间变化。

**结果：4 个候选的变化都是 0.0 µs，模型分辨不出差异。** 两个原因：
1. **模拟器里 s4b 被显存带宽卡住**：每个 CU 固定分到 1/80 的带宽，而 s4b 的 hbm_frac 是 0.82。在 hbm_frac=0.82 时，TA 代价怎么改，结果都是 1007.7 µs；全部 TA 代价乘 3 才会变化。而实测中 s4b 只用了约 55% 的显存带宽，受延迟限制。“每 CU 固定份额、串行排队”的显存模型对突发型 kernel 不成立：实际上一个 CU 可以临时用到超过平均份额的带宽。
2. **小改动下响应不单调**：hbm_frac=0 时，kn/qn 改为原生布局后 TA 更便宜，时间反而从 845 µs 增加到 1034 µs，是调度顺序的副作用。小差值不可信。

**结论**：构造式模型目前能把现有 kernel 的绝对时间推算到 ±20–30%，**但对 s4b 这类“只改访问模式、不改字节数”的布局候选还没有分辨力**，全局布局求解要等模型补上以下两点：
- 显存改为全局共享资源，带排队和突发能力，取代每 CU 固定份额。需要一个新构件：单个 CU 在其他 CU 空闲时与全部 CU 都忙时，各自能拿到多少显存带宽。
- 对小改动做多次带随机扰动的模拟，取统计值，消除调度顺序带来的不单调。


## 12. 新构件：每个 CU 能拿到的显存带宽随活跃 CU 数的变化（`hbm_cu_bench.hip`，第一版）

原始数据：`raw/hbm_cu_v1.txt`。

**可用的结果**（16 行 × 64 B 分片读，每 CU 4 个 wave，即 s4b 一个 CTA 的规模）：
- 活跃 CU 从 1 个增加到 32 个，每 CU 都稳定在 16–17 GB/s；48 个时 14.8，80 个时 13.3 GB/s。
- 也就是说，每 CU 4 个 wave 时，单个 CU 的显存吞吐主要受**在途请求数和延迟**限制，约 11 B/周期，与“峰值带宽平分给 80 个 CU”的份额（11.2 B/周期）相当，到全部 80 个 CU 都活跃时才明显下降。

**本版不可用的数据**：
1. 每 CU 16 个 wave（block 1024）的结果无效：kernel 声明的 `__launch_bounds__(256)` 小于 1024，启动被拒，打印的数字没有意义。
2. 连续 1 KB 读在 80 个 CU 时总带宽只有约 208 GB/s，显然偏低：各 wave 的起始地址相隔 7 MB 的整数倍，低位相同，都落在同一个显存通道上（partition camping），是微基准的问题。

**对模拟器的含义**：“每 CU 固定 1/80 份额”的上限数值本身是对的，问题出在 s4b 在模拟器里的显存需求和排队方式：
- 读和写共用一个串行队列；
- hbm_frac 是按指令字节、整个 kernel 平均计算的。

下一步要先核对 s4b 在模拟器里的显存繁忙率与实测（约 55%）为什么不一致，再决定显存模型怎么改。


### 12.1 s4b 在模拟器里的显存需求与实测吻合，缺的是别的延迟

| 形态 | 实测：显存繁忙率 → 显存时间 | 模拟器：每 CU 的显存时间 / 总时间 |
|---|---|---|
| 16K/12 | 60%（读 0.66 GB、写 0.31 GB，共 1283 µs）→ 约 770 µs | 785 µs / 1008 µs（78%） |
| 16K/48 | 53%（读 2.66 GB、写 1.23 GB，共 5898 µs）→ 约 3130 µs | 3103 µs / 3903 µs（80%） |

**显存需求本身是对的**：模拟器算出的显存时间与实测几乎相同。问题在于模拟器少算了约 20%（16K/48 约 34%）的其他延迟，于是总时间变短，显存看起来就成了瓶颈，TA 代价的变化被掩盖。实测中显存只忙 53–60%，真正起限制作用的是延迟。4 个递推实例也一致偏低 17–19%，说明这是一个共同的漏项。

**最可能的漏项**：负载下的访存延迟。本库的读延迟（L2 386、HBM 588 周期）是在 GPU 空闲、每 CU 只有 1 个 wave 时测的。显存繁忙 50–60% 时，L2 和 DRAM 里有排队，延迟会明显变长。受延迟限制的 kernel（s4b、递推）对此最敏感；而且 16K/48 时总流量更大，延迟可能更长，这与 s4a/s4b 在 16K/48 的超线性变慢方向一致。

**下一步的构件**：测“访存延迟随显存负载的变化”。一部分 CU 做指针追逐测延迟，其余 CU 产生 0–100% 峰值的背景流量。模拟器改为按 kernel 自身的显存繁忙率取延迟，并迭代到自洽。之后重跑 derive11 和 layout_eval。
