## 1. 全局访存（`vmem_bench.hip`，540 个点）
- **参数网格**：每 lane 2/4/8/16 B × 每条 wave 指令覆盖 1/2/4/8/16/32/64 行 × 行距 3/6/12/24/48 KB × 数据来源（L2：4 MB 工作集；显存：1 GB） × 读 / 写 × 访问方式（scatter：相邻指令相距很远；stream：相邻指令访问下一组行）。另有 rowvec16（16 行，每行 4 个 lane 读同一个 4 B）和 uniform（整个 wave 读同一地址）两种特殊模式。
- **ISA 已核对**：循环体内恰好是 8 条目标宽度的 global_load/store（dword/x2/x4/ushort）。

### 主要结论
1. **数据在 L2 里时，TA 代价主要由一条指令覆盖的行数（缓存行数）决定，与每 lane 的宽度基本无关**：

   | 每条指令覆盖的行数 | 读（周期/条/CU） | 写 |
   |---|---:|---:|
   | 1 行（256 B–1 KB，连续） | 12–22 | 15–59 |
   | 4 行 | 10–28 | 13–61 |
   | 16 行 | 41–44 | 51–58 |
   | 32 行 | 77–89 | 104–120 |
   | 64 行 | 165–178 | 227–241 |

   连续读取时：16 B/lane 是 22，8 B/lane 是 21，4 B/lane 是 12，2 B/lane 是 13。
2. **数据来自显存时，代价主要由显存带宽决定，按实际取回的缓存行字节数计**：
   - 1 KB 连续读：99.5 周期，约 1.23 TB/s，接近 1.34 TB/s 的峰值；
   - 16 行 × 64 B：171–208 周期，每行只用到半个 128 B 缓存行，相当于取回 2 KB；
   - 写：1 KB 连续写 111 周期（约 1.1 TB/s，即写峰值）；部分缓存行的写非常贵，64 行 × 4 B 在小行距下要 1500 周期以上（与 R10 一致）。

   所以模型应拆成两项资源：**TA 发射**（用 L2 表）+ **显存流量**（按缓存行粒度计算真正需要取回的字节，再除以带宽）。显存一列的实测值用来核对这个组合。
3. **与旧 TA 表的冲突已经查清**：
   - 16 行 × 64 B：显存 171–208，与旧表的 169 一致（另一个 agent 测的 97 偏低，像是命中了 L2）；
   - 16 行 × 32 B：显存 103–175，旧表是 85。旧表的微基准里，相邻 wave 的地址区间相互重叠，部分数据命中 L2，所以偏低。
4. **tail 的 TA 差额可以解释了**：tail 每条指令只读写一行，数据全部来自显存。按显存一列的代价（512 B 读 49、256 B 读 29、256 B 写约 35、rstd 的 rowvec16 约 100、beta 64 行约 600）逐项相加，每 wave 约 6100 周期，**与实测的 5907–6155 吻合**。说明 PMC 的 TA busy 里包含了因显存带宽而被反压的时间。指令条数 148 与 195 的差距仍未解决。

## 2. LDS 与 barrier（`lds_bench.hip`）
- **单条指令，无冲突时（周期/条/CU）**：
  - ds_read_b32：3.1；b64：5.1；b128：8.1（126 B/周期，接近 128 B/周期的峰值）；read2_b32：8.1；u16：4.7；
  - ds_write_b32：4.7；b64：8.0；b128：10.3；
  - ds_bpermute：6.4。
- **冲突**：每多一路冲突，代价线性增加（b32：2 路 4、4 路 8、8 路 16、16 路 32、32 路 64）。
- **延迟**：相互依赖的 ds_read_b32 约 89 周期。
- **一次 LDS 交换**（写 → barrier → 读 → barrier，W=4，每 CU 1 个 CTA）：每 wave 1 KB 时 281 周期，16 KB 时 1958 周期，约为 160 周期 + 每 KB 约 113 周期。每 CU 放 2–3 个 CTA 时更慢（见原始数据）。
- **s_barrier 本身**：4 个 wave 57 周期，8 个 65 周期，16 个 94 周期。到达时间不齐时，代价约等于最晚到达的 wave 的延迟。

## 4. 递推单步（进行中）

### 第一版（作废）
`rec_step_bench.hip` 用运行期计数的循环，空的一步就要 1.05 µs，还出现了 scratch。原始数据：`raw/rec_step_bench_v1_runtime_params.txt`。

### 第二版：编译期生成（`rec_step_gen.py` → `rec_step_gen.hip`）
每个配置单独实例化成直线代码，没有 scratch，空的一步 51 周期。原始数据：`raw/rec_step_gen_v2.txt`。

**按生产主循环的指令构成配置的复刻点**（每 CU 1 个 CTA）：

| 复刻点 | 合成 kernel（µs/步） | 生产实测（µs/步） | 误差 |
|---|---:|---:|---:|
| 前向 MODE 1 | 2.71 | 2.57（16K/12） | +5% |
| 重算 MODE 4 | 2.62 | 1.96 | +34% |
| dhu 8-wave | 3.27 | 2.56 | +28% |
| dhu 4-wave | 4.06 | 约 3.0（16K/48，每 CU 1 个 CTA、3 轮） | +34% |

**单因素扫描不单调，不能直接拿来建可加模型**：
- 以 fwd1 为基准，减少 VALU（fwd1_v-）反而从 2.7 µs 变成 6.2 µs；
- 去掉全部全局读（fwd1_ld0）变成 5.6 µs；
- 单独测全局读时（ld8、ld16），读取被编译器当作死代码删掉了，违反 R43。

原因：这些合成 kernel 的步时间主要由**编译器排出的指令顺序**决定。MMAC 是普通 builtin，可以被编译器挪动；VALU 和 LDS 用的是 asm volatile，不能挪。同样的指令条数，排法不同，依赖延迟暴露的程度就完全不同（MMAC 依赖延迟 47.6 周期，LDS 89 周期，VMEM 700–900 周期）。这与 R46 是同一个现象：TP8 下的递推单步受延迟和调度限制，**只按指令条数做加法的模型本身就不成立**。

### 方向调整
递推单步的构件模型改为 **ISA 级的顺序发射模拟器**：
- 输入：一个循环体的 ISA。生产 kernel 直接用编译结果；新设计先写骨架，编译后拿到 ISA。
- 模拟：按 wave 顺序发射，用本库测得的各类指令的发射代价和延迟，s_waitcnt 计数器语义、MMAC/VALU 的寄存器依赖、barrier 同步，推算每一步的时间。
- 验收：4 个生产递推实例的单步时间误差在 ±20% 以内。

合成 kernel 保留，作为模拟器的独立检验集：先把它对“读取被删”的处理修好，再用模拟器预测这些合成 kernel 的时间。
