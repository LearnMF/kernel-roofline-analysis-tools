# 方案 A：前向“prep 尾部 ∥ 递推”跨 stream 流水（2026-10-15，bw46，**不合入**）

## 实现（全部逐位一致）
- **P-70**（`examples/kda/p70_fwd_pipe.py`）：新增绑定 `fwd_pipe`，用 `KDA_G2_PIPE=1` 开启，只覆盖 dense 前向。
  - 主 stream 先算前 NT−k 个 chunk 的 prep，记录事件 E；
  - 递推放在 side stream，等到 E 后启动；
  - 尾部 k 个 chunk 的 prep 与递推并发执行。prep_b 每完成一个 (chunk, head)，就以 release 语义写入 `flag[i·H+hh]`；递推预取第 i ≥ NT−k 个 chunk 之前，以 acquire（agent 作用域）读取该标志，必要时自旋等待。
  - 逐位门禁 10/10；k 取 1、8、64、127 也都逐位一致。
- **P-70b**（`p70b_cumask.py`）：用 `hipExtStreamCreateWithCUMask` 划分 CU，递推用 48 个，尾部 prep 用其余 32 个。
- **P-70c**（`p70c_tailcm.py`）：尾部 prep 改为按 chunk 优先的顺序派发。

## Wall 时间（`pipe_time.py`，同一进程内交替开关；括号里是 流水前 → 流水后）
| 版本 | 16K/12 前向 | 64K/12 前向 |
|---|---|---|
| P-70：不划分 CU | 0.73–0.86x | 0.67–0.82x |
| P-70b：CU 划分 48/32 | 0.87–0.98x（k=48 时为 1780→1827） | **1.01–1.03x**（k=192 时为 5733→5563） |
| P-70c：尾部按 chunk 优先 | 0.91–0.94x | 0.92–0.95x |

trace（`p70tr.sh`）显示的情况：
- **P-70**：尾部 prep 的 CTA 被派到递推所在的 CU 上，递推从 518 µs 涨到 1021 µs；按 chunk 优先派发的 prep 本身也变慢，prep_a 慢 20%，prep_b 慢 63%。
- **P-70b（k=48）**：递推从 518 µs 涨到 629 µs，原因是 head 11 的 CTA 要等尾部 prep 全部做完；另外，跨 stream 的交接在开头留下 32 µs 空隙，在结尾留下 57 µs 空隙。

## C-4：只看资源争用的上限（`conc_mask.py`，不加标志、两个任务互不依赖）
| 16K/12 | 时间 |
|---|---|
| 递推，全部 80 个 CU | 512 µs |
| 递推，只用 48 个 CU | 500 µs |
| prep，全部 80 个 CU | 1010 µs |
| prep，只用 32 个 CU | 2059 µs（是 80 CU 时的 2.04 倍） |
| 两者同时跑，各用自己的分区 | 递推 575 µs（+15%），prep 2091 µs |

64K/12 上，递推单独跑 1690 µs，与 prep 同时跑时为 2015 µs（+19%）。每次跨 stream 交接约有 40–50 µs 的空隙。

## 结论
- **可以省下的上限**：递推跑的那段时间里，32 个 CU 只能完成 R/2.04 那么多“全 GPU 等效”的 prep 工作（16K/12 约 282 µs）。从中还要扣掉两项：递推因争用变慢 15–19%（16K/12 约 75 µs），以及交接空隙 40–90 µs。在不出现等待的前提下，16K/12 实际能省约 0–100 µs，64K/12 约 170–500 µs。
- **实测**：16K/12 为负；64K/12 最好快 3%（170 µs），但前向加反向合计几乎没有变化。
- **判定**：用多条 stream 做跨 kernel 流水，在 gfx936 上受三件事限制：32 个 CU 跑生产方会慢一倍、HBM/L2 争用、stream 交接延迟。**它解决不了 TP8 下 CU 用不满的问题，不合入**，代码保留为默认关闭的探针。
- **还没有测的**：反向几对 kernel 并发的上限（重算 ∥ wu 尾部、dhu ∥ s4b 逆序）。dhu 本身受 VMEM 发射吞吐限制，争用对它的影响预计更大。
