# (b) fp32 中间结果改窄格式交接：精度摸底（2026-10-13）

**方法**（hq_emulate.py）：
- 生产版 g2_r5（bw7）上的所有 kernel 原样不动，只在 Python 层的交接点，对指定张量做一次 RNE 舍入（fp32 → bf16 或 fp16 → fp32）。这与“生产方写窄格式、消费方读入后扩回 fp32”完全等价。
- 用 bclass_gate.sh 对照冻结的 FP64 oracle，每个变体跑 17 组配对：k3 与 extreme 门控各 6 个种子，再加 5 个长序列或多 head 的固定配置。生产版和 FLA 用的是同一组输入。

## 结果（候选 / 生产版的 rms_ratio 几何平均；括号内为候选 / FLA 的中位数）

| 变体 | 省下的字节（每 token·head，读+写） | dq | dk | dg_raw | A_log | dt_bias | 规则 2 | 规则 3b |
|---|---:|---:|---:|---:|---:|---:|---|---|
| dq/dk/dg → bf16 | 1.5 KB | 1.064 | 1.051 | **2.007**（1.74） | **1.487**（1.45） | **3.278**（2.63） | FAIL | **FAIL**（比 FLA 差得多） |
| dq/dk/dg → fp16 | 1.5 KB | 1.0010 | 1.0008 | 1.023（0.88） | 1.004 | 1.082（0.86） | FAIL | 通过 |
| dAqk → bf16 | 0.5 KB | 1.020 | 1.012 | 1.013（0.87） | 1.032 | 1.009 | FAIL | 通过 |

- o、dv、dbeta 不受影响（1.000）。
- **g（门控 cumsum）没有测，事先排除**：它是 log2 尺度的累加值，|g| 可达数百。bf16 在 |g|≈256 处的 ulp 是 2；fp16 在 256–512 区间的 ulp 是 0.25，经 exp2 放大后，误差至少约 19%。

## 结论

1. **dq/dk/dg 用 bf16：不可行。** dg 要沿 64 行逆序累加，dt_bias 和 A_log 又要把所有 token 加起来，bf16 的舍入误差被系统性地放大，误差达到生产版的 2–3.3 倍，也比 FLA 差 1.5–2.6 倍。
2. **dq/dk/dg 用 fp16 / dAqk 用 bf16：违反规则 2，但满足规则 3b。** 误差比生产版差 0.1–8%，仍比 FLA 好 12–20%。
   - 生产版在 g_raw 和 dt_bias 上比 FLA 精度更高，这部分余量可以换成速度。
   - 但这意味着把验收线从“不差于生产版”放宽到“不差于 FLA”，需要用户决定。
   - fp16 还有动态范围风险：真实 bf16 训练不做 loss scaling，梯度可能小到 1e-6 到 1e-8，落到 fp16 的非规格化区甚至下溢。合成输入的 oracle 测不出这一点。要用的话，必须加按 tile 的缩放。
3. **性能收益本身也小。** 涉及的 kernel（s4b、收尾、dav）受 TA 或指令发射限制：窄格式让字节减半，但读写指令条数不变。估算：dAqk 用 bf16 约 0.5%，dq/dk 用 fp16（dg 保持 fp32）约 1%，合计不到 TP2 的 1.5%，远低于原先“5–10%”的估计。那个估计只按字节算，正是 R36 指出的漏项。

**判定**：(b) 不值得做。即使放宽到规则 3b，也只能换来约 1.5%，还要承担 fp16 下溢的风险。
