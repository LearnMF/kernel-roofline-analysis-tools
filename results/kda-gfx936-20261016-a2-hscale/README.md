# A2 关键路径复测 + “dhu 是否受显存带宽限制”的验证（2026-10-16，bw46 HCU6/7，生产版 P-65）

## 1. 规模扫描：T 固定为 16384，H 取 12–40（`hscale.sh`，dhu 强制同一个 v8b<1,true> 实例）

| H（CTA 数） | dhu | 前向递推 | 重算递推 |
|---|---:|---:|---:|
| 12（48） | 667 µs | 520 µs | 441 µs |
| 16（64） | 769 µs | 583 µs | 494 µs |
| 20（80） | 862 µs | 668 µs | 562 µs |
| 24（96，16 个 CU 各跑 2 个 CTA） | 1322 µs | 966 µs | 876 µs |
| 32（128） | 1681 µs | 1108 µs | 1084 µs |
| 40（160） | 2294 µs | 1371 µs | 1422 µs |

两种假设的预测：
- **只受各 CU 自身限制**：H ≤ 20 时每个 CU 只有一个 CTA，时间应该不变；
- **受 HBM 带宽限制**：时间应与 H 成正比，H=20 时 dhu 约 1112 µs。

**实测介于两者之间**：从 48 个 CTA 到 80 个，工作量增加 67%，三个递推的时间都只多了 28–29%。按 404 MB × 20/12 ÷ 862 µs 估算，H=20 时 HBM 带宽约 781 GB/s，只占峰值的 58%。

## 2. 同一 kernel 在 H=12 与 H=20 下的每步周期（SQTT，cp_step）

| kernel | 每步周期 H=12 → H=20 | 增加的部分（都是 VMEM 项） | 时间之比 ÷ 周期之比 |
|---|---|---|---:|
| dhu | 3510 → 4229（+20%） | 读受阻 +325，写受阻 +420，其余不变 | 1.07 |
| 前向递推 | 2678 → 3106（+16%） | 读受阻 +387，其余不变 | 1.10 |
| 重算递推 | 2238 → 2733（+22%） | 读延迟 312 → 1557 | 1.05 |

**结论**：
- **不是 HBM 带宽不足**：到 80 个 CTA 时，HBM 也只用了 58%。
- **也不是各 CU 互不影响**：这一点修正了我上一条回答中“只受每个 CU 自身在途请求数限制”的说法。活跃 CU 从 48 个增加到 80 个，每个 CTA 每步的访存等待增加 300–1250 周期，增量全部在 VMEM 项上，其它项不变。也就是说，**访存延迟随全卡流量上升**，L2、互连、HBM 的排队都会让延迟变长。递推每一步都要等访存结果，所以对这种延迟增加最敏感。
- **还有 5–10% 来自时钟**：时间之比除以周期之比为 1.05–1.10，说明活跃 CU 变多时，核心频率大约降了 5–10%（推断，没有直接读取频率）。
- **对“给每个头切 8 个 V-slab”这个想法**：CTA 变多会让访存延迟升高、频率下降，所以每个 CTA 的工作减半并不能换来线性加速。这与 C-3 在前向上的结果一致（96 个 CTA 时，16K/12 快 6.5%，64K/12 慢 3%）。**判定：这个方向收益很小，不做探针。**

## 3. A2：前向与重算递推的新最大项（H=12，`cp_a2_d2.txt` / `cp_a2_d3.txt`）

**前向**，每步 2678 周期：
- VALU 677（bf16 舍入 288、mov 72、pk_fma 70）；
- LDS 读延迟 493：GEMM1 的 16 个 hB 片段一次发出后，第一条读要等 244 周期；o pass 读 vB 约 250 周期；
- VMEM 读受阻 488：K 预取在发射前等 177 周期；
- MMAC 323。

**重算**，每步 2238 周期：
- VALU 626；
- VMEM 读延迟 312，其中 306 来自步中位置 112 的那条预取读（loadU(nxt)）；
- MMAC 292、LDS 读 194、SALU 191。

**备选探针**：
- (a) 前向：hB 的批量读拆成两批，前一半在屏障 A 之前就能发出的部分先发（需要确认依赖关系），减少屏障后第一次读的等待；
- (b) 重算：找出为什么 loadU(nxt) 会在同一步内被等待（可能是 vmcnt 的计数顺序问题，参见 R52），把它往前挪或加固定调度屏障；
- (c) 前向：K 预取的发射受阻。

## 4. Megatron 调用链里 KDA 收到的 cu_seqlens（2026-10-16 核实代码，`verified`）
- **Megatron-LM-das** `4097af5`（HYGON-AI），`pretrain_gpt.py`：只有 batch 里带 `cu_seqlens` 时才会构造 `PackedSeqParams`。3rdparty Megatron-LM `571370c82`（core_r0.18.0）中，只有 `training/datasets/sft_dataset.py` 和 `core/datasets/data_schedule.py` 会产出 cu_seqlens；预训练用的 `GPTDataset` 和 `MockGPTDataset` 都不产出。
- **Megatron-Bridge** `05fd6df97`，`kimi_k3_layers.py::_forward_kda`：`cu_seqlens = packed_seq_params.cu_seqlens_q if packed_seq_params is not None else None`，再经 `kimi_k3_ops.kda` 传给 `chunk_kda(cu_seqlens=…)`。
- **结论**：
  - **预训练**：每张卡、每个 micro-batch 只有 **1 段**，长度就是 seq_length；batch 维等于 micro_batch_size，长上下文时通常为 1。TP8 下 H=12，每个递推只有 48 个 CTA，CU 闲置的情况在真实预训练里同样存在，不是基准测试的偶然现象。`--reset-attention-mask` 只影响 softmax attention 的掩码，不会把文档边界传给 KDA，所以 KDA 的状态会跨文档延续。
  - **SFT**：样本打包，段数等于每个 pack 里的样本数，取决于数据集，`unknown`。
  - Moonshot 内部实际怎么训练 K3、CP>1 时 KDA 怎么处理：`unknown`。

## 5. KDA 训练在 BW1000 上的算术强度（来自 kda_bound，C=64、d=128，P1 显存策略）
- 算法必需量（每 token·head）：MMAC 504 kFLOP；显存读 2576 B、写 1548 B，合计 4124 B。所以**算术强度 ≈ 122 FLOP/B**。
- 机器的屋脊点：bf16 MMAC 476 TFLOPS ÷ HBM 约 1.25 TB/s（读 1339、写 1100）≈ **380 FLOP/B**。
- 16K/TP8 的算法下限：访存 0.65 ms，MMAC 约 0.21 ms，前者是后者的 3 倍。算法本身就是**受访存限制**的：即使字节降到必需量、80 个 CU 全部用上，MMAC 利用率最多也只有约 122/380 ≈ 32%。必需字节主要是每个 token 都要读写的输入、输出和梯度（q/k/v/g/o/do/dq/dk/dv/dg），加大 chunk 也减不掉。要进入受算力限制的区间，算术强度至少要提高约 3 倍，现有算法做不到。
