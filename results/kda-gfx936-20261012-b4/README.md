# B4 第 1 步：s4b 融合收尾 kernel（P-45 / 45b / 45c，B 类）：数值通过，但变慢，被否决（2026-10-12）

## 实现

`examples/kda/p45_s4bt.py`（+ `p45b_s4bt_late_loads.py`、`p45c_s4bt_epi_dots.py`），用 `KDA_G2_S4BT=1` 开启。在生产版 s4b（4 个 wave、每个 CU 2 个 CTA）的 TAIL 实例里做三件事：

1. **dg 不再写回显存**，在循环内完成：
   - wave 内用 4 步 shfl 做逆序前缀和；
   - 每个 wave 的块和放进 TA 表的填充行（第 64–67 行，表本身从不读写这几行）；
   - 跨块的进位等到每轮末尾已有的 barrier 之后再读；
   - 按 FLA 的运算顺序做门控反向，写出 bf16 的 dg_raw；
   - 按 (wave, 列) 和 (wave, CTA) 写出部分和。
2. **l2norm 反向**放在循环之后：读回本线程写出的 dq/dk 和 qn/kn，输出 bf16 的 dq/dk。
3. **db 直接输出**；最后用一个固定顺序的小 kernel 归约部分和，得到 dA_log 和 ddt_bias。

## 数值：通过

同一份构建里，比较融合路径和原路径的输出（4 个配置：dense 8K/12、gate-extreme、16K/48、varlen）：

- o、dv、dbeta：逐位一致。
- dq/dk：0.002% 的元素差 1 个 bf16 最低位。
- dg：约 1% 的元素差 1 个最低位（逆序前缀和的结合顺序变了）。
- dA_log：相对差约 1e-6。
- ddt_bias：bf16 最低位翻转。
- gate-extreme 配置下，dg、dA_log、ddt_bias 也逐位一致。

## 性能：变慢

| 16K/TP8 | s4b + 收尾 + 归约（µs） |
|---|---:|
| 原路径 | 1303 + 698 + 14 = **2015** |
| P-45（256 VGPR，scratch 52 / 88 B） | 2439 + 49 = 2488 |
| P-45c（scratch 12 / 76 B） | 2239 + 50 = **2289** |

fwd+bwd 墙钟（P-45）：0.936 倍（16K/TP8）、0.942 倍（16K/TP2）、0.932 倍（32K/TP4）、0.930 倍（64K/TP8）。

## 原因：s4b 受 VMEM 指令发射（TA）限制，而不是受字节限制

- **瓶颈在 VMEM 发射**：waterlevel 显示 s4b 的 VMEM 发射利用率为 70–73%，显存带宽只有 55%。融合省下的是字节（dg 的一次往返），但往 kernel 里加的是 VMEM 指令。
- **循环内多出 VMEM 指令**：每轮 kt 多了 g_raw、dt_bias 的读和分散的 ddt 部分和写，每个 wave 每轮多 5 条，比原来多约 50%。
- **收尾段的读回模式很差**：每个 lane 读 16 行 × 64 B，每条指令要碰 16 条 cache line。收尾 kernel 自己是一行 512 B 连续读，效率高得多。
- **寄存器溢出**：生产版 s4b 已经用到 236 / 253 个 VGPR，加上收尾逻辑后达到 256 并开始溢出到 scratch。

## 模型漏项（按 1.3.4：先查模型）

`kda_bound.py` 和 `design_eval.py` 只算了访存、VALU、矩阵乘和递推延迟链，**漏掉了 VMEM 指令发射（TA）这一项**，而它恰恰是 s4a、s4b、dhu、递推、dav 等 kernel 实际的瓶颈（61–88%）。设计评估里“按字节估算融合收益”的前提，对受 TA 限制的 kernel 不成立。

2. 把 TA 这一项加进模型；
3. 用修正后的模型重新评估 B4 和 R。
