# Phase A：前向按时间分段流水（P-41）——结果逐位一致，但变慢，方案被证伪（2026-10-12）

## 假设

前向准备（prep_a、prep_b，chunk 之间完全并行）和前向递推（fwd_h_v8o4，只有 H × 4 个 CTA，受延迟限制）放到两个 stream 上，按 chunk 区间流水：递推处理区间 j 时，准备同时处理区间 j+1。递推每段从上一段的 fp32 寄存器状态接着算（状态镜像不做任何变换），所以输出逐位一致。

**依据**：`overlap_probe.py` 让两个 kernel 处理互不相关的数据、在两个 stream 上并发：

| 形态 | 递推被隐藏的比例 |
|---|---:|
| 16K/TP8 | 41% |
| 32K/TP4 | 32% |
| 64K/TP8 | 55% |
| 16K/TP2 | 0% |

## 实现

`examples/kda/p41_fwd_pipe.py`，在构建好的树上用 `KDA_G2_FPIPE=<段数>` 打开。改动包括：
- 递推 kernel 支持 chunk 区间，并能读入、写出状态；
- 准备 kernel 支持 chunk 偏移；
- 新增启动函数和绑定：`fwd_prep_rng`、`fwd_h_o_rng`；
- Python 侧的 `g2_ops.fwd_pipe` 负责两个 stream 的编排。

**门禁**：已跑的 4 组全部逐位一致，含极端门控。

## 结果（墙钟时间，CUDA events，进程交替运行，每侧 4 个进程）

| 形态 | 前向：生产版 → 分 4 段流水 | 前向 + 反向 |
|---|---|---:|
| 16K/TP8 | 1.925 → 2.191 ms（0.88 倍） | 0.965 倍 |
| 16K/TP4 | 3.206 → 3.721 ms（0.86 倍） | 0.964 倍 |
| 32K/TP8 | 3.433 → 3.579 ms（0.96 倍） | 0.987 倍 |
| 32K/TP4 | 5.971 → 6.694 ms（0.89 倍） | 0.972 倍 |
| 64K/TP8 | 6.421 → 6.727 ms（0.95 倍） | 0.989 倍 |

分 2 段时：16K/TP8 为 0.885 倍，32K/TP4 为 0.937 倍。

## 原因（hipprof 时间线，16K/TP8）

1. **和准备 kernel 共用 CU 时，处在关键路径上的递推慢了约 2.2 倍**：四段分别耗时 456、410、361、186 µs，合计 1413 µs；不分段时只要 681 µs。
   - 给递推设 `s_setprio(3)`，并用高优先级 stream，四段变为 377、445、319、186 µs，前向结束时间 1674 µs（不分段为 1663 µs），基本没有改善。
   - 准备 kernel 共用 CU 时也变慢了：prep_a 四段合计 894 µs，不分段为 631 µs。
2. **分段本身就有开销**：同样分 4 段但只用一个 stream（不做并发），16K/TP8 的前向就多了 0.40 ms，来自多出的 launch 和 Python 开销、每段启动时的状态读入，以及每段 CTA 数变少带来的尾部效应。
   - 两个 stream 并发比一个 stream 分段只省 0.14 ms，抵不过分段开销。

## 教训（规则 R35）

- 用互不相关的数据做的并发探针，会高估流水能省下的时间：它测不到“关键路径上的 kernel 被共用 CU 的 kernel 拖慢”这件事。
- 在 gfx936 上，一个受延迟限制的递推和一个吃满整卡的并行 kernel 共用 CU 时，递推会被拖慢约 2 倍，wave 优先级和队列优先级都几乎无效。
- 带依赖的流水要先测“关键路径上的 kernel 在并发时的耗时”，再决定是否投入。
- 反向的结构相同：dhu 和 fwd_h#2 是关键路径上的递推，与 s4、tail 并发同样会被拖慢。没有新的证据之前，不在反向上投入 Phase A。
