# KDA 前向 + 反向的第一性原理下限模型（第一版，2026-10-12）

工具：`examples/kda/kda_bound.py`。模型只看算法本身，不依赖任何 kernel 拆分。完整表格见 `bounds_P1.md`、`bounds_P2.md`。

## 模型

| 项 | 怎么算 |
|---|---|
| 访存 | 必须读写的显存字节 ÷ 实测读、写带宽 |
| 矩阵乘 | 算法所需的矩阵乘 FLOPs ÷ 矩阵乘峰值 |
| VALU + 超越函数 | 逐元素运算量 ÷ VALU 吞吐（fp32 有一半可成对执行）+ 超越函数次数 ÷ exp2 吞吐 |
| 递推延迟链 | 串行遍数 × chunk 数 × 每步最小延迟 |

- **下限**：四项完全重叠时取最大值；“区间上沿”是吞吐项中的最大值加上延迟链。
- **显存策略 P1**（与 hip_kda、FLA 默认一致）：前向保存 rstd、Aqk、T；反向多跑一遍递推来重算状态，共 3 遍串行。
- **显存策略 P2**：前向额外保存 bf16 的 chunk 状态 h（每 token·head 多 512 B，总量与 FLA 默认的 1032 B 持平），共 2 遍串行。

**每个 token·head 的工作量**（P1，C=64，d=128）：

| 项 | 数量 |
|---|---:|
| 矩阵乘 | 504 kFLOP（前向 141，反向 281，重算 82） |
| VALU 运算 | 12.5K 次 |
| 超越函数 | 1.5K 次 |
| 显存读 / 写 | 2576 B / 1548 B |

## 第一版结论（P1）

| 形态 | BW 下限（瓶颈项） | H20 下限（瓶颈项） | A800 下限（瓶颈项） | ours / BW 下限 | FLA@H20 / H20 下限 | FLA@A800 / A800 下限 |
|---|---|---|---|---:|---:|---:|
| 16K/TP2 | 2.62 ms（访存） | 2.86 ms（矩阵乘） | 1.83 ms（访存） | 10.1 倍 | 6.4 倍 | 14.4 倍 |
| 16K/TP8 | 0.65 ms（访存） | 0.72 ms（矩阵乘） | 0.46 ms（延迟链*） | 10.3 倍 | 7.2 倍 | 16.2 倍 |
| 64K/TP8 | 2.62 ms（访存） | 2.86 ms（矩阵乘） | 1.84 ms（延迟链*） | 9.3 倍 | 7.1 倍 | 15.9 倍 |

\* NV 机器的每步延迟暂按 0.6 µs 估计，尚未测量。

1. **三个实现离各自的下限都有 6–16 倍**：照搬 FLA 的拆分方式，无论在哪台机器上都远离极限。
2. **原理上 BW 能赢 H20**：H20 矩阵乘只有 138 TF，到极限时受矩阵乘限制，下限比 BW 高约 10%。
3. **A800 的下限比 BW 低约 1.4 倍**：两者到极限都受访存限制，A800 带宽更高。要赢 A800，只能靠我们的实现比 FLA@A800 更接近各自的下限。目前我们是 10 倍，它是 14–16 倍，所以现在我们在部分形态上领先。

## 差距拆解（16K/TP8 和 16K/TP2，按 kra 采到的每个 kernel 计数器）

| 资源 | 实际执行（每 token·head） | 算法必需 | 多出 |
|---|---:|---:|---:|
| 显存字节 | 25.8–26.7 KB | 4.1 KB | **6.3–6.5 倍** |
| VALU 运算 | 84–85K 次（可能含矩阵乘指令，见待验证 4） | 12.5K + 1.5K 次超越函数 | **约 6 倍** |
| 矩阵乘 | 503 GFLOP（16K/12） | 108 GFLOP | **4.7 倍** |

**以 16K/TP8 为例，从下限到实测的逐层分解**：

| 层 | 时间 | 倍数 | 原因 |
|---|---:|---:|---|
| 下限 | 0.65 ms | | 访存 |
| 现有字节按 100% 带宽搬运 | 3.9 ms | ×6.0 | 多余的字节：中间张量、布局副本、重复读取，来自拆分方式 |
| 实测 | 6.8 ms | ×1.74 | 执行效率：平均只用到峰值带宽的约 57%（受发射、延迟、递推的并行度限制） |

**VALU 也是一个必须控制的量**：现在执行的 VALU 按 BW 的吞吐需要约 2.15 ms（16K/TP8），已经是访存下限的 3 倍。新设计只消掉多余的字节还不够：VALU 不同时降 3–4 倍，就会成为新的瓶颈（约 2 ms）。多出来的 VALU 主要来自：门控和衰减 exp 在多个 kernel 里重复计算、布局转换和转置、64 位地址运算、Kahan 补偿求和，以及累加器清零等。

## 待验证（模型本身有没有漏项）

1. **VALU 和超越函数的算法量目前是粗估**：safe gate 子块参考点需要的额外 exp、反向链式求导的逐元素量，都要逐项精确计数。
2. **BW 的递推每步延迟**：解析估计 0.40 µs，需要写一个最小状态更新的微基准来测；NV 机器取 0.6 µs，也只是估计值。
3. **小分块、带掩码时矩阵乘实际能达到的峰值比例**。
4. **valu_insts 是否把矩阵乘指令也算进去**：如果算进去，每个 token·head 约 20K 次，扣除后 VALU 多出的倍数约 4.6 倍。

## 四项核实（2026-10-12，模型已按结果更新）

| 项 | 方法 | 结果 | 对模型的影响 |
|---|---|---|---|
| 4. 计数器口径 | kra 在 gfx936 上用已知工作量的 kernel 标定过：`SQ_INSTS_VALU` 也计入矩阵乘指令；`SQ_ACTIVE_INST_VALU` 中，VALU 每条记 1 个发射槽，16×16×16 矩阵乘记 2 个，超越函数记 4 个 | 扣除矩阵乘指令（3 亿 FLOP 按 16×16×16 或 16×16×8 两种口径换算），16K/TP8 实际执行的纯 VALU 为每 token·head 44–64K 次 | VALU 多出的倍数修正为 **3.1–4.6 倍**（原来写的 6 倍偏高）。按 BW 的吞吐，这些 VALU 仍需 1.1–1.6 ms，高于访存下限，所以新方案仍须把 VALU 降约 2 倍 |
| 3. 小分块矩阵乘的可达峰值 | `bound_microbench.hip` 中的 k_mmac_tile：4 个 wave，沿用 KDA 的分块方式 | 每个 SIMD 至少 2 个 wave、一个操作数常驻寄存器时（GEMM1 的形式）：**436–452 TF**（峰值的 0.92–0.95）。两个操作数都从 LDS 读：231–237 TF（0.49）。每个 SIMD 只有 1 个 wave：341–349 TF | 矩阵乘一项乘以效率 0.92。对 BW 仍不是瓶颈 |
| 2. 递推单步延迟 | k_step：v8o4 的依赖结构，循环内不访问显存，每个 CU 1 个 CTA | 前向（含 o）**1.23 µs/步**，只更新状态（重算 / dh）**1.00 µs/步**。每个 CU 2 个 CTA 时为 1.2 / 1.86 µs，CTA 再多就转为受吞吐限制 | 原来 0.40 µs 的解析估计漏了 LDS 往返、barrier，以及每个 SIMD 只有 1 个 wave 时矩阵乘的依赖延迟，属于模型漏项。修正后 **BW 在 TP8 时受递推延迟链限制**（16K/TP8 为 0.83 ms，大于访存的 0.65 ms）。生产版每步 2.1–2.66 µs，是这个下限的 1.7–2.2 倍 |
| 1. VALU / 超越函数的算法量 | 按 safe gate 的分解方式重新逐项估算：每个元素在前向约需 4 次 exp（相对子块参考点、相对 chunk 起点、chunk 末端衰减）加门控的 2 次；反向按链式法则逐元素计数 | 约 **12.2K 次 VALU + 1.54K 次超越函数**，与原估计（12.5K + 1.5K）基本一致 | 不变。在 BW 上不是瓶颈（16K/TP8 为 0.40 ms） |

## 修正后的结论（P1）

| 形态 | BW 下限（瓶颈项） | H20 下限（瓶颈项） | A800 下限（瓶颈项） | ours / BW 下限 | FLA@H20 / H20 下限 | FLA@A800 / A800 下限 |
|---|---|---|---|---:|---:|---:|
| 16K/TP2 | 2.62 ms（访存） | 3.18 ms（矩阵乘） | 1.83 ms（访存） | 10.1 倍 | 5.8 倍 | 14.4 倍 |
| 16K/TP4 | 1.31 ms（访存） | 1.59 ms（矩阵乘） | 0.92 ms（访存） | 10.0 倍 | 6.1 倍 | 14.5 倍 |
| 16K/TP8 | **0.83 ms（递推延迟链）** | 0.80 ms（矩阵乘） | 0.69 ms（递推延迟链*） | 8.2 倍 | 6.5 倍 | 10.8 倍 |
| 64K/TP8 | 3.31 ms（递推延迟链） | 3.18 ms（矩阵乘） | 2.76 ms（递推延迟链*） | 7.4 倍 | 6.4 倍 | 10.6 倍 |

\* NV 机器的递推每步延迟仍是估计值。

- **TP4/TP2**：到极限时 BW 的下限比 H20 低 18–21%，原理上能赢。
- **TP8**：两者的下限基本相同（0.83 对 0.80）。BW 卡在递推延迟链上，所以要在 TP8 赢 H20，**必须缩短递推延迟链**，有三种办法：
  - **P2 显存策略**：前向保存状态 h，省掉一遍串行，16K/TP8 的延迟链从 0.83 ms 降到 0.57 ms，显存仍在 FLA 默认的预算内；
  - **加大 chunk**：chunk 改为 128，串行步数减半；
  - **加快单步**：缩短每一步的依赖链。
- **新方案的量化目标**：字节不超过必需量的约 2 倍，VALU 不超过约 2 倍，串行 2 遍、每步约 1 µs。

## 补上 VMEM 指令发射（TA）一项（2026-10-12，起因见 R36 / P-45）

`ta_microbench.hip` 测出每条 wave 级 VMEM 指令占用的 CU 周期数（BW，数据分别在 L2 内 / 显存中）：

| 访问模式 | 读 | 写 | KDA 中的例子 |
|---|---:|---:|---|
| 每个 lane 16 B，64 个 lane 连续（1 KB） | 17 / 21 | 56 / 56 | 生产版里很少用 |
| 每个 lane 8 B，连续（512 B） | 16 / 22 | 28 / 28 | 原生布局的分片读（Wn/Kn…） |
| 每个 lane 4 B，连续 | 10 / 10 | — | |
| 每个 lane 16 B，4 行 × 256 B | 17 / 43 | 56 / 56 | 按行分块的 16 B 访问 |
| **每个 lane 16 B，16 行 × 64 B** | **64 / 169** | 64 / 67 | s4b 的 dq/dk/dg、g 分块 |
| **每个 lane 8 B，16 行 × 32 B** | **64 / 85** | 64 / 67 | s4b 的 k/q 分块、P-45 收尾段读回 |
| 每个 lane 4 B，64 行 × 4 B（gather） | 158 / 229 | — | s4b 开头的 akB/aqB |

### 结论

1. **MMAC 分片式访问代价高**：16 行 × 32–64 B 这种访问，每个字节的 TA 代价是行连续访问的 4–8 倍，数据在显存中时更明显。
2. **写比读贵**：即使是连续访问，写的代价也约为读的 2.6 倍。
3. **理论下限不受影响**：用最优访问模式搬运必需的字节，TA 在 16K/TP8 只需 0.23 ms（16K/TP2 为 0.90 ms），都低于访存一项（0.65 / 2.62 ms）。
4. **现有 kernel 中，TA 是很大一部分的实际瓶颈**：每个 kernel 的下限要加上“实测 TA 忙碌时间 ÷ 0.92”，即使所有 kernel 都以 100% 效率执行，也不能低于这个值。
   - TA 成为瓶颈的 kernel：TP8 时为 s4b、dhu、prep_b；TP2 时为 s4b、s4a、dhu、两个递推和 prep_b。
   - s4b 离自身下限的距离因此从 1.51 倍降到 1.32 倍（TP8），说明现有拆分下局部优化的空间比原来以为的还小。

### 新架构的设计规则

1. **全局访存用行连续模式**：每个 lane 16 B，每行连续段不少于 256 B；转换成 MMAC 分片的工作放在 LDS 里做（LDS 带宽 15 TB/s）。
2. **尽量少写**：连续访问时，写的代价也约为读的 2.6 倍。
3. **融合 kernel 要明确列出 VMEM 指令预算**：每个阶段用几条指令、什么访问模式，同时给出 VGPR 和 LDS 预算。P-45 失败的原因，正是沿用了 s4b 的分片式访问模式、寄存器已经顶到上限，又额外增加了 VMEM 指令。

### 对候选方案的重新评估

- **B4**：仍然是最大的一块（16K/TP8 预测 −2.2 ms，TP2 预测 −10 ms），但前提是按上面的规则重新设计一个 kernel；不能在 s4b 上嫁接。
- **R（递推流水化）**：TP8 时递推受延迟限制，R 有效；TP2 时 fwd_h_bn 的 TA 主要花在写出状态和 v_new 上，R 的收益要打折扣。

## chunk 128 的递推单步微基准（2026-10-13，bound_microbench.hip 中的 k_step128）

同样的依赖结构，循环内不访问显存，序列长度 T 相同（chunk 64 时 NT=256，chunk 128 时 NT=128）：

| CTA 数 | 只更新状态：每步 µs | 一遍串行 ms | 含 o：每步 µs | 一遍串行 ms |
|---|---|---|---|---|
| 48（TP8，每 CU 1 个） | 1.014 → 1.614（1.59 倍） | 0.260 → 0.207（**−20%**） | 1.241 → 2.105（1.70 倍） | 0.318 → 0.269（**−15%**） |
| 192（TP2，每 CU 2.4 个） | 1.729 → 3.311（1.92 倍） | 0.443 → 0.424（**−4%**） | 2.557 → 4.536（1.77 倍） | 0.655 → 0.581（**−11%**） |

**结论**：
- chunk 加倍后，每一步的工作量也翻倍；递推本身又受指令发射限制，所以每步耗时变成原来的 1.6–1.9 倍。
- 步数减半带来的净收益：TP8 只有 15–20%，TP2 只有 4–11%。

|---|---:|---:|---|

## chunk 32 的递推单步微基准（2026-10-13，k_step32）

同样的依赖结构，序列长度 T 相同：chunk 64 时 NT=256，chunk 32 时 NT=512。

| CTA 数 | 只更新状态 | 含 o |
|---|---|---|
| 48（TP8） | 每步 1.015 → 0.702 µs（0.69 倍）；**一遍串行 0.260 → 0.360 ms（+38%）** | 每步 1.242 → 0.937 µs（0.75 倍）；**0.318 → 0.480 ms（+51%）** |
| 192（TP2） | 每步 1.729 → 1.250 µs；**0.443 → 0.640 ms（+44%）** | 每步 2.556 → 1.452 µs；**0.654 → 0.743 ms（+14%）** |

**为什么每一遍串行都变长**：每一步里有一块固定开销，包括 barrier、LDS 往返、h 的转换和写回（h 是 d×BV，与 C 无关），这块开销约 0.4 µs，不随 chunk 变小而减少。步数翻倍后，每遍串行都长了 14–51%。

**换算到整个算子**：

| 项 | 16K/TP8 | 16K/TP2 |
|---|---|---|
| 三遍递推 | 约 +0.8 ms | 约 +1.5–2.5 ms |
| 状态接口字节（h/dh 每 chunk 落盘，∝ 1/C） | 从 2.56 增加到 5.12 KB/token·head，扣除块内节省后净增约 2 KB（+7.5%） | 同左 |
| 块内工作量减半 | 约 −0.4 ms | 约 −1.5–2 ms |
| **净效果** | **约 +9%** | **约 +4–9%** |

**结论**：chunk 32 在 BW1000 上前向、反向都不划算，chunk 64 仍是最优选择。

## gfx936 实际能同时驻留的 wave 数（occupancy_probe.hip）

**方法**：每个 wave 记录 HW_ID 和起止的 s_memtime，统计每个 SIMD 上同时在跑的 wave 数峰值。

**结果**：

| VGPR | 同时驻留的 wave 数（每 SIMD） |
|---|---|
| 200–256 | **3**（320/320 个 SIMD 都是如此） |
| 256，限定每 CU 1 个 CTA | 1 |
| 256，限定每 CU 2 个 CTA | 2（每个 wave 的耗时变为 1.58 倍） |

**DTK 编译器的 `; Occupancy:` 注释不可信**：它按每个 lane 256 个 VGPR 计算，只要 VGPR 超过 128 就报 1。这低估了实际硬件能力。

**规则 R38**：在 gfx936 上，每个 wave 最多 256 个 VGPR 是 ISA 上限，但每个 SIMD 能同时驻留几个 wave，不能按“256 ÷ VGPR 数”推算，必须实测。“VGPR ≤ 128 才能每 SIMD 驻留 2 个 wave”这条经验规则在 gfx936 上不成立。我们的 kernel 实际受 LDS 限制（每 CU 能放的 CTA 数 ≈ 64 KB ÷ 每个 CTA 的 LDS）。
