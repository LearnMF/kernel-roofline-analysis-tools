# KDA 前向 + 反向数据流 IR（第二阶段第 ② 步，2026-10-13）

工具：`examples/kda/kda_ir.py`。所有量都按每 token·head 计，任何形态都是 T×H 乘以同一组数字。

## 1. 结构：三层

| 层 | 内容 |
|---|---|
| 逻辑层 | 算法里的张量（39 个）和运算（18 个），与 kernel 拆分无关。每个运算标注：<br>• 并行结构：按行 / 按 chunk / 正向递推 / 反向递推 / 沿 T 归约；<br>• 递推能否按 V 切分；<br>• MAC 数（三角乘积按一半计）；<br>• 元素级运算和超越函数的数量 |
| 物化层 | 逻辑张量在显存里的一种存法：dtype + 布局（行主序 / A、B、C 形式原生片段 / bN 状态块 / aN / vB）。同一个张量的多种物化就是布局副本 |
| 拆分层 | kernel = 一组运算 + 它从显存读写的物化张量。**生产版（P-54a）是第一个实例** |

此外定义了算法写法的变体（`formulation()`），供第 ④ 步搜索使用：
- **W/U**：显式构造（生产版），或不构造（FROST 式，递推直接使用 k、v、T⁻¹ 和门控）；
- **状态**：反向重算（生产版），或前向保存（keep-state）；
- **dAqk**：由 dav 计算（生产版），或在 s4b 里重算（P-55）；
- **chunk 大小**：32 / 64 / 128。

## 2. 验证

| 项 | 结果 |
|---|---|
| 生产版拆分与 optrace 逐个 launcher 核对：16 个形态 × 10 个 launcher 的读写字节 | **最大相对误差 0.0000%**（`validate.txt`） |
| 运算量与 `kda_bound.py` 对齐：MAC、元素级运算、超越函数 | 前向、反向、重算三段完全一致（`inventory.md`）。各运算之间的元素级运算拆分是估计值，但每段总数与 kda_bound 相同 |

## 3. 第一批结论

### 3.1 生产版的中间张量流量按原因分解（`breakdown.md`，C=64）

| 原因 | 每 token·head（写 + 读） | 占比 | 说明 |
|---|---:|---:|---|
| crossing | 8464 B | 44% | 按 chunk 并行的运算与递推之间必须交接的张量；由算法写法决定，与拆分无关（下限 8224 B） |
| **handoff** | **8712 B** | **45%** | 按 chunk 并行的反向被拆成多个 kernel 后，kernel 之间的交接：<br>• g（fp32）1536 B；<br>• qn、kn 各 1024 B（各被 3 个 kernel 读）；<br>• dq、dk、dg（fp32）各 1024 B；<br>• dAqk、dA、dwT、kgB 各 512 B |
| copy | 1024 B | 5% | Wb（W 的 B 形式）、dOT（do 的 B 形式） |
| saved | 676 B | 4% | 前向留给反向的 T⁻¹、Aqk、rstd、beta |
| extra_read | 280 B | 1% | 交接张量被同一侧多个 kernel 重复读取（如 Vn 被 dav 和 s4 各读一次） |
| 合计 | 19156 B | | |

**含义**：拆分层的差距里，最大的一块不是递推与并行阶段之间的交接（那部分由算法写法决定），而是**按 chunk 并行的反向内部被拆成 l2n_apply、head_gate、wu、dav、s4a、s4b、tail 后产生的交接，占 45%**。拆成这么多 kernel，根本原因是每 CU 64 KB LDS、每 wave 256 个 VGPR 放不下整个工作集（F6）。如果按 chunk 并行的部分能在容量允许的范围内合并得更好，这部分字节就是可以省的。省下多少字节、又要付出多少指令和延迟代价，要等第 ③ 步的构造式模型来定价（R36：字节不等于时间）。

### 3.2 各种算法写法必须跨阶段交接的字节数（`crossing.md`，写 + 读）

| 写法 | C=32 | C=64 | C=128 | 递推遍数，每步依赖的乘积数 |
|---|---:|---:|---:|---|
| **生产版**：W/U 显式构造、重算 | 10176 | **8224** | 7440 | 3 遍：[4, 2, 3] |
| W/U 显式构造、keep-state | 9664 | 7712 | 6928 | 2 遍：[4, 3] |
| W-free、重算 | 11592 | 9768 | 9240 | 3 遍：[5, 3, 4] |
| W-free、keep-state | 11592 | 9768 | 9240 | 2 遍：[5, 4] |

- **W-free（FROST 式）在 gfx936 上不划算**：
  - 交接字节反而多了约 1.5 KB，因为递推要读 fp32 的 g 来现场计算衰减，还要读 kn、v、T⁻¹；
  - 每个递推每步多一个依赖的乘积，拉长了 TP8 的关键路径。

  这是第一次定量回答“不构造 W 的写法值不值得”。
- **keep-state**：少交接 512 B，少一遍递推；代价是前向要在递推链上多写数据（P-50 标定：每条写指令约 205 周期），并且要多占显存。
- **chunk 大小**：交接字节随 C 增大而减少（状态字节按 1/C 缩放），但 C×C 张量和每步的工作量都会变大。之前的单步微基准不支持 C=128 / C=32，最终要由构件库的递推单步模型来定价。

## 4. 局限
- 布局只是标签（natA / natB / natC / bN / aN / vB / row），每种布局对生产方和消费方的访问代价，要等构件库（`docs/tasks/kda_blocks_task.md`）给出。
- 变长、门控 precomputed、allow_neg_eigval 等分支没有建模。beta sigmoid、to_gn / exp2 这些小运算并入了总量，或者标注为不在 optrace 中。
- 交接字节的计算假设同一侧的消费方已经融合（每次交接按 1 写 1 读计）；实际能融合到什么程度，受容量约束限制，由第 ④ 步决定。

## 5. 下一步
第 ③ 步：构造式成本模型。构件库到手后，按 IR 的运算、物化张量和每个 kernel 的 tiling，组合出时间和 LDS/VGPR 占用。验收标准是**只用构件库“从零”推算现有 11 个 kernel 的时间，误差 ±20–30%**。

## 6. 按 chunk 并行的反向分组：容量核算（`examples/kda/kda_partition.py`）

### 做法
- **分段**：反向里按 chunk 并行的运算被两个递推隔成几段，一个 kernel 只能包含同一段里的运算（递推是硬边界，R48/C1）。
  把 dav 拆成两半后：
  - **S0**（递推之前）= {l2n、gate、wu、dav 的 dVn 部分}；
  - **S2**（两个递推之后）= {dav 的 dAqk 部分、s4a、s4b、tail}。
- **枚举**：每段按执行顺序切分成连续的 kernel，两段各 2³ 种，共 64 种分组（含生产版）。
- **每种分组算两样**：
  1. 显存交接字节：被另一个 kernel 或递推读取的张量，按 1 写 + 每个读取方 1 读计算；
  2. 每个 kernel 的片上工作集：
     ```
     LDS  = max_i（运算 i 自身的 LDS + 跨过运算 i 仍需留在片上的交接张量）
     VGPR = 同理
     ```
     其中运算自身的 LDS/VGPR 取**现在执行它的生产 kernel 的实测值**，代表现有实现的占用，不是下限。
- **交接张量在片上怎么存**，按算法结构逐条确定：
  - l2n 用保存的 rstd 在读入时现场算，不占片上空间；
  - g、dAqk、dA、dwT、dq、dk 需要整块常驻（消费方要在整块就绪后才能开始，或者要按任意行列访问）；
  - dg 可以按 kt 分块流式处理；
  - db 放在寄存器里。

### 结果（C=64）

| 分组类别 | 数量 | 说明 |
|---|---:|---|
| 放不下（LDS > 64 KB 或 VGPR > 256） | 40 | 凡是包含 s4b+tail 的都放不下：dq、dk 要整块常驻，fp32 共 64 KB |
| 放得下，但每 CU 只能放 1 个 CTA | 16 | **所有能减少交接字节的可行分组都在这一类**，例如 gate+wu（58 KB，省 512 B）、s4a+s4b（64 KB，省 1 KB，即 F6） |
| 每 CU 能放 2 个以上 CTA | 7 | **交接字节一个都没少**，只省了 launch |

**结论：在现有运算实现的占用下，按 chunk 并行的反向分组被容量锁死**。任何能省交接字节的融合，要么放不下，要么驻留数降到 1。按标定的 P1 曲线，驻留数从 2 降到 1 会让 kernel 慢 23–41%（F6、B4b 的实测结果与此一致）。

**锁死的主因是交接张量本身，不是运算实现的低效**（`partition_budget.md`）：

| 融合组 | LDS 峰值 | 其中最大运算自身的占用 | 片上交接张量 | 距每 CU 2 个 CTA 的预算（32 KB） |
|---|---:|---:|---|---:|
| gate+wu | 58.2 KB | 26.2 KB | g 32 KB | +26.2 KB |
| s4a+s4b | 64.0 KB | 32.0 KB | dwT 16 KB、dA 16 KB | +32.0 KB |
| dav(dAqk)+s4a+s4b | 80.0 KB | 32.0 KB | dAqk、dwT、dA 各 16 KB | +48.0 KB |
| s4b+tail | 104.0 KB | 32.0 KB | dq 32 KB、dk 32 KB、dg 8 KB | +72.0 KB |

C=64 时，每个 CTA 处理 64 行，fp32 的 64×128 张量就是 32 KB，比运算本身的占用还大。

### chunk 大小的作用（`partition_C32.md`）
chunk 取 32 时，每个 CTA 上的交接张量减半（64×64 的减到四分之一）：
- 到 32 KB 预算的差距缩小到：gate+wu **+10 KB**，s4a+s4b **+12 KB**，dav(dAqk)+s4a+s4b **+16 KB**。这里运算自身的占用仍按 C=64 的值计算，偏保守；C=32 时实际会更小。
- s4b+tail 仍放不下：dq、dk 还要 32 KB。

这说明 **chunk 大小和按 chunk 并行部分能否融合是耦合的**：
- C 越小，越容易融合；
- 但递推的步数翻倍，单步固定开销更突出（之前的单步微基准认为 C=32 不划算）。

FROST 选 C=16，正是站在“融合优先”的一端。这个取舍必须由构造式模型统一定价，不能分开判断。

### 对第 ④ 步搜索的含义
在 C=64、现有运算实现下，**没有容量上可行、又能减少交接的分组**。系统层面的空间只能从以下几个维度来打开，这些都要构造式模型来定价：
1. **chunk 大小与分组联合选择**：C=32 时，s4a+s4b、dAqk+s4a+s4b、gate+wu 有机会回到每 CU 2 个 CTA；
2. **重新设计运算内部，缩小自身占用**：例如 s4b 的 h/dh 暂存由双缓冲改为单缓冲（16 KB → 8 KB）、缩小块内表格；
3. **改成流式计算**：交错执行 s4a 的 pass W 和 s4b 的 kt 循环，使 dwT、dA 按块生产、按块消费，而不是整块常驻；
4. **接受每 CU 1 个 CTA 的融合**：用 P1 曲线给驻留数下降定价，与省下的字节和 launch 比较。

tail 在逐位一致的约束下不能与 s4b 融合：l2norm 反向需要整行点积完成后才能回写，dq、dk 必须整块保留。

## 7. 运算的最小片上占用，以及 C=32 能否解锁融合（`kda_partition.py --scenarios`）

### 缓冲区目录
从 `g2_wu.cuh`、`g2_dav.cuh`、`g2_wy.cuh`、`g2_bwd_tail.cuh` 中，把每个运算的 LDS 缓冲区逐个列出来，写成 chunk 大小 c 的函数。**c=64 时与 6 个生产 kernel 的实测 LDS 逐字节相同**。每个缓冲区按必要性分为四类：
- **need**：wave 之间交换数据，或布局转换必须经过 LDS。逐位一致的约束下不能用改 K 顺序的技巧（R44）。
- **cache**：可以改为从 L1/L2 重读的复用数据。
- **pipe**：双缓冲或预取级。
- **small**：标量和每行向量。

“精简版”只保留 need + small，相当于重新设计运算内部，去掉缓存和双缓冲。

| 运算 | C=64 现状 / 精简（KB） | C=32 现状 / 精简（KB） | 精简掉的部分 |
|---|---|---|---|
| wu | 26.2 / 17.8 | 11.9 / 9.6 | sA：T⁻¹ 的 LDS 缓存 |
| dav | 17.0 / 17.0 | 9.0 / 9.0 | 无（全是布局转换） |
| s4a | 29.8 / 25.8 | 13.4 / 11.4 | kgB 分块的双缓冲 |
| s4b | 32.0 / 24.0 | 24.4 / 16.4 | h/dh 暂存的第二个缓冲（h/dh 分块与 c 无关，所以 C=32 时缩小有限） |
| tail | 6.0 / 6.0 | 3.0 / 3.0 | — |

### 融合组的 LDS 峰值（括号内为每 CU 驻留的 CTA 数，0 表示放不下）

| 融合组 | 省下的交接（B/tok·head） | C=64 现状 | C=64 精简 | C=32 现状 | C=32 精简 |
|---|---:|---:|---:|---:|---:|
| gate+wu | 512 | 58.2 (1) | 49.8 (1) | 27.9 (2) | **25.6 (2)** |
| s4a+s4b | 1024 | 64.0 (1) | 57.8 (1) | 36.4 (1) | **28.4 (2)** |
| dav(dAqk)+s4a+s4b | 1536 | 80.0 (0) | 73.8 (0) | 40.4 (1) | 32.4 (1) |
| s4b+tail | 3592 | 104.0 (0) | 96.0 (0) | 60.4 (1) | 52.4 (1) |
| dav(dAqk)+s4a+s4b+tail | 5136 | 152.0 (0) | 144.0 (0) | 76.4 (0) | 68.4 (0) |

### 结论
1. **C=64 下，即使把运算内部重新设计到精简版，也没有任何能省字节的融合可以保持每 CU 2 个 CTA。** 交接张量本身（32 KB 级）就占掉了预算。
2. **C=32 + 精简版下，gate+wu 和 s4a+s4b 可以保持每 CU 2 个 CTA**（VGPR 没有建模，需另行确认），合计省 1536 B/tok·head。
3. **但 C=32 本身要多付交接**：h、dh 状态按每 token 计翻倍，按 chunk 并行的部分与递推之间必须交接的字节从 8224 增加到 10176 B/tok·head，**多 1952 B，超过了融合能省的 1536 B**。再加上递推步数翻倍（之前的单步微基准认为 C=32 不划算），C=32 在字节和串行链两方面都更差。

**所以，按 chunk 并行的反向，其分组方式在 gfx936 上无论 C=64 还是 C=32 都被锁死**：C=64 是容量，C=32 是交接字节加串行链。系统层面的收益不能指望重新分组这部分运算。

### 第 ③④ 步的重点相应调整
剩下的系统性空间在体检卡的另外两层：
1. **访问方式层（1.3–1.65 倍）**：交接张量的布局要**全局统一选择**，使生产方与所有消费方的访问代价之和最小。s4b、前向递推、s4a、tail 的 TA 放大达到 4–5 倍。P-17、P-20、P-22 只是这个问题的局部特例，全局的组合优化还没有做过。IR 的物化层已经有布局维度，构件库会给出每种访问模式的代价，两者合在一起就能求解。
2. **实现层（1.21–1.30 倍）与递推单步延迟**：要靠构件库的递推单步模型和发射模型，为运算内部重新设计（tiling、调度）定价。TP8 下串行链就是第一性下限。
