# TP8 的 CU 利用率：三组实验（2026-10-15，bw46）

**问题**：TP8、H = 12 时，三个递推（前向、重算、dhu）的网格都是 4 个 V-slab × 12 个头 = 48 个 CTA，80 个 CU 里有 32 个空着。三个递推在 16K/12 上合计约 1600 µs，约占算子的 25%。

## C-1：生产方和递推并发能不能互相掩盖（`examples/kda/conc_probe.py`）
在两条 stream 上同时发射 fwd_prep（按 chunk 并行）和 fwd_h_o（递推），两者用的是彼此独立的操作数：

| 形态 | prep 单跑 | fwdh 单跑 | 两者之和 | 先 prep 后 fwdh | 先 fwdh 后 prep |
|---|---:|---:|---:|---:|---:|
| 16K/12 | 1008 µs | 518 µs | 1526 µs | 1584（-11%） | **1363（掩盖 31%）** |
| 64K/12 | 3683 µs | 1708 µs | 5391 µs | 5913（-31%） | **4792（掩盖 35%）** |

- **先发射 prep**：它的 3072 个 CTA 会占满所有 CU，递推拿不到 CU，结果比串行还慢。
- **先发射递推**：prep 能用上空闲的 32 个 CU，能掩盖的时间大约是递推时间的 0.31–0.36。
- **再加 `s_setprio(3)` 提高递推 wave 的优先级**（`prio_patch.py`）：结果不变（1376 / 4787）。说明 prep 实际上只用上了空闲的 32 个 CU，没有挤进递推所在 CU 的剩余发射能力。
- **上限估计**：串行耗时 T = W/80 + R·(1 − 32/80)，其中 W 是 prep 的总 CU·时间，R 是递推时间。所以每个递推最多能省约 0.4R。三个递推合计，16K/12 约可省 **560–640 µs（约占算子 9–10%）**。前提是生产方和消费方按 chunk 做流水，并跨 kernel 用就绪标志同步。

## C-3：把 V 切得更细，让 CTA 数从 48 变 96（`c3_patch.py`，强制前向走 v8o4w）
- **对比方法**：两边都用 v8o4w 的旧代码（不含 P-58 到 P-65），只改 NVH，从而只看 CTA 数的影响。
- **逐位**：NVH = 1（16 列，96 个 CTA）和 NVH = 2（32 列，48 个 CTA）的输出都与生产版逐位一致。也就是说，V 怎么切是个不影响数值的自由参数。
- **时间**：16K/12 上 NVH = 1 为 643 µs、NVH = 2 为 688 µs（快 6.5%）；64K/12 上分别是 2459 µs 和 2388 µs（慢 3%）。
- **结论**：96 个 CTA 摊到 80 个 CU 上，有 16 个 CU 要跑两个 CTA，负载不均；而且切薄 V-slab 并不缩短每步的 LDS 和屏障延迟。**靠细切 V 用满 CU，收益很小。**

## P-68：dhu（8-wave v8b）把 HbN / aN 的写挪到预取读之后（不合入）
- 逐位门禁 10/10，FI=3 PASS。
- dhu 在 16K/12 上为 **0.876**，64K/12 上为 **0.883**，明显变慢。
- dhu 卡在每个 CU 的 VMEM 发射吞吐上，这时调整读写顺序的效果和前向（P-64B）相反。R52 只适用于链上时延受限的情形。

## 结论
在 TP8 上，32 个空闲 CU 的主要价值不在于让递推本身变快（C-3 已经说明这条路收益很小），而在于**让按 chunk 并行的 kernel 和递推重叠执行**（C-1），每个递推最多省约 0.4R。实现需要：
1. 生产方按 chunk-major 的顺序处理，每处理完一个 chunk 就做一次 release 写入就绪标志；
2. 递推先发射，读操作数前对标志做 acquire 自旋；
3. 前向：prep 与 fwd_h 流水；反向：wu → 重算 → dav 流水，dhu 与 s4a / s4b 按逆序流水；
4. hip_kda 和 flash-train runner 都要支持算子内部的第二条 stream（或者改成单个持久化 kernel），并从工作区里分配就绪标志。
计算内容和计算顺序都不变，所以结果仍然逐位一致。改动涉及集成契约（stream、工作区、CUDA graph 捕获），需要用户先定方案。
