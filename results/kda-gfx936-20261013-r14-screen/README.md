# 第 14 轮：消融上限筛选（2026-10-13，生产版 9cc164f，bw52）

**方法**：每个候选项先做一个只用来计时的消融（结果故意算错），测出可能收益的上限，上限够大才实现（R42）。
- 每个消融都用 `isa_loop_mix.py` 核对主循环：除了被消融的那部分，其余工作量必须与生产版相同（R43，教训见下）；
- A/B 用 ab_kernels，每边 5 个进程，带显存位置抖动；比值 = 生产版 / 消融版。

## 教训
- **R43 消融必须保持其余工作量不变**：第一版冲突消融（`fwdh_noconf` / `noconf2`）把 kb0 和 kb1 写到同一个地址。编译器于是把前一次写判为死存储删掉，又顺着删掉了 ht0 整条 GEMM2 链（每步 8 个 MMAC）。结果测出的“递推快 11–18%”全是假象；修正后的 `noconf3` 显示没有收益。所以每个消融都必须用 ISA 核对 MMAC、访存、舍入等指令数。
- **R44 MMAC 结果依赖 K 的顺序**（`mmac_kperm_probe.hip`）：在两个操作数上对 K 做同一个置换，数学上结果不变，但 838 万个输出中有 25.7% 不逐位一致，转置置换（k = q+4e ↔ 4q+e）也是 25.8%。所以“按 MMAC 寄存器布局直接生成片段、不走转置”的方案要置换 K，只能归为 B 类。

## 对“操作数在寄存器中复用 / LDS 读改宽 / 片段按 MMAC 布局生成”方案的结论
- **寄存器复用**：只有前向递推存在重复读（GEMM1 和算 o 读同一份 h），已实现为 P-53。
- **LDS 读改宽**：矩阵乘操作数已经用 `ds_read2_b64`，与 b128 指令数相同。剩下的 u16 收集，上限不到 0.3%。
- **片段按 MMAC 布局生成**：在 gfx936 上做不到逐位一致（R44）。hB/vB 经 LDS 中转是 4 个 wave 交换状态必需的。

## 判断
剩下的 A 类候选项，没有一个的上限能达到算子的 1%（舍入除外，但它做不到逐位一致）。现有拆分方式下，kernel 级的局部优化基本见顶了，这与第一性原理天花板的结论一致。再往前只有两条路：改拆分结构，或接受数值有变化的 B 类方案。
