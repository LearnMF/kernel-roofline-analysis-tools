# 生产版 P-82b 的字节账目与每个 kernel 的上限（2026-10-16，bw46 HCU1/2）

**数据**：
- `raw/<T>_<H>/`：由 `examples/kda/ceiling/collect46.sh` 采集，包括 5 次 hip-trace、pmc read/write、L2 与 SQ 的自定义计数器、optrace；
- `raw/g2_ops_hip.s`：生产版源码的 ISA，由 `isa_g2_dbg.sh` 生成；`raw/isa_mix.json`：由它统计出的指令构成。
- 账目由 `examples/kda/byte_ledger.py` 生成（新增 `--pmc-iters 4 --trace-iters 9`，因为 kda_run 默认有 3 次 warmup；并把前向 MODE 5 也归到 fwd_h_o）。
- 每个 kernel 的上限由 `examples/kda/ceiling/cards.py` 计算（`KRA_CARDS_RES` 指向本目录）。

## 1. 字节账目：与 P-65 对比

| | P-65（10-16 早） | P-82b | 变化 |
|---|---:|---:|---|
| 16K/12 实测 HBM | 5075 MB（25812 B/th，**6.26 倍**） | 4873 MB（24784 B/th，**6.01 倍**） | −202 MB |
| 16K/12 各 kernel 时间之和 | 6364 µs | 5994 µs | −5.8% |
| 16K/48 实测 HBM | 20841 MB（6.43 倍） | 20447 MB（26000 B/th，**6.30 倍**） | |

省下的字节比预期少：
- 去掉的部分：l2n_apply 203 MB，重算递推 310 MB，wu 的 P1 布局 150 MB；
- 新增的部分：前向写 h 101 MB，wu 读 h 101 MB，prep_a 写 qn/kn 101 MB。

时间降得比字节多，是因为去掉的重算递推本身受访存延迟限制，省下的时间比它的字节量对应的更多。

## 5. “非 kp 的 MODE 5 从寄存器直接写出 h”的可行性

- **kp/BP 版为什么能做到**（P-63）：kp 布局下，状态里 lane 第 m 行存的是 v = pi16(m)。selector MMAC（`c = mmac(bsel, hx, -0)`）把 k 换到行上；输出 C 片段的列位置是 q4 + 4e，正好与 pi16 相互抵消，得到 bN 需要的“4 个 v 连续”排布（4·q4 + e）。
- **非 kp 状态为什么不行**：非 kp 的状态里，lane 第 m 行存的是 v = m，列是 k = q4 + 4e（`c_col`）。selector MMAC 能把 k 换到行上（按 pi16(m) 选），但输出的 v 会落在 q4 + 4e 这种交错位置。要变成 4·q4 + e，必须先在源寄存器上做一次 16-lane 的置换（n → pi16(n)）。MMAC 只能置换行（选择器那一侧），换不了源寄存器的 lane 顺序。每个 v4bh 需要 2 次 `ds_bpermute`，每步共 8 次，再加 4 条 MMAC，这和现在走 LDS 的 bN_emit（16 次 ds_read_u16）占用的是同一条 LDS 流水，看不出能省多少。
- **等价做法**：在这些形态上改用 kp 布局。kp 布局本身就让状态里的 v 按 pi16 排列，再加上 BP 版 MODE 5。在当前生产版上实测（`sqtt/b86k.out`，同一进程内切换，全部输出与 base 逐位一致）：

| 形态 | kp + 保存 h | 只保存 h（非 kp） |
|---|---:|---:|
| 8K/48 | **1.021** | 1.014 |
| 16K/48 | **1.015** | 1.004 |
| 16K/32 | 0.995 | 0.991 |
| 8K/96 | 0.986 | 0.979 |
| 16K/96 | 0.972 | 0.966 |

**结论**：直接从寄存器写出没有便宜的办法。能拿到的收益只在 H=48 且 NT < 512（TP2 的短序列）：前向+反向快 1.5–2.1%。要实现，kp 的判定就得同时看 H 和 NT，hip_kda 里有 6 处要改（Python 的 `_kp`，C++ 的 prep、wu、fwd_v8 调度）。flash-train 没有 saved-h，不能跟着启用 kp（单开 kp 时 16K/48 为 0.994），所以这条规则得用编译宏隔开，比如只在 hip_kda 构建里打开的 `G2_KP_SHORT`。H=32 和 H=96 都是负收益，不启用。

## 6. 第三轮诊断：访存指令清点与 TA 宽度微基准（2026-10-17）

**访存指令清点**（`examples/kda/vmem_census.py`：从带 -g 的 ISA 里列出每条 global 读写的位宽、对应源代码行、是否在循环内）：
- prep_b：读 R（fp32 中间结果）用了 80 条 `dword`（`R4`：每个 lane 读 4 个相隔 256 B 的 dword）。每条指令 64 个 lane 合起来正好是 256 B 连续，已经是合并访问。
- tail：dq/dk/dg 的 fp32 读写基本都是 `dword` 或 `dwordx2`（一个 lane 对应一列，每条指令连续 256–512 B）。
- s4b：每轮 kt 用 `dwordx4` 读 g，用 `dwordx2` 读 k/q，用 `dwordx4` 写 dq/dk/dg。

**TA 宽度微基准**（`examples/kda/blocks/ta_width.hip`，bw52 HCU3）：字节数相同，比较“4 条 dword，每条连续 256 B”和“1 条 dwordx4，连续 1 KB”：
- 8 MB 数据（全部落在 L2 内）：10.72 µs 对 10.56 µs；
- 1 GB 数据：230.6 µs 对 229.6 µs；
- **两者没有差别**。

**结论**：
- 只要访问已经合并，TA 的代价只看字节数，与指令宽度无关（这把 R54 推广到了 global 读取）。
- 把 prep_b、tail 改成更宽的指令不会带来收益。
- 现在按 chunk 并行的这些 kernel 基本都受字节数和 TA 限制，剩下的等待调整顺序也只是挪位置（P-79 OT=2 已经验证）。
- 要再降，只能减少字节：
  - s4 → tail 之间 fp32 的 dq/dk/dg（604 MB）；
  - prep 和 s4a/s4b 的中间结果（约 520 MB）；
  - fp32 的 g（302 MB）。

  这几项要么受片上容量限制（P-78a/b），要么得降低精度（B 类，不允许）。

**这一轮唯一的较大收益**来自 P-84c 的连带效果：saved-h 路线变便宜了，可以推广到 H=48（P-87）。
