# 方案 A 反向部分：C-5 上限测量与 P-71“重算 → dav”消费方流水（2026-10-15，bw46，**方案 A 整体关闭**）

## C-5：反向三对 kernel 的争用上限（`conc_bwd.py`）
递推用 48 个 CU，配对 kernel 用其余 32 个 CU，两者操作数互不依赖；“上限” = 递推期间配对 kernel 能完成的全 GPU 等效工作量 − 递推因争用多出的时间，没有扣除 stream 交接开销。

| 配对 | 16K/12：递推变慢 / 上限 | 64K/12：递推变慢 / 上限 |
|---|---|---|
| 重算 ∥ wu | +15% / 211 µs | +17% / 678 µs |
| 重算 ∥ dav | +19% / 214 µs | +22% / 655 µs |
| dhu ∥ s4（s4a + s4b） | +17% / 311 µs | +25% / 879 µs |

配对 kernel 只用 32 个 CU 时，比用满 80 个 CU 慢 1.78–1.88 倍。

## P-71：重算（生产方）→ dav（消费方），只在 hip_kda 中实现（`examples/kda/p71_rec_dav_pipe.py`）
- **生产方**：重算递推每 PUB 步，由每个 wave 的 lane 0 用 release 写 `prog[(bh·4+vs)·4+wv] = i+1`。
- **消费方**：dav 第 1 段跑在另外 32 个 CU 的 stream 上，每个 CTA 先以 acquire 等到本 head 全部 16 个 wave 的进度都超过 i，再开始计算。
- **收尾**：主 stream 汇合两条 stream 后，在全部 CU 上跑 dav 第 2 段。递推是生产方，不会因为等待而停顿。
- **正确性**：带开关的逐位门禁 10/10；m 取 0、64、128 以及 cm = 2 时也都逐位一致。

**拆开测各项开销**（`p71_parts.py`，16K/12）：

| 项目 | 时间 |
|---|---|
| 重算单独跑 / 加上进度发布 | 452 / 489 µs（release 每次都要等 vmcnt(0)，发布带来 +35 µs） |
| dav 按 head 顺序 / 按 chunk 顺序 / 16 个 chunk 一块（块内按 head 顺序） | 282 / 475 / 337 µs（全部 80 个 CU） |
| 只用 32 个 CU：按 head 顺序 / 按 chunk 顺序 / 分块 | 521 / 679 / 527 µs |
| 重算与按 chunk 顺序的 dav 并发 | 重算涨到 685 µs（+54%），争用很重 |
| 重算加发布，与分块 dav（带等待）并发 | 重算 534 µs，dav 767 µs（消费方等待很多） |

**Wall 时间**（`pipe_time.py`，前向 + 反向）：
- 按 chunk 顺序：16K/12 为 0.95–0.98x，64K/12 为 0.96–0.97x；
- 分块顺序：16K/12 为 0.979–0.991x，64K/12 为 0.985–0.998x。
- **所有配置都没有变快。**

## 结论：方案 A（跨 kernel 流水）关闭
C-5 估计的上限在 16K/12 上有 200–300 µs，但实现时被以下几项依次吃掉：
1. 每次 release 发布都要排空 vmcnt，进度发布让递推多了 35 µs；
2. 消费方必须跟着生产顺序走，而按 chunk 的顺序会让 dav 慢 70%，还会大幅加重与递推的争用；分块顺序可以避免这两点，但消费方会因等待进度而落后；
3. 每对 kernel 要做两次 stream 交接，共 40–90 µs；
4. 递推本身因争用变慢 15–25%。

在 gfx936 上，前向（P-70 系列）和反向（P-71）都没有拿到正收益。代码保留为默认关闭的探针（`KDA_G2_PIPE` / `KDA_G2_BPIPE`），不合入，也不移植到 flash-train。

**方法上的教训**：只看资源争用的上限（C-4 / C-5）会系统性地高估收益。真正的流水还要再付三笔：同步发布、顺序约束、等待。小于约 300 µs 的上限，不值得做成实现。
