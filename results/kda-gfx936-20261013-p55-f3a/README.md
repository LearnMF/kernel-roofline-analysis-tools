# P-55：F3a，s4b 自己算 dAqk（结构搜索第 3 步）——逐位一致，但 s4b 慢 20%，证伪

**改动**（`examples/kda/p55_f3a.py`）：s4b 不再读取 dav 写出的 fp32 dAqk，改为自己计算。
- **aqA[b]**：A 操作数用本 wave 已经读入的 do 片段，B 操作数用第 b 行块的 Vn 片段；
- **aqB[b]**：两个操作数对调。`mmac_swap_probe.hip` 实测：对调后的结果与转置结果逐位一致，419 万个输出无一差异；
- **布局对齐**：MMAC 输出的布局是 [m][q+4e]，加载版是 [m][4q+x]，用同一 m 的 4 个 lane 之间做 4×4 转置（3 次 shuffle 加 select）把它对齐；
- 每个 wave 补读另外 3 个行块的片段（24 条 ld8），共 40 次 MMAC；
- 完整版（`full`）中 dav 同时跳过第一阶段，不再写 dAqk。

## 结果

| 项 | 结果 |
|---|---|
| 资源 | dense 实例 VGPR 仍为 236，变长实例 253→255，无溢出，LDS 不变 |
| 门禁（8192:12、8192:48，含 keep-state、极端门控、变长） | 全部逐位一致 |
| s4b 时间，只改 s4b 的 probe 版（每边 5 个进程） | 16K/12：1304→1625 µs（0.80）；16K/48：5947→7224 µs（0.82）；64K/12：5115→6345 µs（0.81）；8K/96：6814→7256 µs（0.94） |
| 模型预测 | s4b 快约 9%（第一版） |

dav 跳过第一阶段最多能省 1.1–1.2%（模型估算），抵不过 s4b 变慢 20%，整个算子约慢 5%。**判定证伪，完整版不再测。**

## 原因
1. **代码量几乎翻倍**：s4b 的 4 个 wave 各走一条按 A 特化的代码路径。每条路径加上 5 个 tile 的展开 MMAC 和转置后，kernel 从 5177 行变成 9409 行，4 条路径同时运行，指令缓存压力大增。
2. **主循环本身变长了**：寄存器总数没变，但主循环从 456 条变成 499 条（LDS 读 +6、waitcnt +9、VALU +24）。寄存器压力迫使编译器在循环里重新读表、插入更多等待。
3. **新增的计算落在关键路径上**：原来的 dAqk 读取发出后，要到循环里才用到，延迟被掩盖了；现在 MMAC 链和转置必须在进入循环前完成。
4. **第一版候选打分对访问模式的假设错了**：我按“64 行 × 4 B”的 gather 估算 s4b 读 aqB/akB 的代价（每条 229 个 TA 周期）。实际读源码，它是“4 行 × 64 B”（约 43 周期）。改正后，L1/L2 的预测从 +0.5% / +1.1% 变成 −0.7% / −0.1%，F3a 从 +3.0% 降到 +1.7%（`candidates_v2.txt`）。

## 规则
- **R46**：往 s4a/s4b 这类受延迟限制、VGPR 接近 256、按 wave 特化成 4 条代码路径的 kernel 里加代码，即使 VGPR 总数不变，也会因为代码膨胀和寄存器压力拉长主循环。评估器按“每条指令多少周期”累加，捕捉不到这类效应。凡是往这类宿主加工作的候选，不管模型怎么预测都视为高风险，先做实测探针。
- **R47**：访问模式必须从代码里推出来（每条指令覆盖几行、每行多少字节），不能凭名字猜。“gather”有 4 行 × 64 B 和 64 行 × 4 B 两种，TA 代价相差 5 倍多。
