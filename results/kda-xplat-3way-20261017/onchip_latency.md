# 片上资源、访存延迟与“能不能融合”：gfx936（BW1000）对比 A800 / H20（2026-10-17）

**数据来源**：
- `examples/kda/blocks/lat_inflight.cu`：设备属性；单线程指针追逐（随机环，每个节点占一条 128 B 的 cache line）测访存延迟；流式读取时“每个 CU/SM 在途字节数”与带宽的关系。bw52 用 HCU3（快卡），A800 用 a800-141 的 GPU1。
- `raw/a800_ncu_fla_occ_16384_12.csv`：用 ncu 在 A800 上统计 FLA 各 kernel 的 smem、寄存器和占用率。
- H20 这次没能实测，表中数值取自 Hopper 的公开规格和 10-12 的实测（78 SM，读带宽 3.82 TB/s）。

## 1. 片上资源

| | BW1000（gfx936） | A800（Ampere） | H20（Hopper） |
|---|---:|---:|---:|
| CU / SM 数 | 80 | 108 | 78 |
| 每 CU/SM 的 LDS / shared memory | **64 KB** | 164 KB（与 L1 共用 192 KB） | 228 KB（与 L1 共用 256 KB） |
| 全卡 LDS / smem | 5 MB | 17.3 MB | 17.4 MB |
| 每 CU/SM 的寄存器文件 | **512 KB**（512 VGPR × 64 lane × 4 B × 4 SIMD） | 256 KB | 256 KB |
| 全卡寄存器 | 40 MB | 27 MB | 19.5 MB |
| L2 | **8 MB** | 40 MB | 60 MB |
| 实测显存读带宽 | 1.24–1.34 TB/s | 1.77–1.86 TB/s | 3.82 TB/s |
| 显存延迟（指针追逐，工作集 1 GB） | 325 ns | 270 ns | 未测 |
| L2 命中延迟（1–4 MB） | 140–163 ns | 150 ns | 未测 |
| 异步搬运（global → smem，不占寄存器） | 无可用的通用机制，在途数据都要放在 VGPR 里 | cp.async | TMA + cp.async |

gfx936 唯一占优的是寄存器（每 CU 是 NV 每 SM 的 2 倍）。LDS 只有 A800 的 39%、H20 的 28%，L2 只有它们的 1/5 和 2/15。

## 2. FLA 的 kernel 是怎么用这些资源的（A800，16K/12，ncu）

| FLA kernel | 时间（µs） | 每 CTA 的 smem | 寄存器/线程 | 理论占用率 | 每 SM 驻留的 CTA 数 |
|---|---:|---:|---:|---:|---:|
| chunk_kda_bwd_kernel_wy_dqkg_fused | 2302 | 40 KB | 255 | **12.5%** | 1（受寄存器和 smem 限制） |
| chunk_kda_bwd_kernel_intra | 1056 | 10 KB | 255 | 12.5% | 8 个小 CTA |
| chunk_gated_delta_rule_bwd_kernel_dhu | 563 | **124 KB** | 252 | **6.25%** | 1，整个 grid 只有 48 个 CTA |
| chunk_gated_delta_rule_fwd_kernel_h（两次） | 489 / 490 | **120 KB** | 150 | 6.25% | 1 |
| recompute_w_u_fwd（两次） | 265 / 332 | 64 KB | 168 / 254 | 12.5% | 2 |
| chunk_kda_bwd_kernel_dAv | 152 | 64 KB | 193 | 12.5% | 2 |

**FLA 的主要 kernel 都在“每 SM 只驻留 1–2 个 CTA、占用率 6–12%”下运行，每个 CTA 用 40–124 KB 的 smem**，访存延迟靠 Triton 的多级软件流水（cp.async）来掩盖。其中 dhu 和前向 h 这两个 kernel，一个 CTA 用的 smem 就超过了 gfx936 一个 CU 的全部 LDS（64 KB）。

我们在 gfx936 上测过“把每 CU 的 CTA 数降到 1”的代价（P-78a/b、P-79）：
- s4b：+355 µs，慢 16%；
- prep：+565 µs，慢 35%；
- 即使把屏障全部去掉，s4b 也还要多 229 µs。

原因是 gfx936 没有通用的异步搬运：每个在途字节都要占 VGPR，而且以“读 → 屏障 → 计算”为阶段组织的 kernel 只能靠多个 CTA 交替运行来掩盖延迟。所以 gfx936 上每个 kernel 都必须做到 LDS ≤ 32 KB、VGPR ≤ 256，才能让每个 CU 放下 2 个 CTA。

## 3. 回答：是不是片上资源多，FLA 才能融合

**“能融合”这个前提，确实是 NV 的片上资源加异步搬运给的；但 FLA 并没有用它来少读写字节。**
- FLA 一次前向+反向有 22 个 kernel，我们是 12 个；FLA 读写的显存字节反而比我们多 56%（16K/12：7.42 GB 对 4.75 GB，见 `h20_bytes_tables.md`）。
- 唯一一处“FLA 合成一个、我们必须拆开”的是 wy + dqkg：FLA 是 `wy_dqkg_fused`，每 CTA 40 KB smem，每 SM 1 个 CTA；我们拆成 s4a 和 s4b，因为在 gfx936 上合并版更慢。
- 所以在 H20 上，FLA 快不是因为融合得多，而是：
  - 带宽是我们的 2.85 倍；
  - L2 大 7.5 倍，能接住一部分 kernel 之间交接的数据；
  - 大 smem 加异步流水，让它低占用率的大 tile kernel 也能跑得满。

**对我们的意义**：真正受片上资源限制的是我们自己的融合方案。例如 s4b + tail 每个 chunk·head 的工作集约 180–200 KB，在 gfx936 上根本放不下；在 H20 上（228 KB smem，每 SM 1 个 CTA 也不怕延迟）是放得下的。

## 4. 回答：延迟敏感会不会放大 gfx936 带宽不足的劣势

分两种情况，结论相反：

1. **直接的延迟：没有放大，反而缩小了差距。**
   - gfx936 的原始访存延迟并不比 A800 差多少：显存 325 对 270 ns，L2 命中都在 140–160 ns。
   - 流式读取时，每个 CU 只需约 8 KB 在途就能达到 1.22 TB/s（自身上限的约 98%）；A800 每个 SM 需要 16–32 KB 才能到 1.8 TB/s。
   - 在纯延迟或串行链受限的阶段，两边都被延迟卡住，带宽差距发挥不出来：
     - 前向递推：H20 / 我们 = 1.01；
     - dhu：0.66；
     - 对比流式阶段：收尾 0.40，dAv 0.31。

   所以延迟受限的阶段，恰恰是我们和 H20 差距最小的地方。

2. **间接的延迟：放大了，而且这是结构性的根源。**
   - gfx936 掩盖延迟只有一条路：在每个 CU 上放多个 CTA。而 LDS 只有 64 KB、在途数据又要占寄存器，每个 CTA 能用的工作集就很小，于是算子只能拆成更多 kernel，kernel 之间的交接字节就多了。
   - 现在实测字节是算法必需量的 5.86 倍，其中各 kernel 之间交接的接口字节就有 4.12 GB。
   - 字节一多，带宽劣势被成倍放大。
   - NV 可以用“大 smem + 异步流水 + 低占用率”的方式掩盖延迟，同样的融合在那里不会带来这个代价。

**一句话**：KDA 对延迟敏感，这本身没有让 gfx936 吃亏；吃亏的是 gfx936 只能靠提高占用率来掩盖延迟，这就封死了融合这条减少字节的路，最终把带宽不足的劣势放大了。
