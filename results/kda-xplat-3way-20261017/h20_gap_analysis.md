**测量说明**：
- A800 上的 FLA 今天在 a800-141 重测了一遍（`raw/a800_fla052_20261017.jsonl`），16 个形态与 10-11 的数据相差都在 ±0.4% 以内。所以沿用同一软件栈下测得的 H20 FLA 数据（10-12）是可靠的。H20 这台机器目前被其他团队的 sglang 服务占满，没有重测。
- bw52 上 HCU2、HCU4 两张卡比其余卡慢约 10%：同一个 s4 kernel 跑 8080 µs 对 7350 µs。之前每轮跟踪都把墙钟时间放在 HCU2 上测，HCU4 也分到过 3 个形态。另外主机上有一个从 10-07 起一直占满一个核的 root `cat` 进程，墙钟时间会受影响。这次的设备时间改用快卡重测，按离散度 ≤ 3% 挑选（`raw/bw_dev_*_merged.json`）。

## 2. 为什么还差：字节更少、利用率更高，但硬件带宽差了 2.85 倍

| 16K/12（TP8） | FLA 在 H20 上 | 我们在 BW1000 上 | 我们 / FLA |
|---|---:|---:|---:|
| 一次前向+反向读写的显存字节 | 7.42 GB（在 A800 上用 ncu 测，不清 cache） | **4.75 GB** | **0.64**（少 36%） |
| 实际达到的平均带宽 | 1.44 TB/s | 0.82 TB/s | 0.57 |
| 占本机实测峰值读带宽的比例 | 38%（峰值 3.82 TB/s） | **61%**（峰值 1.34 TB/s） | 1.6 倍 |
| 时间 = 字节 / 带宽 | 5.16 ms | 5.78 ms | 0.89 |

16K/48（TP2）：FLA 29.9 GB、1.63 TB/s，用时 18.33 ms；我们 19.9 GB（少 33%）、0.88 TB/s，用时 22.6 ms。

**结论**：我们读写的字节比 FLA 少约 1/3，带宽利用率是 FLA 的约 1.6 倍，两者合起来，单位工作的“字节效率”约为 FLA 的 2.5 倍。但 H20 的实测带宽是 BW1000 的 2.85 倍（L2 也大 7.5 倍：60 MB 对 8 MB），这笔硬件差距我们补不完。BW1000 有 3.4 倍的 bf16 算力（476 对 138 TFLOPS），但 KDA 的 MFU 只有 3–5%，这部分优势用不上。

**分阶段看**（16K/12，单位 µs，详见 `h20_gap_tables.md` 和 `h20_bytes_tables.md`）：

| 阶段 | FLA 在 H20 上 | 我们 | H20 / 我们 | FLA 在 H20 上的带宽 | 我们的带宽 | 字节（我们 / FLA） |
|---|---:|---:|---:|---:|---:|---:|
| 收尾（cumsum、门控反向、l2norm 反向） | 256 | 636 | 0.40 | **3.29 TB/s（峰值的 86%）** | 0.99 | 0.74 |
| dAv | 86 | 280 | 0.31 | **2.59 TB/s** | 1.01 | 1.26 |
| 前向准备 | 642 | 1014 | 0.63 | 1.86 TB/s | 0.84 | 0.71 |
| 反向重算（门控、w/u、v_new） | 724 | 833 | 0.87 | 1.29 TB/s | 0.96 | 0.85 |
| dhu | 438 | 660 | 0.66 | 0.93 TB/s | 0.61 | 0.99 |
| 前向递推 h + o | 582 | 573 | **1.01** | 1.20 TB/s | 0.66 | 0.55 |
| wy + intra（dq/dk/dg） | 2324 | 1785 | **1.30** | 1.22 TB/s | 0.79 | 0.50 |

- FLA 在 H20 上接近带宽上限的那些阶段（收尾、dAv、前向准备），我们只有它的 0.31–0.63，即使字节更少也追不上。差距主要在这里：收尾 +380 µs，前向准备 +371，dhu +222，dAv +193，合计 +1166 µs。
- FLA 在 H20 上受延迟或计算限制、带宽只用到 0.9–1.3 TB/s 的阶段（wy + intra、递推），H20 的带宽优势用不上，我们持平或更快：wy + intra 快 1.30 倍，少 539 µs。
- 16K/12 的净差距 = +640 µs。

**TP1（H=96）差得更多（0.71–0.72）的原因**：这次分析发现，s4a/s4b 按 head 折算的耗时随 H 增大而变长（见上节表格），TP1 时比线性多出约 11% 的总时间。根源是 grid 顺序，见 P-88。

## 3. “剩余空间很小”有没有数据？我之前的说法需要更正

### 3.1 有数据的部分：每个 kernel 离自身资源下限还有多远

资源下限 = 每个 kernel 最忙的那项资源（访存、TA、VALU、MMAC、递推串行链）实测忙了多久，即在当前字节数和指令构成不变时，理论上能压到的最短时间。

| | 实际 | 各 kernel 下限之和 | 差距（重叠不充分） | 接口下限（只读写各 kernel 的输入输出，且访存方式理想） | H20 FLA |
|---|---:|---:|---:|---:|---:|
| 16K/12 | 5770 µs | 4870 µs | 900 µs（15.6%） | 3352 µs | 5160 µs |
| 16K/48 | 22.6 ms | 约 18.4 ms | 约 4.2 ms（18.6%） | 约 12.2 ms | 18.33 ms |

16K/48 这一行的数据采自偏慢的 HCU4，已按快卡的总时间折算。

**这就是“难再追”的硬数据**：即使每个 kernel 都把等待完全掩盖、压到自己的资源下限，16K/12 也只比 H20 快 6%（4.87 对 5.16 ms），16K/48 只是与 H20 持平。要真正拉开差距，只能减少字节或改变各 kernel 的接口。

**900 µs 差距的构成和已经做过的实验**（16K/12）：

| kernel | 差距 | 已做过的实验和结果 |
|---|---:|---|
| s4b | 367 | 调整读取顺序（P-79 OT1/OT2：0.995–1.003，等待只是挪了位置）；完全去掉屏障的上限（P-79c：−8 µs）；重排输入布局的上限（P-73a：s4b −5.5%，扣除生产方的代价后算子只快 0.3–0.8%）；与 tail 融合（P-78/79：必须降到每 CU 1 个 CTA，+229–355 µs）。**P-88 改 grid 顺序：s4 −178 µs** |
| prep_a | 142 | 受 VALU 限制（76%）；与 prep_b 融合会慢 565 µs（P-78b）。VALU 本身还没有深挖 |
| wu | 133 | P-84b/c 已经拿掉大部分；剩下的还没有逐项细查 |
| 其余（s4a、dav、tail、prep_b、dhu、递推、gate） | 共 258 | dhu（P-74/75：≤ 0.6%）、递推（P-71/76：无收益）、tail（P-72：0.97–0.98）、加宽访存（ta_width：0） |

### 3.2 需要更正的部分

我上次说“剩下的空间很小”，依据只是 kernel **内部**的实验（调整读取顺序、预取、加宽访存、融合），这个结论下得太满了：

1. 16K/48 还有约 4.2 ms 的差距（18.6%），其中 wu（837 µs）、MODE 5 前向（603 µs）、prep_a（593 µs）三项都还没有专门做过实验。
2. **CTA 之间的维度此前没有查过**。这次按 head 数折算之后，发现 s4a/s4b 随 H 增大而变慢，于是做了 P-88：只把 grid 从 (NT, H) 换成 (H, NT)，结果逐位一致：
   - s4 kernel 快 1.11–1.55 倍；
   - 前向+反向：16K/12 快 1.028 倍，16K/48 快 1.068 倍，TP1 快 1.165–1.188 倍。

   s4b 那 367 µs 的差距里，有一部分并不是我原先以为的“调度挪不动”，而是同时驻留的 CTA 集合造成的 DRAM/TLB 访问局部性问题。

更准确的说法应该是：在三条约束下，kernel 内部的调度空间基本挖完了；但在 grid 顺序（CTA 之间）和少数还没细查的 kernel（TP2 下的 wu、前向 MODE 5、prep_a）上仍有空间。即使把这些都挖满，上限也就是在 TP2 上与 H20 持平、TP8 上快约 6%。要明显超过 H20，必须减少字节：
- 现在实测字节是算法必需量的 5.86 倍：4.75 GB 对 0.81 GB；
- 其中各 kernel 之间交接的接口字节是 4.12 GB，kernel 内部的中间结果 0.63 GB；
- 剩下的大块分别卡在这些约束上：
  - s4 交给 tail 的 fp32 dq/dk/dg，604 MB：融合要降低占用率，或者改用 bf16 而改变精度；
  - prep 的中间结果 R/Kb，265 MB：融合会慢 565 µs；
  - s4a 交给 s4b 的中间结果，约 300 MB：合并成一个 kernel 反而更慢；
  - fp32 的 g，302 MB：只能改精度；
  - Wb，101 MB：P-80a 实测是负收益。

## 4. 下一步
1. 合入 P-88（hip_kda 三台机器 + flash-train，只改 kernel 内部，不改接口），然后把 grid 顺序这个维度推广到所有按 chunk 并行的 kernel（wu、tail、prep_a/b、dav、gate），逐个做 A/B。
2. 对 TP2 下还没细查的 wu（837 µs）、前向 MODE 5（603 µs）、prep_a（593 µs）做 SQTT，并把等待点对应到源代码。
3. 测量规范：每轮跟踪避开 bw52 的 HCU2 和 HCU4；墙钟时间改在快卡上测，并先确认主机上没有占满 CPU 的进程。
